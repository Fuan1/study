## 페이지의 목적과 전환을 정할 때

규칙: 페이지는 한 가지 약속을 하고 한 가지 행동을 요청한다. 행동이 여럿이면 페이지를 나눈다.

| 구분 | 정하는 것 | 예 | 규칙 |
|---|---|---|---|
| 주 전환 | 목적을 이룬 이벤트 1개 | 견적 신청이 서버에 접수됨 | 버튼 클릭이 아니라 성공한 결과로 센다 |
| 보조 행동 | 주 전환 곁의 다른 행동 | 전화 걸기, 자료 받기 | 이벤트를 따로 두고 전환율에 더하지 않는다 |

이 글이 쓰는 정의다. 보고서에는 분모를 반드시 적는다.

| 지표 | 식 | 해석 |
|---|---|---|
| 도착률 | 랜딩 세션 / 광고 클릭 | 클릭보다 세션이 적으면 로딩 이탈이나 추적 누락이다 |
| 폼 완료율 | 제출 성공 / 폼 시작 | 폼 시작은 첫 필드를 만진 시점이다 |
| 전환율(CVR) | 주 전환 / 랜딩 세션 | 클릭 기준 CVR을 쓰는 곳도 있다. 분모를 맞춰 비교한다(m08) |

가상 예: 클릭 2,000, 세션 1,700, 폼 시작 340, 접수 119. 도착률 85%, 폼 시작률 20%, 폼 완료율 35%이고 곱하면 5.95%(클릭 기준)다. 세션 기준 CVR은 7.0%다. 같은 페이지도 분모에 따라 값이 다르다.

## 광고·검색에서 온 사람에게 약속을 이어 줄 때

규칙: 광고와 검색어가 한 약속(혜택, 대상, 조건, 행동)을 첫 화면에서 같은 말로 이어라. 같은 문장일 필요는 없고 같은 약속이면 된다.

| 점검 항목 | 광고·검색에서 | 첫 화면에서 | 어긋나면 |
|---|---|---|---|
| 혜택 | 약속한 결과 | 헤드라인이 같은 결과 | 클릭한 이유가 사라진다 |
| 대상 | 누구를 위한 것 | 같은 대상 표현 | 대상 아닌 사람이 남는다 |
| 조건·가격 | 가격, 기한, 조건 | 같은 조건이 같은 화면에 | 불신, 표시 문제(m13) |
| 용어 | 검색어에 쓴 말 | 헤드라인에 그 말 | 찾던 곳이 아니라고 느낀다 |
| 행동·시각 | 시킨 행동, 이미지 | 같은 CTA, 같은 톤 | 다른 곳으로 느낀다 |

<Figure caption="나쁜 예는 광고의 약속(견적, 바로)이 헤드라인에서 사라진다. 고친 예는 같은 약속을 잇는다. 가정한 문구다.">

- 광고 그룹마다 약속이 다르면 헤드라인도 달라야 한다. 소재나 검색어를 바꾸면 페이지도 같이 점검한다.
- Google Ads는 품질 점수의 구성 요소로 광고 관련성과 랜딩 페이지 경험을 둔다. 다만 품질 점수는 진단용이며 최적화할 목표가 아니라고 안내한다.<Ref n={1} /> 점수를 올리려는 게 아니라 일치를 점검하는 용도로 쓴다.

## 폼을 설계할 때

규칙: 필드는 "이 정보가 없으면 지금 요청한 일을 못 하는가"로 정한다. 못 하지 않으면 제출 뒤에 받는다.

<Callout kind="warn">
필드가 늘수록 입력 부담이 커져 완료율이 떨어지는 쪽이 일반 원칙이다. 얼마나 떨어지는지는 맥락마다 달라 수치를 쓰지 않는다. 필드를 줄이면 접수는 늘어도 문의의 질이 떨어질 수 있으니 후속 전환까지 본다.
</Callout>

| 필드 | 받는 조건 | 아니면 |
|---|---|---|
| 이메일 또는 전화 | 응답할 연락 수단이 필요하다 | 하나만 받고 선택은 사용자가 한다 |
| 회사명, 직책 | 응답 담당을 정하는 데 필요하다 | 제출 뒤 연락에서 묻는다 |
| 주소 | 지금 배송이나 방문이 필요하다 | 결제나 일정 단계에서 받는다 |

단계 나누기는 필드가 많거나 답에 따라 질문이 갈릴 때만 쓴다. 쉬운 질문부터 묻고 진행 위치를 보여 주며 뒤로 가도 입력을 유지한다. 단계가 늘면 이동 비용이 생기므로 한 장짜리와 같은 지표로 비교한다(u04).

| 규칙 | 기준 | 근거·연결 |
|---|---|---|
| 라벨 | 필드 위에 항상 보이는 라벨. 입력하면 사라지는 안내문만 두지 않는다 | WCAG 3.3.2<Ref n={2} /> |
| 자동 완성 | 이름, 이메일, 전화에 맞는 `autocomplete` 값을 쓴다 | WCAG 1.3.5, MDN<Ref n={2} /><Ref n={3} /> |
| 입력 형식 | 값에 맞는 입력 유형, 가능하면 선택지로 | u03 |
| 오류 | 틀린 필드 옆에 원인과 해결 방법을 쓰고 입력값 유지 | WCAG 3.3.1, u03 |
| 재입력 | 이미 받은 정보를 다시 묻지 않는다 | WCAG 3.3.7 |
| 제출 | 버튼 문구는 행동과 결과, 옆에 수집 고지 | m13 |

`autocomplete="off"` 를 폼 전체에 붙이지 마라. 없는 값을 지어내도 같은 효과가 난다.<Ref n={3} />

## CTA를 쓸 때

규칙: 한 화면에 주 CTA는 하나다. 문구는 행동과 결과를 같이 쓰고, 보조 행동은 시각적으로 약하게 둔다.

| 나쁜 예 | 고친 예 | 이유 |
|---|---|---|
| 제출 | 견적 확인하기 | 누르면 무엇을 얻는지 없다 |
| 자세히 보기 | 요금표 보기 | 어디로 가는지 모른다 |

크기와 대비는 UX 과정의 기준과 같다(u01, u05).<Ref n={4} />

| 항목 | 기준 | 비고 |
|---|---|---|
| 터치 영역 최소 | 24 x 24 CSS px 이상 | WCAG 2.5.8(AA). 간격이 충분하면 예외 |
| 터치 영역 권장 | 44pt(iOS), 48dp(Android) | 주 CTA에 적용한다 |
| 글자 대비 | 4.5:1 이상 | WCAG 1.4.3<Ref n={2} /> |

- 반복 CTA는 같은 행동에 같은 문구다. 위치마다 다른 행동을 시키지 않는다.

## 신뢰 요소를 놓을 때

규칙: 증거는 주장 옆, 그리고 사람이 망설이는 지점(입력, 결제 직전)에 둔다. 사용 규칙은 m04, 표시 의무는 m13이다.

| 요소 | 놓을 곳 | 규칙 |
|---|---|---|
| 후기 | 주장 아래, 폼 근처 | 실제 고객의 말만 쓰고 누구의 말인지 밝힌다 |
| 고객 로고 | 첫 화면 아래 | 실제 거래처만, 허락받고 쓴다 |
| 수치 | 헤드라인 근처 | 기준, 기간, 대상을 같이 적는다. 못 밝히면 쓰지 않는다 |
| 보증·환불 | CTA와 폼 옆 | 조건을 같은 화면에 쓴다 |
| 정책 링크 | 폼과 버튼 아래 | 환불, 개인정보, 사업자 정보. 항목은 m13 |

- 하지 마라: 근거 없는 최상급이나 만든 후기. 출처를 못 대면 빼라.

## 속도와 모바일을 점검할 때

규칙: 속도는 실제 방문자의 75번째 백분위로 판정하고 모바일과 데스크톱을 나눠 본다. 내 폰에서 빠른 것은 통과가 아니다.<Ref n={5} />

| 지표 | 좋음 | 랜딩에서 흔한 원인 | 처방 |
|---|---|---|---|
| LCP | 2.5초 이하 | 큰 히어로 이미지, 느린 서버 응답 | 첫 화면 이미지는 지연 로딩하지 않고 우선순위를 높인다<Ref n={6} /> |
| INP | 200ms 이하 | 오래 도는 스크립트(태그, 위젯) | 불필요한 스크립트를 뺀다 |
| CLS | 0.1 이하 | 크기 없는 이미지, 늦게 뜨는 배너·광고, 웹폰트 | 이미지에 너비·높이를 쓰고 자리를 미리 잡는다<Ref n={7} /> |

LCP 시간의 배분 가이드는 서버 응답 약 40%, 리소스 로드 지연 10% 미만, 로드 시간 약 40%, 렌더 지연 10% 미만이다. 시간 목표가 아니라 줄일 부분을 정하는 비율이다.<Ref n={6} /> 기준값은 바뀔 수 있다. 값은 2026년 10월에 확인했고 측정 방법은 u10에 있다.

- 첫 화면은 390px 폭에서 가로 스크롤 없이 보여야 한다.
- 쿠키 배너와 하단 바가 CTA와 입력창을 가리지 않는다.

## 접근성과 개인정보 고지를 확인할 때

규칙: 접근성은 기본 조건이다. 개인정보 고지는 위치만 이 글에서 정하고 문구와 항목은 m13을 따른다.

| 항목 | 기준 | 확인 방법 |
|---|---|---|
| 대비 | 글자 4.5:1 이상(1.4.3) | 대비 측정 도구로 확인 |
| 키보드 | 폼 제출까지 키보드로 가능, 포커스가 보임(2.1.1, 2.4.7) | Tab과 Enter만으로 끝까지 해 본다 |
| 대체 텍스트 | 의미 있는 이미지는 같은 뜻의 글(1.1.1) | 이미지를 끄고 읽어 본다 |
| 수집 고지 | 제출 버튼 근처에서 제출 전에 보인다 | 폼을 끝까지 내리지 않아도 보이는지 |

기준 번호는 WCAG 2.2 성공 기준이다.<Ref n={2} />

## 측정 이벤트를 설계할 때

규칙: 이벤트를 시작 전에 정한다. 주 전환은 서버의 성공 응답 뒤에 직접 보낸다. 이름은 예시다.

| 이벤트 | 발생 시점 | 담는 값 | 답하는 질문 |
|---|---|---|---|
| landing_view | 페이지 도착 | 소스, 캠페인, 소재 | 도착률, 소스별 전환율(UTM은 m12) |
| scroll | 화면 아래 90%가 처음 보임 | 없음 | 끝까지 내려가는가 |
| cta_click | CTA 클릭 | 위치, 문구 | 어느 CTA가 눌리는가 |
| form_start | 첫 필드를 만짐 | 폼 이름 | 폼 시작률 |
| field_focus | 필드를 만짐 | 필드 이름 | 필드별 도달 수, 이탈 필드 |
| field_error | 오류 메시지 표시 | 필드, 오류 유형 | 마찰이 큰 필드 |
| submit_success | 서버가 접수 성공 응답 | 폼 이름 | 주 전환 |
| submit_fail | 제출 실패 응답 | 오류 종류 | 속도·오류 단계 |

- GA4 향상된 측정에는 scroll(90% 깊이에 처음 도달할 때)과 form_start, form_submit이 있다. form_submit은 사용자가 제출한 시점이며 접수 성공을 뜻한다고 문서에 나오지 않으므로 주 전환은 submit_success를 직접 보낸다.<Ref n={8} />
- 필드 이탈은 필드를 만질 때마다 기록해 마지막 필드로 계산한다. 이탈 순간 보내는 이벤트는 누락될 수 있다.
- 개인정보 값(이름, 이메일, 전화)은 이벤트에 담지 않는다. 필드 이름과 상태만 보낸다(m13).

- 순서는 의심의 우선순위다. 클릭 대비 세션이 심하게 적으면 속도부터 본다.
- 비교 기준은 업계 평균이 아니라 지난 기간과 같은 페이지의 다른 소스·기기다. 한 번에 하나만 고친다.

| 증상 | 원인 | 처방 |
|---|---|---|
| 클릭 대비 랜딩 세션이 적다 | 로딩 중 이탈, 추적 누락 | 현장 LCP와 서버 응답을 보고 태그를 점검한다 |
| 특정 소스나 키워드만 전환이 낮다 | 의도가 다른 트래픽 | 검색어와 타깃을 정리하고 소스별 목표 CPA를 나눈다(m07, m08) |
| 소재별 전환 차이가 크다 | 광고와 헤드라인 약속 불일치 | 소재별로 헤드라인을 맞춘다 |
| 도착은 정상인데 CTA 클릭과 스크롤이 낮다 | 첫 화면에서 무엇을 주는지 안 읽힌다 | 헤드라인과 하위 문장을 다시 쓰고 처음 보는 사람에게 확인(u10) |
| 폼 시작 뒤 한 필드에서 크게 줄어든다 | 불필요하거나 민감한 필드, 형식 오류 | 삭제하거나 뒤로 미루고 오류 문구를 고친다 |
| 오류 이벤트가 많거나 한 기기만 낮다 | 제출 실패, 호환 문제 | 해당 환경에서 재현해 고친다 |
| 제출 직전에 이탈한다 | 비용, 개인정보, 다음 단계가 불확실 | 폼 옆에 정책, 보증, 후기를 둔다 |

## 전환율 변화를 해석할 때

규칙: 변화는 차이와 95% 신뢰구간으로 말한다. 구간이 0을 덮으면 변화가 있다고 말하지 않는다. 검정 기초는 d09, 실험 설계는 d10이다.

두 전환율 p1, p2와 표본 n1, n2에서 차이 `d = p2 - p1`, 표준오차 `SE = sqrt(p1(1-p1)/n1 + p2(1-p2)/n2)`, 구간은 `d ± 1.96 SE`다. python으로 계산한 가상 예다.

| 상황 | 전환율 | 차이 | 95% 구간 | 판정 |
|---|---|---|---|---|
| 군당 2,000명(100 대 120) | 5.0%에서 6.0% | +1.0%p | -0.4에서 +2.4%p | 0을 덮는다. p=0.165, 보류 |
| 군당 20,000명(1,000 대 1,200) | 5.0%에서 6.0% | +1.0%p | +0.6에서 +1.4%p | 0을 덮지 않는다. 개선 |

<Figure caption="같은 +1.0%p여도 군당 2,000명이면 구간이 0을 덮고, 20,000명이면 덮지 않는다. 가정한 숫자다.">
  <ConversionCI />
</Figure>

5.0%에서 6.0%를 검정력 80%, 양측 5%로 보려면 군당 8,159명이 필요하다(d10의 비율 표본 식). 앞 예의 2,000명은 그보다 훨씬 적다.

- 지난주와 이번 주를 비교하면 계절, 소재, 유입 구성이 같이 바뀐다. 가능하면 같은 기간에 두 버전을 동시에 보여 주는 A/B 테스트로 본다(d10).
- 기간은 7일의 배수로 잡고(관행), 계획한 표본이 찰 때까지 판정하지 않는다. 쪼갠 세그먼트는 표본이 줄어 구간이 넓어진다.
- 채택은 구간 하한이 손익분기 개선분을 넘는지로 정한다(m08).

## 점검 체크리스트

- 목적 1개와 주 전환 1개(서버 접수 성공)가 정해져 있고 보조 행동은 따로 재는가.
- 첫 화면에 헤드라인, 하위 문장, 주 CTA, 증거가 390px에서 스크롤 없이 보이는가.
- 소재와 검색어별로 헤드라인이 같은 약속을 하는가.
- 폼 필드마다 필요한 이유가 있고 라벨, 자동 완성, 오류 문구, 입력값 유지를 확인했는가.
- CTA 문구가 행동과 결과이고 터치 영역과 글자 대비가 기준 안인가.
- 후기, 수치, 보증에 출처와 조건이 있고 m13을 점검했는가.
- LCP, INP, CLS를 현장 75번째 백분위로 확인했는가.
- 키보드 제출, 포커스 표시, 대체 텍스트, 수집 고지 위치를 확인했는가.
- 이벤트가 빠짐없이 있고 개인정보 값은 보내지 않는가.
- 전환율 변화를 차이, 신뢰구간, 기간으로 보고했는가.
