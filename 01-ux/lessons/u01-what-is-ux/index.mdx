<Overview>

**UX(User Experience, 사용자 경험)** 는 사람이 제품이나 서비스를 쓰기 전, 쓰는 동안, 쓴 뒤에 갖게 되는 인식과 반응 전체다. 화면의 모양(UI)은 그중 눈에 보이는 일부일 뿐이다.

- UI 문제는 보이는 방식을 고치면 풀린다. UX 문제는 흐름, 구조, 기능 범위, 목적까지 내려가 봐야 풀린다.
- 예뻐 보이는 것과 쓰기 쉬운 것은 다르다. 첫인상이 좋으면 불편이 덜 눈에 띈다.
- 화면 층(UI)에는 통용되는 기준 수치가 있다(글자 대비 4.5:1, 터치 영역 44pt 등). 그 아래 층은 수치가 아니라 사용자 관찰로 확인한다.

</Overview>

## 정의

### 표준과 업계의 정의

- **ISO 9241-210**: 제품, 시스템, 서비스를 사용하거나 사용을 예상할 때 사람이 갖게 되는 인식과 반응. 사용 전, 중, 후의 감정, 믿음, 선호, 행동 등이 모두 들어간다.<Ref n={1} />
- **Nielsen Norman Group**(Don Norman, Jakob Nielsen): 기업, 서비스, 제품과 사용자가 맺는 상호작용의 모든 측면.<Ref n={2} />
- 용어는 1990년대 Apple에서 Don Norman이 직함에 쓰면서 퍼진 것으로 알려져 있다. 정확한 시점과 경위는 확인 필요.

두 정의의 공통점은 기준이 화면이 아니라 사람의 인식과 반응이라는 점이다. 같은 화면도 사용자, 상황, 기대에 따라 다른 경험이 된다.

### 비슷한 용어와의 구분

| 용어 | 가리키는 것 | 무엇으로 판단하나 |
|---|---|---|
| UX | 사용 전, 중, 후에 겪는 인식과 반응 전체 | 쓰고 나서 어떻게 느끼고, 다시 쓰는가 |
| UI | 화면에서 눈과 손에 닿는 부분(색, 글꼴, 버튼, 배치) | 읽히는가, 눌리는가, 일관적인가 |
| 사용성 | 정해진 사용자가 정해진 상황에서 목표를 달성하는 정도<Ref n={3} /> | 효과성, 효율성, 만족도 |
| CX | 광고, 구매, 배송, 상담까지 포함한 고객과 기업의 모든 접점 | 제품 밖의 접점까지 |

<Callout>
UX는 만들어 내는 결과물이 아니라 사용자가 겪는 일이다. 설계자는 경험 자체가 아니라 좋은 경험이 생기도록 조건을 설계한다.
</Callout>

- 화면 캡처만 보면 A와 B는 구분되지 않는다. 차이는 순서와 실패했을 때의 반응에서 나온다.
- 실패했을 때의 동작(내용 삭제 vs 자동 저장)은 화면 디자인 목록에 잘 나타나지 않아 빠뜨리기 쉽다.

## UX의 5개 층

Jesse James Garrett은 UX를 전략, 범위, 구조, 골격, 표면의 5개 층으로 나눈다.<Ref n={5} /> 아래층의 결정이 위층의 선택지를 정한다.

<Figure caption="위로 갈수록 눈에 보이고, 아래로 갈수록 이유에 가깝다. 앞의 빙산과 같은 대상을 다른 방식으로 자른 것이다.">
  <PlanesStack />
</Figure>

| 층 | 정하는 것 | 어긋나면 나타나는 증상 |
|---|---|---|
| 표면 | 색, 글꼴, 아이콘, 이미지 등 감각적 마감 | 글자가 흐리다, 화면마다 스타일이 다르다 |
| 골격 | 인터페이스, 내비게이션, 정보의 배치 | 버튼이 붙어 있어 오조작한다, 메뉴를 못 찾는다 |
| 구조 | 상호작용 방식, 정보 구조(분류와 순서) | 어디에 올릴지 모른다, 흐름이 중간에 끊긴다 |
| 범위 | 넣을 기능과 콘텐츠 | 핵심 기능이 없거나, 안 쓰는 기능이 가득하다 |
| 전략 | 사용자의 요구와 제품의 목표 | 만들어 놓아도 쓸 이유가 없다 |

<Callout kind="warn">
위층만 고치면 아래층 문제는 그대로 남는다. 표면을 다듬었는데 사용자가 계속 막힌다면 원인은 더 아래에 있다.
</Callout>

## 좋은 UX를 이루는 요소

### 사용성의 5가지 품질

Jakob Nielsen은 사용성을 다섯 가지 품질로 나누고, 별도로 유용성(필요한 기능이 있는가)을 함께 본다.<Ref n={4} />

| 품질 | 묻는 것 |
|---|---|
| 학습 용이성 | 처음 보는 사용자가 기본 과업을 얼마나 쉽게 하는가 |
| 효율성 | 익숙해진 뒤 얼마나 빨리 하는가 |
| 기억 용이성 | 한동안 안 쓰다 돌아와도 다시 쉽게 쓰는가 |
| 오류 | 오류가 얼마나 자주, 얼마나 심각하게 나는가. 복구는 쉬운가 |
| 만족도 | 쓰는 것이 즐거운가 |

### 측정하는 방법

ISO 9241-11은 사용성을 효과성, 효율성, 만족도로 본다.<Ref n={3} /> 실무에서는 이렇게 숫자로 바꾼다.

| 관점 | 흔히 쓰는 지표 |
|---|---|
| 효과성 | 과업 완수율, 오류 횟수 |
| 효율성 | 소요 시간, 클릭·탭 수 |
| 만족도 | SUS 같은 설문 점수 |

SUS(System Usability Scale)는 10문항 설문으로 0에서 100점을 낸다.<Ref n={13} /> 여러 제품을 모은 평균이 대략 68점이라는 보고가 자주 인용된다(확인 필요).

<Callout kind="warn">
68점은 합격선이 아니라 평균일 뿐이다. 다른 제품과 비교하거나 같은 제품의 전후를 비교할 때 의미가 있다.
</Callout>

### UX 허니콤

Peter Morville은 UX를 일곱 가지 측면으로 정리했다.<Ref n={6} /> 사용 가능(Usable)은 그중 하나일 뿐이다.

<Figure caption="쉬운 것(사용 가능)만으로는 부족하다. 쓸모, 매력, 신뢰, 접근성까지 함께 본다.">
  <Honeycomb />
</Figure>

| 요소 | 묻는 것 |
|---|---|
| 유용 | 쓸모가 있는가 |
| 사용 가능 | 쉽게 쓸 수 있는가 |
| 바람직 | 매력과 감성이 있는가 |
| 찾기 쉬움 | 제품과 그 안의 정보를 찾을 수 있는가 |
| 접근 가능 | 장애가 있어도 쓸 수 있는가 |
| 신뢰 | 믿을 수 있는가 |
| 가치 있음 | 사용자와 사업 모두에게 가치가 있는가 |

## 핵심 원칙 3가지

### 발견 가능성과 이해 가능성

Don Norman은 좋은 설계의 첫 조건을 두 가지로 둔다.<Ref n={7} />

- **발견 가능성**: 어떤 행동이 가능한지 알아낼 수 있는가
- **이해 가능성**: 제품이 어떻게 작동하고 어떻게 쓰는지 알 수 있는가

행동이 일어날 위치와 방식을 알려주는 신호를 시그니파이어라고 한다. 신호가 틀리면 사용자가 아니라 설계가 틀린 것이다.

<Figure caption="세로 손잡이가 달린 문은 당기라는 신호를 주지만 실제로는 밀어야 한다. 평평한 판은 밀라는 신호를 주고 실제로도 민다.">
  <NormanDoor />
</Figure>

<Callout kind="warn">
설명서를 안 읽는 것은 사용자의 문제가 아니다. 설명이 필요한 순간 이미 신호 설계가 실패한 것이다.
</Callout>

### 생각하게 만들지 마라

Steve Krug의 첫 번째 사용성 법칙이다.<Ref n={8} />

- 화면이 자명(self-evident)하면 가장 좋다. 그것이 안 되면 최소한 설명 없이 알 수 있게(self-explanatory) 한다.
- 사용자는 읽지 않고 훑는다. 최선의 선택이 아니라 처음 괜찮아 보이는 것을 고른다. 이유를 몰라도 대충 헤쳐 나간다.
- 질문이 하나 늘 때마다(이게 눌리는 건가, 이 이름은 무슨 뜻인가) 사용자의 부담이 쌓인다.

### 예뻐 보이면 쓸 만해 보인다

Aesthetic-Usability Effect는 보기 좋은 디자인을 더 쓰기 쉽다고 느끼는 경향이다.<Ref n={14} />

| 연구 | 보고된 것 | 해석할 때 주의 |
|---|---|---|
| Kurosu & Kashimura (1995)<Ref n={9} /> | ATM 화면 26종, 참가자 252명. 겉보기 사용성은 실제 사용성보다 미적 평가와 더 강하게 이어졌다 | 사용자는 예쁜 화면을 쓰기 쉽다고 느낄 뿐, 실제로 쉽다는 증거는 아니다 |
| Lindgaard 외 (2006)<Ref n={10} /> | 화면을 50ms만 보여줘도 시각적 매력 평가가 더 오래 본 평가와 높게 이어졌다 | 첫인상이 빨리 굳는다는 뜻이다. 사용성을 판단했다는 뜻은 아니다 |

<Callout kind="warn">
호감이 불편을 가려 사용성 테스트에서 문제가 덜 드러날 수 있다고 알려져 있다.<Ref n={14} /> 예쁜 시안에 대한 좋은 반응을 사용성의 증거로 쓰지 않는다.
</Callout>

## UI 층의 통용 기준값

표면과 골격에는 수치로 검증할 수 있는 기준이 있다. 구조, 범위, 전략에는 그런 수치가 없고 사용자를 관찰해서 확인한다.

| 항목 | 기준 | 출처 |
|---|---|---|
| 본문 글자 대비 | 4.5:1 이상(AA). 7:1 이상이면 AAA | WCAG 1.4.3, 1.4.6<Ref n={11} /> |
| 큰 글자 대비 | 3:1 이상. 큰 글자는 18pt(약 24px) 이상 또는 굵은 14pt(약 18.7px) 이상 | WCAG 1.4.3 |
| 버튼, 아이콘 등 UI 요소 대비 | 인접한 색과 3:1 이상 | WCAG 1.4.11 |
| 터치 영역 최소 | 24×24 CSS px 이상. 간격이 충분하면 예외 | WCAG 2.5.8(AA) |
| 터치 영역 권장 | iOS 44×44pt, Android(Material) 48×48dp<Ref n={12} /> | Apple HIG, Material Design |
| 터치 영역 강화 | 44×44 CSS px | WCAG 2.5.5(AAA) |

<Figure caption="같은 회색 계열이라도 4.5:1을 넘느냐에 따라 통과와 미달이 갈린다. 비율은 WCAG 공식으로 계산한 값이다.">
  <Contrast />
</Figure>

<Callout kind="warn">
기준을 채웠다고 좋은 UX가 되는 것은 아니다. 대비와 크기가 완벽해도 흐름이 틀리면 사용자는 막힌다.
</Callout>

## 흔한 오해와 주의점

| 오해 | 실제 | 주의할 점 |
|---|---|---|
| UX는 예쁜 화면이다 | 화면은 5개 층 중 맨 위 하나다 | 시안에 대한 호감을 성과로 착각하기 쉽다 |
| UX는 쉬움이다 | 쉬움은 사용성의 일부다. 쓸모, 신뢰, 접근성도 포함한다 | 쉬워도 필요 없으면 쓰지 않는다 |
| 내가 쓰기 편하면 된다 | 만든 사람은 이미 구조를 알고 있다 | 제작자와 처음 쓰는 사람의 시선이 다르다. 아는 사람이 모르는 사람의 입장을 잊는 현상을 지식의 저주라고 부른다 |
| 기능이 많을수록 좋다 | 기능 수는 범위 층의 결정이다 | 선택지가 늘수록 결정 비용이 커진다(U4에서 다룬다) |
| 사용자에게 물어보면 답이 나온다 | 사용자는 자기 행동을 정확히 설명하지 못할 때가 많다 | 말보다 행동을 관찰한다(U8에서 다룬다) |
| UX에 1원을 쓰면 100원이 돌아온다 | 널리 퍼진 수치지만 출처가 불분명한 경우가 많다 | 인용 전에 원출처 확인 필요 |

## 실전 진단표

사용자가 막혔다고 할 때 가장 먼저 할 일은 어느 층의 문제인지 정하는 것이다. 층을 잘못 짚으면 엉뚱한 곳을 고친다.

| 증상 | 의심할 층 | 먼저 볼 것 |
|---|---|---|
| 글자가 안 읽힌다, 산만해 보인다 | 표면 | 글자 대비, 글자 크기, 스타일 일관성 |
| 눌러야 할 곳을 못 찾는다, 오조작이 난다 | 골격 | 버튼 배치와 간격, 터치 영역 크기 |
| 원하는 곳으로 가지 못하고 되돌아온다 | 구조 | 분류 이름, 메뉴 구조, 흐름의 단계 수 |
| 기능은 많은데 안 쓰이거나, 필요한 기능이 없다 | 범위 | 핵심 과업 대비 기능 목록 |
| 가입한 뒤 떠난다, 쓸 이유가 없다 | 전략 | 사용자가 얻고 싶은 것, 제품의 약속 |
| 예쁘다는 말은 듣는데 완수율이 낮다 | 아래층 전체 | 사용자가 실제로 쓰는 모습 관찰 |

층을 정한 뒤 세 가지를 물어본다.

1. 목표를 끝냈는가(효과성)
2. 몇 단계, 몇 초가 걸렸는가(효율성)
3. 다시 쓰고 싶어 하는가(만족도)

## 사례

| 사례 | 층 | 핵심 |
|---|---|---|
| Google 검색 첫 화면 | 범위, 구조 | 기능을 검색 하나로 좁혀 흐름이 짧다. 처음 온 사람도 무엇을 할지 고민하지 않는다 |
| Amazon 1-Click 주문(1990년대 후반 도입) | 구조 | 결제 단계를 줄인 사례다. 화면 꾸밈이 아니라 흐름의 변경이다. 효과 수치는 출처 확인 전까지 인용하지 않는다 |
| 초기 iPod(2001) | 전략 | 용량 스펙(5GB)보다 사용자가 얻는 가치(주머니 속 1,000곡)로 제품을 설명했다는 점이 자주 언급된다 |
| 밀어야 하는 문의 세로 손잡이 | 골격 | 신호와 동작이 어긋난 대표 사례(그림 5) |
| 글쓰기 5단계 vs 4단계 | 구조 | 같은 UI에서 흐름만 다른 가정 예시(그림 2). 실제 서비스가 아니다 |
