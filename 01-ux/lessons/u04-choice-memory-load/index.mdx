- 선택지가 많으면 묶고, 추천과 기본값을 하나 정하고, 드문 항목은 접어라. 줄이는 것만이 답은 아니다.

- 점진적 공개는 두 단계까지만 쓰고, 자주 쓰는 항목은 숨기지 마라.

## 선택지가 많을 때

규칙: 선택지를 무작정 줄이지 말고, 고르기 어려운 이유를 먼저 가려라.

선택 시간은 선택지 수 n에 대해 대략 `log2(n+1)`에 비례해 늘어난다(Hick-Hyman 식).<Ref n={1} /> 선택지가 2배가 되어도 시간은 2배가 되지 않는다.

<Figure caption="선택지가 2배가 될 때마다 늘어나는 양은 1 안쪽이다. 식으로 계산한 모양이며 사람을 측정한 값이 아니다.">
  <HickCurve />
</Figure>

이 식을 "적을수록 빠르다"의 근거로 쓰지 마라. 맞는 조건이 좁다.<Ref n={2} />

| 조건 | 어긋나면 |
|---|---|
| 모든 선택지가 같은 확률로 고른다 | 자주 쓰는 항목은 더 빨리 고른다 |
| 신호를 보고 정해진 키를 누르는 과제 | 보이는 대상을 직접 가리키면 증가가 거의 없다 |
| 처음 쓰는 사용자 | 연습하면 증가폭이 줄어든다 |
| 순서 없는 목록 | 가나다순처럼 익숙한 순서면 로그에 가깝게 찾는다 |
| 고르는 시간만 | 읽고 이해하는 시간은 식 밖이다 |

<Callout kind="warn">
HCI 화면에 이 법칙을 적용한 연구는 "적을수록 좋다"를 지지하지 않는다고 본다.<Ref n={3} /> 정렬된 목록은 항목이 많아도 로그로만 늘기 때문에, 단계를 늘려 항목을 줄이면 오히려 느려질 수 있다.<Ref n={4} />
</Callout>

처방은 원인에 맞춰 고른다.

| 상황 | 처방 | 주의 |
|---|---|---|
| 비슷한 항목이 많다 | 이름 붙인 그룹으로 묶는다 | 그룹 이름은 사용자가 아는 말로 쓴다 |
| 고를 기준이 없다 | 추천이나 기본값을 하나 눈에 띄게 두고 비교 기준을 보여 준다 | 전후를 같은 지표로 비교해 확인한다 |
| 한 번에 정할 것이 많다 | 결정을 단계로 나눠 단계마다 하나만 묻는다 | 단계가 늘면 이동 비용이 생긴다 |
| 목록을 정렬할 수 있다 | 익숙한 순서로 정렬하고 다 보여 준다 | 이름이 모호하면 넓은 목록도 훑기 어렵다<Ref n={4} /> |
| 드물게 쓰는 항목이다 | 접어 둔다 | 아래 점진적 공개 규칙을 따른다 |

<Callout kind="warn">
선택지가 많으면 구매가 줄어든다는 결과가 유명하다(잼 24종 대 6종에서 구매가 크게 갈렸다).<Ref n={5} /> 하지만 50개 실험을 합친 메타분석은 평균 효과를 거의 0으로 보고했다.<Ref n={6} /> 선택지 구성이 복잡하고 과제가 어렵고 선호가 불확실할 때 효과가 커진다고 정리한 분석도 있다.<Ref n={7} /> "많으면 항상 나쁘다"로 쓰지 말고, 줄이기 전후를 같은 지표로 비교해라.
</Callout>

## 메뉴와 탭 항목 수를 정할 때

규칙: 항목 수는 공식 가이드의 수치로 정한다. "7개 이하"는 근거가 아니다.

7±2는 바로 따라 말할 수 있는 항목 수에 대한 이야기다. Laws of UX도 이를 설계 제한의 근거로 쓰지 말라고 안내한다.<Ref n={8} /> 화면에 보이는 항목은 기억에 의존하지 않는다.

| 출처 | 기준 | 비고 |
|---|---|---|
| Material 3 하단 바 | 3개에서 5개 | 안드로이드 구현의 기본 라벨 모드는 3개 이하면 전부 보이고 4개 이상이면 선택된 항목만 보인다<Ref n={9} /> |
| Apple HIG 탭 바 | 최대 수치 없음 | 적을수록 이동이 쉽다. 공간이 모자라면 마지막 탭이 More로 바뀌어 찾기 어려워진다. 사용자가 탭을 고르게 할 때 기본 목록은 5개 이하를 권한다<Ref n={10} /> |
| NN/g 모바일 탭 바 | 5개 이하 | 아이콘에는 가능하면 라벨을 붙인다<Ref n={11} /> |
| NN/g 모바일 최상위 메뉴 | 4개 이하면 노출 | 4개를 넘을 때 숨김을 고려한다<Ref n={12} /> |

<Figure caption="탭 바는 3개에서 5개, 모바일 최상위 메뉴는 4개 이하면 보이게 둔다. 6개 이상이면 묶거나 다른 패턴을 쓴다.">
  <NavCount />
</Figure>

숨기면 쓰임이 줄어든다. NN/g 연구에서 모바일 사용자는 숨긴 내비게이션을 약 57퍼센트의 경우에 썼고, 보이는 메뉴를 곁들이면 약 86퍼센트였다. 과업 시간은 숨긴 쪽이 약 15퍼센트 느렸다.<Ref n={12} />

- 모든 칸에 아이콘과 라벨을 함께 둬라.
- 항목이 넘치면 묶거나 우선순위로 줄여라. 넘치는 항목을 More에 밀어 넣지 마라.

## 메뉴를 깊게 할지 넓게 할지

규칙: 깊이는 가능한 한 얕게 두고, 정렬된 익숙한 목록은 넓게 보여 줘도 된다.

| 상황 | 기준 | 한계 |
|---|---|---|
| 같은 목적지를 나눌 때 | 2단계에 단계당 8개 구성이 가장 빨랐다(64개 목적지 기준)<Ref n={13} /> | 1981년 데스크톱 메뉴 실험이다. 설계 세부는 확인 필요 |
| 사이트 구조 | 깊이가 늘수록 탐색 성능이 나빠졌다<Ref n={14} /> | 최적 넓이 수치는 확인 필요 |
| 정렬된 익숙한 항목 | 다 보여 주는 쪽이 3묶음으로 나눈 것보다 빨랐다(미국 50개 주 예)<Ref n={4} /> | 정렬되지 않았거나 이름이 모호하면 해당 없음 |

<Callout kind="warn">
위 연구는 모바일 이전 환경이다. 폭이 좁은 모바일 화면에 그대로 옮기지 말고 우리 화면에서 확인해라.
</Callout>

클릭 수보다 클릭마다 드는 고민을 줄여라. 클릭이 여러 번이어도 각 단계의 선택지가 구별되면 괜찮다.<Ref n={15} /> 환영 문구와 늘어진 설명은 먼저 지우고, 설명이 필요한 곳은 화면을 고쳐 설명을 없앤다.<Ref n={15} />

## 숨길지 보여 줄지

규칙: 자주 쓰거나 필수인 것만 먼저 보이고, 고급·드문 기능은 요청할 때 보이게 한다.<Ref n={16} />

| 기준 | 내용 |
|---|---|
| 단계 수 | 두 단계까지. 세 단계 이상이면 길을 잃기 쉽다<Ref n={16} /> |
| 무엇을 숨기나 | 사용 데이터와 관찰로 드문 기능을 가려낸다 |
| 단서 | 더 보기 같은 버튼을 보이게 두고 무엇이 나올지 적는다 |

<Figure caption="기본 화면에는 자주 쓰는 설정만 두고 나머지는 한 번 눌러 연다. 가정한 설정 화면이며 실제 서비스가 아니다.">
  <Disclosure />
</Figure>

| 나쁜 예 | 고친 예 | 이유 |
|---|---|---|
| 모든 설정을 한 목록에 나열 | 자주 쓰는 것 몇 개와 고급 설정 더 보기 | 처음 쓰는 사람은 필요한 것에 집중하고 숙련자는 쓸데없는 항목을 훑지 않는다 |
| 자주 쓰는 메뉴까지 햄버거 안에 숨김 | 모바일 최상위 4개 이하는 노출 | 숨기면 사용이 약 57퍼센트로 떨어졌다 |
| 버튼 이름이 그냥 더 보기 | 고급 설정 더 보기 | 무엇이 나올지 알려야 누른다 |
| 3단계 이상 중첩된 설정 | 2단계로 압축 | 깊이가 늘면 길을 잃는다 |

<Callout kind="warn">
점진적 공개는 감추기와 다르다. 자주 쓰는 항목까지 숨기면 발견 가능성과 속도가 함께 떨어진다.
</Callout>

## 사용자가 기억해야 할 때

규칙: 외우게 하지 말고 보이는 것 중에서 고르게 한다. 외워야 하는 숫자는 의미 단위로 끊어 보여 준다.

- 이전 화면의 값을 기억해 다음 화면에 입력하게 하지 마라. 그 값을 다시 보여 주고 고르게 해라.
- 기억 단위는 낱개가 아니라 사용자에게 의미 있는 덩어리다. 같은 숫자열도 아는 사람에게는 한 덩어리다.

<Figure caption="같은 숫자라도 묶으면 확인할 단위가 줄어든다. 숫자는 모두 가정한 예시다.">
  <Chunking />
</Figure>

| 대상 | 묶는 방식 | 근거와 주의 |
|---|---|---|
| 카드 번호 | 실물 카드처럼 4자리 블록으로 띄어 쓰고 자동 띄어쓰기를 지원한다 | Baymard 결제 테스트에서 사용자는 4자리 단위로 입력하고 확인했다. 자동 띄어쓰기를 하지 않은 사이트가 15퍼센트였다<Ref n={17} /> |
| 전화번호 | 3-4-4 같은 관례 단위로 끊는다 | 번호 체계는 나라와 회선에 따라 다르다 |
| 긴 목록과 메뉴 | 의미가 같은 항목끼리 이름 붙인 그룹으로 묶는다 | 그룹 이름은 사용자가 아는 말이어야 한다 |
| 긴 입력 양식 | 관련 필드를 구역으로 나눈다 | 임의로 쪼개면 덩어리가 아니라 단계만 는다 |

묶는 기준은 개수가 아니라 뜻이다. 4개씩 자르기 전에 사용자가 하나로 이해하는 단위를 찾아라.

## 중요한 항목을 둘 위치

규칙: 가장 중요한 목적지는 맨 앞과 맨 끝 칸에 두고, 보조 항목은 가운데에 둔다.

<Callout kind="warn">
이 규칙은 목록 회상에서 처음과 끝이 잘 남는다는 서열 위치 효과에서 끌어낸 설계 경험칙이다. 하단 탭의 양 끝이 더 많이 눌린다는 것을 보인 근거는 없다.<Ref n={18} /> 사용 빈도와 작업 흐름이 우선이고, 클릭률은 따로 측정해라.
</Callout>

## 무엇부터 만들고 다듬을지

규칙: 개선은 가장 자주 쓰는 소수의 기능과 화면에 먼저 모은다.

흔히 결과의 80퍼센트가 원인의 20퍼센트에서 나온다고 말한다(파레토 원칙). 정확한 상수가 아니라 90 대 10이나 70 대 30일 수도 있다.<Ref n={19} />

<Callout kind="warn">
파레토는 법칙이 아니라 우선순위를 정하는 경험칙이다. 기능의 80퍼센트가 쓸모없다는 뜻이 아니다. 드물게 쓰는 기능(결제 오류 복구 등)이 치명적일 수 있으니 실제 사용 데이터로 확인해라.
</Callout>

## 증상으로 찾기

| 증상 | 원인 | 처방 |
|---|---|---|
| 선택지 화면에서 오래 머물다 이탈한다 | 기준 없이 항목이 많다 | 추천이나 기본값을 두고 비교 기준을 보여 준다. 전후를 측정한다 |
| 하단 탭에 항목이 6개 이상이다 | 가이드 범위 초과 | 묶거나 우선순위로 줄이고 나머지는 다른 패턴으로 옮긴다 |
| 카드 번호나 계좌를 자주 틀린다 | 긴 숫자를 한 덩어리로 보여 준다 | 자동 띄어쓰기와 묶음 표시를 넣는다 |
| 가운데 탭이나 메뉴를 못 찾는다 | 위치와 이름이 모호하다 | 핵심을 양 끝에 두고 이름을 사용자의 말로 바꾼다 |
| 같은 메뉴를 열었다 닫았다 한다 | 라벨이 서로 구별되지 않는다 | 라벨을 구별되게 고치고 단계 수를 점검한다 |
| 초보자가 설정 화면에서 길을 잃는다 | 모든 설정이 한 곳에 있다 | 자주 쓰는 것만 먼저 두고 고급은 접는다 |
| 메뉴를 숨겼더니 이용이 줄었다 | 숨김 내비게이션 | 핵심 항목은 항상 보이게 둔다 |
| 안 쓰는 기능이 가득하다 | 우선순위 없이 기능을 늘렸다 | 사용 데이터로 상위 기능에 개선을 모은다 |

## 점검 체크리스트

- 하단 탭이 3개에서 5개이고 모든 칸에 아이콘과 라벨이 있는가.
- 모바일 최상위 메뉴가 4개 이하이면 보이게 두었는가.
- 항목 수 근거로 7개 이하를 쓰지 않았는가.
- 선택지 화면에 기본값이나 추천이 하나 눈에 띄는가.
- 정렬할 수 있는 긴 목록은 익숙한 순서로 정렬했는가.
- 숨긴 항목은 드물게 쓰는 것뿐이고, 더 보기 버튼이 무엇이 나올지 알려 주는가.
- 숨김이 두 단계를 넘지 않는가.
- 긴 숫자 입력은 의미 단위로 끊어 보여 주는가.
- 인사말과 설명을 반으로 줄여 보았는가.
