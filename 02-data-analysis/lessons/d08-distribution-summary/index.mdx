## 요약값을 고를 때

규칙: 평균을 기본값으로 두지 말고, 분포 모양과 쓰임이 요약값을 정하게 해라.

| 요약값 | 쓰는 때 | 이상치·치우침 |
|---|---|---|
| 평균 | 합계로 되돌릴 때(총매출 = 평균 × 건수). 대칭이고 이상치가 없을 때 | 매우 민감하다 |
| 중앙값 | "보통 건"의 값. 치우친 값의 기본 요약 | 둔감하다. 극단값이 절반 미만이면 거의 안 움직인다 |
| 최빈값 | 범주(가장 많은 등급), 정수 점수 | 연속값은 구간 폭에 따라 바뀐다. 폭을 같이 적는다 |
| 분위수 p25, p75, p90, p95, p99 | 꼬리를 봐야 할 때(지연, 기준 초과 비율) | p50 근처는 둔감하다. p99 같은 끝 분위수는 표본이 작으면 흔들린다 |
| 트림 평균(양끝 10% 제외) | 이상치를 덜고 평균의 성질을 남기고 싶을 때 | 자른 비율 안쪽 극단값에는 둔감하다. 비율은 표준이 없으니 밝힌다 |

판단 순서는 다음과 같다.

1. 건수, 최솟값, p25, p50, p75, 최댓값을 먼저 뽑는다.
2. 평균과 중앙값이 10퍼센트 넘게 다르면(이 글의 기준) 치우침을 의심하고 히스토그램을 그린다.
3. 목적을 고른다. 합계가 필요하면 평균, 보통 건이면 중앙값, 느린 쪽이 문제면 상위 분위수다.

## 평균과 중앙값이 갈릴 때

규칙: 두 값이 크게 갈리면 하나만 고르지 말고 이유를 설명하고 둘 다 적어라.

주문 1,000건과 체류 시간 1,000세션을 가상으로 만들어 계산했다(주문은 보통 주문 970건에 대량 주문 30건을 섞었다).

구간별 개수는 `floor(amount / 10000.0) * 10000` 으로 묶어 `count(*)` 로 센다(PostgreSQL, BigQuery, MySQL 공통). 10만 원 이상은 42건이다. 합계가 필요한 것이 아니면 이렇게 모양부터 본다.

## 지연 시간을 요약할 때

규칙: 지연과 응답 시간은 평균이 아니라 분위수로 보고하고, 건수를 같이 적어라.

p95는 요청의 95퍼센트가 이 값 이하라는 뜻이다. 평균 100밀리초인 서비스에서 요청의 1퍼센트가 5초 걸릴 수 있고, 평균은 그것을 가린다.<Ref n={1} /> 가상 로그 `api_log` 2,000건(4개 시간대, 가정)을 쓴다.

```sql
SELECT count(*) AS n,
  round(avg(latency_ms), 0) AS mean,
  percentile_cont(0.5)
    WITHIN GROUP (ORDER BY latency_ms)
    AS p50,
  percentile_cont(0.95)
    WITHIN GROUP (ORDER BY latency_ms)
    AS p95,
  percentile_cont(0.99)
    WITHIN GROUP (ORDER BY latency_ms)
    AS p99
FROM api_log;
```

| n | mean | p50 | p95 | p99 |
|---|---|---|---|---|
| 2000 | 229 | 116 | 1189.25 | 2195.04 |

평균 229밀리초는 빠른 약 92퍼센트와 600밀리초 이상인 느린 약 8퍼센트의 중간이라 어느 쪽 경험도 대표하지 못한다. 결과는 PostgreSQL 이 아니라 같은 계산(위치 1 + p × (n − 1), 이웃 값 선형 보간)을 SQLite 와 파이썬으로 돌려 검증한 값이다.

### 분위수 함수의 방언

| 하려는 일 | PostgreSQL | BigQuery | MySQL |
|---|---|---|---|
| 연속 분위수 | `percentile_cont(0.95) WITHIN GROUP (ORDER BY x)`, 집계 함수, NULL 무시<Ref n={2} /> | `PERCENTILE_CONT(x, 0.95) OVER ()`, OVER 가 필요한 윈도 함수<Ref n={3} /> | 내장 함수 없음(8.4 집계 함수 목록에 없다)<Ref n={4} /> |
| 근사 분위수 | 확인 필요 | `APPROX_QUANTILES(x, 100)[OFFSET(95)]`, 근사값<Ref n={5} /> | 확인 필요 |
| 최빈값 | `mode() WITHIN GROUP (ORDER BY x)`<Ref n={2} /> | 집계 함수 목록에 없다. GROUP BY 와 COUNT 로 구한다 | 함수 없음. GROUP BY 와 COUNT 로 구한다<Ref n={4} /> |
| 표본 표준편차 | `stddev_samp`, `stddev` 도 같다<Ref n={2} /> | `STDDEV_SAMP`, `STDDEV` 는 별칭<Ref n={6} /> | `STDDEV_SAMP`. `STDDEV` 는 모집단 `STDDEV_POP` 이다<Ref n={4} /> |

### 분위수를 평균 내거나 합치지 마라

시간대별 p95를 평균 내면 전체 p95가 아니다. `hourly_stats` 는 시간대(03, 09, 12, 20시), 요청 수(200, 300, 1,000, 500), p95(191, 269, 1,634, 963)를 담은 가상 요약 테이블이다.

```sql
-- 나쁜 쿼리: 시간대 p95 의 평균
SELECT round(avg(p95_ms)) AS avg_p95
FROM hourly_stats;
```

| avg_p95 |
|---|
| 764 |

고친 쿼리는 원자료에 위 `percentile_cont(0.95)` 를 쓰는 것이다. 결과는 1189.25다. 요청 수로 가중해도 1,117로 틀린다. 분위수는 평균·합이 성립하지 않으니 원자료에서 다시 구하거나, 구간별 건수(히스토그램)를 합친 뒤 구해라.<Ref n={1} />

### 분위수가 믿을 만한 표본 크기

가상 모집단(p99 2,274)에서 300번 뽑아 5–95퍼센트 범위를 보면, 100건 표본의 p99는 1,336–2,434로 흔들렸고 1,000건은 2,121–2,368(오차 약 7퍼센트 이내)이었다. p50은 100건에서도 106–122였다. p99는 1,000건 이상일 때 쓰고 건수를 병기해라(이 가상 분포 기준이며 일반 표준이 아니다).

## 퍼짐을 요약할 때

규칙: 대칭이면 표준편차, 치우쳤으면 IQR, 단위가 다른 둘을 비교하면 변동계수를 써라.

| 지표 | 쓰는 때 | 주의 |
|---|---|---|
| 표준편차 | 대칭 분포에서 평균과 짝으로 | 이상치에 민감하다. 치우친 값에 평균 ± SD 는 모양을 못 그린다 |
| IQR(Q3 − Q1) | 치우친 분포, 이상치가 있을 때. 중앙값과 짝으로 | 가운데 50퍼센트의 폭이다 |
| 변동계수(SD ÷ 평균) | 단위·규모가 다른 두 지표의 상대적 퍼짐 비교 | 평균이 0 근처거나 음수가 가능하면 쓰지 마라. 꼬리가 길면 부풀려진다 |

주문 금액은 SD 147,144원, IQR 22,575원이다. 평균 58,560 ± 147,144 는 하한이 음수로 내려가는데 금액은 음수가 없다. 변동계수는 주문 금액 2.51, 체류 시간 1.29로 단위가 달라도 주문 금액이 상대적으로 더 흩어져 있다.

### 표준편차와 표준오차를 구분할 때

규칙: 개별 값의 퍼짐은 SD, 평균이 얼마나 믿을 만한지는 SE = SD ÷ √n 이다. n이 커지면 SE만 준다.<Ref n={7} />

<Figure caption="표본이 커져도 SD는 거의 그대로이고 SE만 줄어든다. 가상 체류 시간에서 앞 n개를 뽑아 계산했다.">
  <SdSe />
</Figure>

같은 데이터에서 크기 n짜리 표본을 2,000번 되뽑아 잰 평균의 SD는 n=100에서 8.78, n=1,000에서 2.85로 SE(10.67, 2.81)와 같은 수준이다. n=25처럼 작으면 표본 SD 자체가 흔들려 공식과 벌어진다(17.06 대 21.64).

```sql
SELECT count(*) AS n,
  avg(dwell_sec) AS mean,
  stddev_samp(dwell_sec) AS sd,
  stddev_samp(dwell_sec)
    / sqrt(count(*)) AS se
FROM sessions;
```

| n | mean | sd | se |
|---|---|---|---|
| 1000 | 68.92 | 88.88 | 2.81 |

결과는 반올림해 적었다. 쓰임은 다음과 같다.

- 데이터의 퍼짐을 설명할 때는 SD나 IQR, 평균을 비교하거나 신뢰구간을 만들 때는 SE를 쓴다(d09).
- 오차막대에는 SD인지 SE인지 적어라. SE 막대를 "데이터가 이 안에 있다"로 읽게 두지 마라.
- 같은 사용자의 세션처럼 묶인 관측은 SE 공식이 작게 나온다. 독립 관측일 때만 맞다.

## 박스플롯을 읽을 때

규칙: 상자는 가운데 50퍼센트, 점은 울타리 밖 값이며 점이 곧 오류는 아니다.

박스플롯의 수염은 울타리 안에서 가장 먼 값까지 그린다. 울타리는 Q1 − 1.5×IQR 와 Q3 + 1.5×IQR 이고, 3×IQR 밖은 따로 구분하기도 한다.<Ref n={8} /> 1.5는 관행 값이다.

## 치우친 분포를 로그로 볼 때

규칙: 양수이고 오른쪽 꼬리가 길고 "몇 배"가 의미 있는 값은 로그를 취해서 모양을 본다. 보고는 원래 단위로 되돌린다.

| 0 이하 값이 있다 | 0의 뜻을 먼저 확인한다. 0이 의미 있으면 log(1 + x)를 쓰거나 쓰지 않는다 |
| 최댓값이 중앙값의 10배 이상 | 로그 후보(이 글의 기준, 표준 아님). 체류 시간은 17.5배 |
| 로그 후 히스토그램이 좌우 대칭에 가깝다 | 로그 척도가 맞다 |

## 평균을 합치거나 가중할 때

규칙: 묶음별 평균이나 비율을 다시 평균 내지 마라. 분모를 가중치로 쓴 가중평균이나 합계의 비율을 써라.

가중평균은 합(가중치 × 값) ÷ 합(가중치)이다. 가상 채널 3개를 보자.

| 채널 | 방문 | 구매 | 전환율 |
|---|---|---|---|
| 뉴스레터 | 200 | 30 | 15.0% |
| 검색광고 | 8,000 | 240 | 3.0% |
| 소셜 | 1,800 | 18 | 1.0% |

```sql
-- 나쁜 쿼리: 비율의 평균
SELECT round(
  avg(1.0 * buyers / visits), 4)
  AS bad_rate
FROM channel_stats;
```

| bad_rate |
|---|
| 0.0633 |

```sql
-- 고친 쿼리: 합계의 비율
SELECT round(1.0 * sum(buyers)
  / sum(visits), 4) AS rate
FROM channel_stats;
```

| rate |
|---|
| 0.0288 |

6.33퍼센트는 방문이 200건뿐인 채널과 8,000건인 채널을 똑같이 센 값이다. 전체 전환율 2.88퍼센트는 방문 수로 가중한 평균과 같다. 평균의 평균도 같은 함정이다. 가상 예로 신규 28,000원(600건), 재구매 41,000원(300건), 기업 210,000원(10건)의 평균을 그냥 평균하면 93,000원이고, 건수로 가중하면 34,286원이다.

## 숫자를 표기할 때

규칙: 숫자는 믿을 수 있는 자리까지만 적고, 단위와 표본 크기를 붙이고, 반올림은 마지막에 한 번만 해라.

| 규칙 | 나쁜 예 | 고친 예 |
|---|---|---|
| 흔들림(SE)이 가리키는 자리까지 | 평균 58,559.6원 (SE 약 4,650원) | 약 5.9만 원 (SE 약 0.5만 원, n=1,000) |
| 단위와 건수 병기 | p95 1189 | p95 1,189 ms (n=2,000) |
| 비율은 분자와 분모 병기 | 전환율 3% | 전환율 3.0% (240 / 8,000) |
| 반올림은 마지막에 | 전환율 2.46%를 2.5%로 적고 4만 방문에 곱해 1,000건 | 반올림 전 값으로 계산해 984건을 적는다 |

## 나쁜 예와 고친 예

| 나쁜 예 | 고친 예 | 이유 |
|---|---|---|
| 평균 응답 229ms 로 보고 | p50 116, p95 1,189, p99 2,195 ms (n=2,000) | 느린 8퍼센트가 가려진다 |
| 평균 58,560 ± 147,144원 | 중앙값 29,500원, IQR 22,575원 | 치우친 값에서 SD는 모양을 못 그린다 |
| 막대 위 오차막대 ± 값 (설명 없음) | "평균 ± SE" 또는 "평균, SD" 로 표시 | SD와 SE는 의미가 다르다 |

<Callout kind="warn">
데이터는 모두 가상이다. 트림 10퍼센트, 로그 10배, 표본 크기 기준은 이 글의 선택이며 표준이 아니다.
</Callout>

## 증상으로 찾기

| 증상 | 원인 | 처방 |
|---|---|---|
| 평균은 정상인데 불만이 많다 | 느린 꼬리가 평균에 묻힌다 | p95, p99 를 같이 보고하고 히스토그램을 그린다 |
| 평균이 중앙값보다 훨씬 크다 | 오른쪽 꼬리나 대량 건 | 중앙값과 분위수로 보고하고 평균은 합계에만 쓴다 |
| p99 가 날마다 크게 변한다 | 표본이 작다 | 건수를 병기하고 기간을 늘리거나 p95 를 쓴다 |
| 평균 p95 가 전체 p95 와 다르다 | 분위수를 평균했다 | 원자료나 구간별 건수에서 다시 구한다 |
| 전체 전환율이 채널 평균과 다르다 | 비율의 평균을 썼다 | 합계의 비율이나 가중평균을 쓴다 |
| 박스플롯에 점이 줄줄이 있다 | 치우친 분포다 | 로그 변환을 검토하고 값의 출처를 확인한다 |
| MySQL 표준편차가 낮게 나온다 | `STDDEV` 가 모집단 SD 다 | `STDDEV_SAMP` 를 쓴다 |

## 점검 체크리스트

- 요약값을 내기 전에 히스토그램이나 p25, p50, p75 표를 확인했는가.
- 지연은 p50, p95, p99 와 건수를 함께 적었는가.
- 분위수를 평균 내거나 더하지 않았는가.
- 비율은 합계의 비율이나 가중평균인가.
- SD, IQR, SE 중 무엇인지 표기했는가.
- 박스플롯의 점을 오류로 단정하지 않고 값의 출처를 확인했는가.
- 숫자에 단위, 표본 크기, 반올림 시점이 맞는가.
