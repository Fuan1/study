<Overview>

- 해라: 사용자 단위로 먼저 줄인 뒤 세라. 퍼널·리텐션·DAU 는 행 수가 아니라 고유 사용자 수다.
- 해라: 퍼널은 단계 순서와 전환 기간을 쿼리에 명시해라. 조건 없이 단계별 고유 사용자만 세면 뒷 단계가 부풀려진다.
- 하지 마라: 아직 관측하지 못한 리텐션 칸을 0%로 읽기. 코호트 날짜 + N일이 마지막 관측일을 넘으면 빈칸이다.
- 기준값: 세션 간격 30분은 GA4·Amplitude 웹의 기본값이지 표준이 아니다. 우리 정의로 문서에 고정해라.
- 해라: 느리면 읽는 양부터 줄이고(필요한 컬럼, 기간 필터, 조인 전 행) EXPLAIN 으로 확인해라. 인덱스 컬럼에 함수를 씌우지 마라.

</Overview>

## 퍼널을 계산할 때

규칙: 사용자별로 단계 시각을 구하고, 단계 순서와 전환 기간을 조건으로 건다.

| 항목 | 규칙 | 안 지키면 |
|---|---|---|
| 세는 단위 | 단계마다 `COUNT(DISTINCT user_id)` | 반복 조회가 단계를 부풀린다 |
| 단계 순서 | 다음 단계 시각이 직전 단계 이후 | 장바구니를 먼저 담은 사람도 전환이 된다 |
| 전환 기간 | 첫 단계부터 N일 안(예제 1일) | 몇 주 뒤 구매도 전환이 된다 |

나쁜 쿼리는 순서와 기간이 없다.

```sql
-- bad: no order, no window
SELECT event,
       COUNT(DISTINCT user_id) AS u
FROM events
WHERE event IN ('view', 'cart',
                'purchase')
  AND ts >= '2025-01-25'
  AND ts < '2025-02-01'
GROUP BY event;
```

고친 쿼리는 단계마다 이전 단계 사용자에게 다음 이벤트를 붙인다.

```sql
WITH v AS (
  SELECT user_id, MIN(ts) AS t1
  FROM events
  WHERE event = 'view'
    AND ts >= '2025-01-25'
    AND ts < '2025-02-01'
  GROUP BY user_id),
c AS (
  SELECT v.user_id, v.t1,
         MIN(e.ts) AS t2
  FROM v JOIN events e USING (user_id)
  WHERE e.event = 'cart'
    AND e.ts >= v.t1
    AND e.ts < v.t1 + INTERVAL '1 day'
  GROUP BY v.user_id, v.t1),
p AS (
  SELECT c.user_id, MIN(e.ts) AS t3
  FROM c JOIN events e USING (user_id)
  WHERE e.event = 'purchase'
    AND e.ts >= c.t2
    AND e.ts < c.t1 + INTERVAL '1 day'
  GROUP BY c.user_id),
f AS (
  SELECT 1 AS n, 'view' AS step,
         COUNT(*) AS users FROM v
  UNION ALL
  SELECT 2, 'cart', COUNT(*) FROM c
  UNION ALL
  SELECT 3, 'purchase', COUNT(*) FROM p)
SELECT step, users,
  ROUND(100.0 * users
    / LAG(users) OVER w, 1) AS step_pct,
  ROUND(100.0 * users
    / FIRST_VALUE(users) OVER w, 1)
    AS total_pct
FROM f
WINDOW w AS (ORDER BY n)
ORDER BY n;
```

| step | users | step_pct | total_pct |
|---|---|---|---|
| view | 130 | | 100.0 |
| cart | 64 | 49.2 | 49.2 |
| purchase | 30 | 46.9 | 23.1 |

같은 기간을 세는 방법별로 비교하면 다음과 같다.

| 세는 방법 | view | cart | purchase |
|---|---|---|---|
| 행 수 `COUNT(*)` | 499 | 118 | 54 |
| 나쁜 쿼리(순서·기간 없음) | 130 | 81 | 45 |
| 고친 쿼리(순서·1일) | 130 | 64 | 30 |

<Figure caption="조건 없이 고유 사용자만 세면 cart 는 81, purchase 는 45로 나온다. 순서와 1일 조건을 걸면 64, 30이다. 가정 데이터의 쿼리 결과다.">

<Callout kind="warn">
기간 끝에 첫 단계를 한 사용자는 전환 기간을 다 채우지 못했다. 마지막 N일은 빼라. 위 쿼리는 중간에 다른 이벤트가 끼어도 순서만 맞으면 전환으로 세는 느슨한 정의다. 허용 여부를 지표 정의서에 적어라.
</Callout>

## 리텐션을 계산할 때

규칙: 가입일 코호트를 만들고, 달력 날짜 차이 N일에 활동했는지 센다. 분모는 코호트 가입자 수다. PostgreSQL 에서 date 끼리 빼면 일수 정수가 나온다.<Ref n={1} />

```sql
WITH f AS (
  SELECT user_id,
         MIN(DATE(ts)) AS cohort
  FROM events
  WHERE event = 'signup'
  GROUP BY user_id),
a AS (
  SELECT DISTINCT e.user_id,
         DATE(e.ts) - f.cohort AS n
  FROM events e JOIN f USING (user_id)
  WHERE e.event <> 'signup')
SELECT f.cohort,
  COUNT(DISTINCT f.user_id) AS size,
  COUNT(DISTINCT CASE WHEN n = 1
        THEN a.user_id END) AS d1,
  COUNT(DISTINCT CASE WHEN n = 2
        THEN a.user_id END) AS d2,
  COUNT(DISTINCT CASE WHEN n = 3
        THEN a.user_id END) AS d3,
  COUNT(DISTINCT CASE WHEN n = 4
        THEN a.user_id END) AS d4,
  COUNT(DISTINCT CASE WHEN n = 5
        THEN a.user_id END) AS d5,
  COUNT(DISTINCT CASE WHEN n = 6
        THEN a.user_id END) AS d6
FROM f LEFT JOIN a USING (user_id)
WHERE f.cohort >= DATE '2025-01-25'
GROUP BY f.cohort
ORDER BY f.cohort;
```

```text
cohort      size d1 d2 d3 d4 d5 d6
2025-01-25    15  7  7  8  7  2  2
2025-01-26    16  9  7  5  3  5  0
2025-01-27    14  6  5  5  6  0  0
2025-01-28    14  7  5  9  0  0  0
2025-01-29    15  6  5  0  0  0  0
2025-01-30    16  6  0  0  0  0  0
2025-01-31    13  0  0  0  0  0  0
```

비율은 `dN / size` 다. 마지막 관측일이 1/31 이므로 코호트 날짜 + N 이 1/31 을 넘는 칸의 0 은 "0명"이 아니라 "아직 못 봄"이다.

<Figure caption="결과표를 가입자 수로 나눠 그렸다. 점선 칸은 관측 전이라 비어 있다. 이 칸을 0%로 평균 내면 최근 코호트가 나빠 보인다.">
  <RetentionHeat />
</Figure>

리텐션 정의는 셋이 흔하다. 이름은 이 글에서 붙인 것이고 도구마다 다르다. 위 `f`, `a` 를 두고 마지막 SELECT 의 조건만 바꾼 결과다.

| 정의 | 뜻 | 조건 | 1/25 코호트 15명 |
|---|---|---|---|
| N일 리텐션 | 정확히 N일째 활동 | `n = 3` | 8명, 53.3% |
| 구간 리텐션 | 1일부터 N일 사이 한 번이라도 활동 | `n BETWEEN 1 AND 3` | 13명, 86.7% |
| N일 이후 리텐션 | N일째 이후 한 번이라도 활동 | `n >= 3` | 11명, 73.3% |

같은 데이터에서 53%와 87%가 나온다. 어느 정의인지 정의서에 적고 같은 정의끼리만 비교해라.

- 가입 이벤트는 활동에서 뺀다. 넣으면 D0 가 의미 없이 100%다.
- 날짜는 달력 날짜다. 23시 가입자는 1시간 뒤 자정이 D1 이다.

## DAU·WAU·MAU 와 stickiness 를 낼 때

규칙: 활성 정의를 고정하고, (사용자, 날짜) 중복을 제거한 뒤 기간만 바꿔 센다. stickiness 는 특정일 DAU 가 아니라 일평균 DAU 를 MAU 로 나눈다.

```sql
WITH da AS (
  SELECT DISTINCT user_id,
         DATE(ts) AS d
  FROM events
  WHERE event <> 'signup'
    AND ts >= '2025-01-02'
    AND ts < '2025-02-01')
SELECT
  COUNT(DISTINCT CASE
        WHEN d = DATE '2025-01-31'
        THEN user_id END) AS dau,
  COUNT(DISTINCT CASE
        WHEN d >= DATE '2025-01-25'
        THEN user_id END) AS wau,
  COUNT(DISTINCT user_id) AS mau,
  ROUND(COUNT(*) / 30.0, 1) AS avg_dau,
  ROUND(100.0 * COUNT(*) / 30
    / COUNT(DISTINCT user_id), 1)
    AS stickiness_pct
FROM da;
```

| dau | wau | mau | avg_dau | stickiness_pct |
|---|---|---|---|---|
| 58 | 146 | 174 | 18.9 | 10.9 |

`da` 의 행 수를 30으로 나누면 일평균 DAU 다. 1/31 하루의 58로 나누면 33.3%가 되어 같은 서비스가 세 배로 보인다.

| 함정 | 증상 | 처방 |
|---|---|---|
| 활성 정의 | 같은 기간 MAU 가 176(가입 포함), 174(가입 제외), 79(구매만) | 정의를 고정하고 가입만 한 사람은 뺀다 |
| 기간 겹침 | 7일 구간 4개의 합 274, 28일 고유 174 | 고유 수는 더하지 않는다. 전체 기간으로 한 번에 센다 |
| 시간대 | UTC 로 자르면 한국 자정 전후 활동이 다른 날이 된다 | 자르기 전에 기준 시간대로 변환한다(문법은 확인 필요) |

<Figure caption="7일 고유 사용자 4구간(33, 42, 53, 146)의 합은 274로, 같은 28일 고유 사용자 174보다 100 크다. 겹친 사람이 여러 번 세어졌다. 가정 데이터.">

## 세션을 나눌 때

규칙: 같은 사용자의 직전 이벤트와 간격이 기준을 넘으면 새 세션이다. `LAG` 로 새 세션 표시(1 또는 0)를 만들고 누적합으로 번호를 붙인다.

| 도구 | 기본 세션 간격 | 비고 |
|---|---|---|
| GA4 | 30분 | 비활동 기준, 변경 가능<Ref n={2} /> |
| Amplitude 웹 SDK | 30분 | 브라우저 SDK 설정으로 변경<Ref n={3} /> |
| Amplitude 모바일 SDK | 5분 | 값을 바꾸는 메서드가 있다<Ref n={3} /> |

다른 도구는 확인 필요. 30분은 표준이 아니라 관행이다. 도구 숫자와 비교하기 전에 같은 기준인지 본다.

```sql
WITH g AS (
  SELECT user_id, event, ts,
    CASE
      WHEN LAG(ts) OVER w IS NULL
        OR ts - LAG(ts) OVER w
           > INTERVAL '30 minutes'
      THEN 1 ELSE 0
    END AS new_s
  FROM events
  WHERE user_id = 176
  WINDOW w AS (PARTITION BY user_id
               ORDER BY ts))
SELECT ts, event,
  SUM(new_s) OVER (
    PARTITION BY user_id
    ORDER BY ts
    ROWS UNBOUNDED PRECEDING
  ) AS session_no
FROM g
ORDER BY ts;
```

```text
ts                  event    session_no
2025-01-20 08:50:00 signup            1
2025-01-20 08:51:10 open              1
2025-01-20 08:58:30 view              1
2025-01-20 09:14:00 view              1
2025-01-20 09:44:00 cart              1
2025-01-20 10:15:30 view              2
2025-01-20 10:20:00 purchase          2
2025-01-20 14:02:00 open              3
2025-01-20 14:09:40 view              3
```

<Figure caption="간격이 30분을 넘는 곳(31분 30초, 3시간 42분)에서 세션이 나뉜다. 정확히 30분인 09:44 는 같은 세션이다. 가정한 한 사용자의 하루.">

- 경계는 초과만 새 세션이다. 첫 이벤트는 `LAG` 가 NULL 이라 별도 조건이다.
- 누적합에는 프레임을 명시해라. 기본 프레임은 같은 정렬 값의 행을 한 묶음으로 본다.<Ref n={4} /> 같은 `ts` 가 있으면 `ORDER BY` 에 보조 키를 더해라.

## 전기 대비 증감과 이동평균을 낼 때

규칙: 일별로 집계한 뒤 달력 테이블에 `LEFT JOIN` 해서 빠진 날을 0 으로 채우고, 그다음에 `LAG` 와 이동평균을 쓴다. 이벤트 없는 날은 행이 없기 때문이다.

```sql
WITH cal AS (
  SELECT CAST(g.day AS DATE) AS day
  FROM generate_series(
    TIMESTAMP '2025-01-20',
    TIMESTAMP '2025-01-31',
    INTERVAL '1 day') AS g(day)),
d AS (
  SELECT DATE(ts) AS day,
         COUNT(*) AS buys
  FROM events
  WHERE event = 'purchase'
    AND ts >= '2025-01-20'
  GROUP BY DATE(ts)),
x AS (
  SELECT cal.day,
         COALESCE(d.buys, 0) AS buys
  FROM cal LEFT JOIN d USING (day))
SELECT day, buys,
  buys - LAG(buys) OVER w AS diff,
  ROUND(AVG(buys) OVER (
    ORDER BY day
    ROWS BETWEEN 6 PRECEDING
             AND CURRENT ROW), 1) AS ma7
FROM x
WINDOW w AS (ORDER BY day)
ORDER BY day DESC
LIMIT 6;
```

| day | buys | diff | ma7 |
|---|---|---|---|
| 2025-01-31 | 8 | 1 | 7.7 |
| 2025-01-30 | 7 | -4 | 7.0 |
| 2025-01-29 | 11 | -2 | 6.0 |
| 2025-01-28 | 13 | 13 | 4.7 |
| 2025-01-27 | 0 | -9 | 3.3 |
| 2025-01-26 | 9 | 3 | 3.7 |

`cal` 과 `x` 없이 `d` 만 쓰면 1/27 행이 없다. 그러면 1/28 증감이 +13 이 아니라 +4(1/26 과 비교)가 되고, `ROWS 6 PRECEDING` 은 7일이 아니라 7행이라 1/31 의 `ma7` 이 7.7 이 아니라 8.1 이 된다. 달력은 `generate_series`<Ref n={1} /> 로 만든다.

- 증감률의 분모가 0 이면 `NULLIF(prev, 0)` 으로 NULL 처리한다. 이동평균의 처음 6행은 창이 덜 찼으니 제외해라.

### 상위 N 과 누적 기여도

규칙: 비율의 분모는 자르기 전의 전체 합이다. `LIMIT` 은 윈도우 계산 뒤에 적용된다. `sales(item, amount)` 는 가정한 품목별 판매 24행이다.

```sql
WITH t AS (
  SELECT item, SUM(amount) AS amt
  FROM sales
  GROUP BY item)
SELECT item, amt,
  ROUND(100.0 * amt
    / SUM(amt) OVER (), 1) AS share,
  ROUND(100.0 * SUM(amt) OVER (
    ORDER BY amt DESC, item
    ROWS UNBOUNDED PRECEDING)
    / SUM(amt) OVER (), 1) AS cum_pct
FROM t
ORDER BY amt DESC, item
LIMIT 5;
```

| item | amt | share | cum_pct |
|---|---|---|---|
| cable | 1180 | 28.3 | 28.3 |
| charger | 910 | 21.8 | 50.1 |
| case | 760 | 18.2 | 68.3 |
| earbuds | 420 | 10.1 | 78.4 |
| stand | 330 | 7.9 | 86.3 |

- 상위 5개를 서브쿼리에서 먼저 자르고 윈도우를 돌리면 분모가 5개의 합이 되어 5번째 누적이 100.0 이 된다(위 데이터로 확인).
- 합계가 같은 행이 있으면 `ORDER BY` 에 보조 키를 둔다. 누적 80%에서 끊는 기준은 관행이며 맥락에 따라 정한다.

## 방언이 갈릴 때

| 용도 | PostgreSQL | BigQuery | MySQL 8.0 |
|---|---|---|---|
| 일수 차이 | `d1 - d2` | `DATE_DIFF(d1, d2, DAY)` | `DATEDIFF(d1, d2)` |
| 초 차이 (a 에서 b 를 뺌) | `EXTRACT(EPOCH FROM a - b)` | `TIMESTAMP_DIFF(a, b, SECOND)` | `TIMESTAMPDIFF(SECOND, b, a)` |
| 주 시작 | `DATE_TRUNC('week', ts)` 월요일 | `DATE_TRUNC(d, WEEK)` 일요일, `WEEK(MONDAY)` 로 변경 | `DATE_SUB(d, INTERVAL WEEKDAY(d) DAY)` 월요일, 확인 필요 |
| 날짜 목록 | `generate_series` | `UNNEST(GENERATE_DATE_ARRAY(a, b))` | `WITH RECURSIVE` |

출처: PostgreSQL<Ref n={1} />, BigQuery<Ref n={5} />, MySQL<Ref n={6} />. BigQuery 의 차이 함수는 정수 단위로 자른다. 분 단위로 쓰면 30분 20초가 30분이 되므로 세션 간격은 초로 비교해라.

## 쿼리가 느릴 때

규칙: 읽는 양을 줄이는 순서로 고치고, 고친 뒤 실행 계획으로 확인한다.

| 순서 | 확인 | 고치는 법 |
|---|---|---|
| 1 | 읽는 컬럼 | `SELECT *` 를 빼고 필요한 컬럼만 쓴다 |
| 2 | 날짜·파티션 필터 | 가장 안쪽(첫 CTE)에 기간 조건을 건다. 끝은 반열린 구간 |
| 3 | 조인 전 행 수 | 사용자·일 단위로 먼저 집계하거나 중복을 제거한다 |
| 4 | 같은 계산 반복 | CTE 로 한 번 계산해 재사용한다. PostgreSQL 은 한 번만 참조하는 CTE 를 본 쿼리에 합치고, 여러 번 참조하면 먼저 계산해 둔다<Ref n={7} /> |
| 5 | 실행 계획 | `EXPLAIN` 으로 큰 노드를 찾는다 |

### EXPLAIN 읽는 법

PostgreSQL 의 `EXPLAIN` 은 계획의 추정치를 보여 주고, `EXPLAIN ANALYZE` 는 실제로 실행해 실측값을 더한다.<Ref n={8} />

| 볼 곳 | 의미 | 판단 |
|---|---|---|
| 노드 이름 | Seq Scan 은 테이블 전체, Index Scan 과 Bitmap Heap Scan 은 인덱스로 위치를 찾는다 | 일부만 필요한 큰 테이블에서 Seq Scan 이면 인덱스를 못 탔다 |
| 추정 `rows` 와 `actual rows` | 예상 행 수와 실제 행 수 | 크게 다르면 통계가 낡았다. `ANALYZE` 로 갱신한다 |
| Rows Removed by Filter | WHERE 가 버린 행 수 | 많이 버리면 조건이 인덱스를 못 쓰는 중이다 |
| `loops`, Execution Time | 노드 실행 횟수, 전체 시간 | 안쪽 노드의 loops 가 크면 반복 실행 중이다 |

<Callout kind="warn">
`EXPLAIN ANALYZE` 는 문장을 실제로 실행한다. INSERT, UPDATE, DELETE 는 `BEGIN` 과 `ROLLBACK` 으로 감싸라.
</Callout>

### 인덱스를 못 타는 패턴

| 패턴 | 나쁜 예 | 고친 예 | 이유 |
|---|---|---|---|
| 컬럼에 함수 | `WHERE DATE(ts) = '2025-01-20'` | `WHERE ts >= '2025-01-20' AND ts < '2025-01-21'` | 인덱스는 `ts` 값 기준이라 함수 결과로 찾지 못한다. 같은 식의 인덱스를 만들 수 있으나 갱신 비용이 든다<Ref n={9} /> |
| 앞쪽 와일드카드 | `WHERE event LIKE '%art'` | `WHERE event LIKE 'car%'` 또는 `= 'cart'` | B-tree 는 패턴이 앞에 고정된 상수일 때만 쓴다. C 로케일이 아니면 패턴용 연산자 클래스가 필요하다<Ref n={10} /> |
| 암묵적 형 변환 (MySQL 예) | `WHERE str_col = 1` | `WHERE str_col = '1'` | 문자열 컬럼을 숫자와 비교하면 인덱스를 못 쓴다<Ref n={11} /> |

함수 쿼리와 범위 쿼리는 예제에서 같은 행 수 53(1/20 하루)을 돌려준다. `ts` 에 인덱스를 만든 SQLite 의 계획은 함수 쪽이 `SCAN`, 범위 쪽이 `SEARCH ... USING INDEX` 였다. PostgreSQL 의 Seq Scan 과 Index Scan 차이는 직접 확인하지 않았다. 비교는 컬럼과 같은 타입의 값으로 하고 조인 키 타입도 맞춰라.

### 스캔량으로 과금되는 환경

BigQuery 온디맨드에서는 읽은 데이터량이 비용이다.<Ref n={12} />

- 실행 전에 검증기나 dry run 으로 추정 바이트를 확인해라.
- `SELECT *` 를 쓰지 마라. 클러스터링하지 않은 테이블에서 `LIMIT` 은 비용을 줄이지 못한다.
- 파티션 컬럼에 필터를 걸면 해당 파티션만 읽는다.<Ref n={13} /> `require_partition_filter` 로 필터 없는 쿼리를 막고, 최대 청구 바이트로 상한을 둬라.
- 데이터를 볼 때는 쿼리 대신 테이블 미리보기를 쓴다. 비용이 들지 않는다.

## 결과를 검증할 때

규칙: 숫자를 내기 전에 합계를 대조하고, 몇 명은 원본 이벤트까지 내려가 눈으로 맞춘다.

| 대조 | 기준 |
|---|---|
| 퍼널 | 첫 단계가 같은 기간 view 고유 사용자 수와 같다(130). 뒤로 갈수록 같거나 작다 |
| 코호트 | `size` 합이 같은 기간 가입자 수와 같다(1/25부터 1/31까지 103명) |
| 활성 | DAU 는 WAU 이하, WAU 는 MAU 이하(58, 146, 174) |
| 세션과 이동평균 | 세션 번호가 붙은 행 수가 원본과 같고, 달력 행 수가 일수와 같다(12일) |
| 누적 기여도 | 전체를 다 보면 마지막이 100.0 이다 |
| 샘플 | 사용자 두세 명의 원본 이벤트를 시간순으로 펼쳐 결과와 손으로 맞춘다 |

## 증상으로 찾기

| 증상 | 원인 | 처방 |
|---|---|---|
| 퍼널 뒷 단계가 높게 나온다 | 행 수로 셌거나 순서·기간 조건이 없다 | 사용자별 첫 시각과 순서·기간 조건 |
| 최근 코호트 리텐션이 0%다 | 관측 전 칸을 0 으로 읽었다 | 코호트 날짜 + N 이 마지막 관측일을 넘으면 빈칸 |
| MAU 가 도구 숫자와 다르다 | 활성 정의, 기간, 시간대가 다르다 | 정의서 기준으로 맞춘다 |
| 증감이나 이동평균이 튄다 | 빠진 날의 행이 없다 | 달력 테이블에 `LEFT JOIN`, 0 으로 채움 |
| 쿼리가 갑자기 느려졌다 | 데이터가 늘었고 조건이 인덱스를 못 탄다 | `EXPLAIN` 에서 Seq Scan, 함수·앞 와일드카드·형 변환을 고친다 |
| BigQuery 비용이 크다 | 파티션 필터 없음, `SELECT *` | dry run 으로 바이트를 확인하고 줄인다 |

## 점검 체크리스트

- 퍼널 쿼리에 단계 순서, 전환 기간, 날짜 범위가 모두 있다.
- 리텐션 정의와 분모, 활성 정의, 시간대, 세션 간격이 정의서와 같다.
- 관측 전 칸이 0 이 아니라 빈칸이다.
- 증감과 이동평균 앞에 달력 조인이 있다. 기간 조건이 첫 CTE 에 있고 `SELECT *` 가 없다.
- 느린 쿼리는 `EXPLAIN` 으로 고치기 전후를 비교했다.
- 합계 대조를 했고 사용자 몇 명은 원본 이벤트로 맞췄다.
