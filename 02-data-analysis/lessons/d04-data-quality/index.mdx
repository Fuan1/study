## 점검이 무엇을 내놓는지 볼 때

규칙: 점검은 기준을 먼저 정하고 그 기준에 데이터를 대 보는 일이다. 중요한 항목부터 고르고, 볼 차원과 좋고 나쁜 범위를 정한 뒤 적용하고, 결과를 검토해 고치고, 주기적으로 반복한다.<Ref n={1} />

| 질문 | 필요한 데이터 | 분석 | 결과물 | 결정에 쓰는 법 |

| 이 데이터를 써도 되나 | 원본, 출처·기간·단위 설명 | 설명서와 행 수·기간 대조 | 점검표 | 통과, 조건부 통과, 보류 |
| 값이 빠졌나 | 항목별 채워진 칸 | 빈 비율과 몰린 곳 확인 | 이슈 로그, 결정 기록 | 그대로, 제외, 대체 중 선택 |
| 같은 것이 두 번 세어졌나 | 행의 키, 원천 건수 | 행 수와 실제 대상 수 비교 | 이슈 로그 | 겹친 행 정리, 원천 수정 요청 |

## 품질을 어떤 기준으로 볼지 정할 때

규칙: 품질은 6개 차원으로 나눠 묻고, 차원마다 비율이나 시간 차 같은 수치 하나로 적는다.<Ref n={1} /> 아래 계산 예는 DAMA UK 문서가 든 가상의 학교 사례다.

| 차원 | 점검 질문 | 재는 법 |
|---|---|---|
| 완전성 | 채워져야 할 값이 다 있나 | 채워진 수 나누기 채워져야 할 수. 연락처 300칸 중 294칸이면 98퍼센트 |
| 유일성 | 같은 대상이 한 번만 기록됐나 | 실제 대상 수 나누기 기록 수. 500명인데 520건이면 96.2퍼센트 |
| 적시성 | 필요한 시점의 현실을 담았나 | 일어난 시각과 기록된 시각의 차. 약속은 2일인데 3일 걸림 |
| 유효성 | 형식, 종류, 범위를 지키나 | 규칙에 맞는 값의 비율. 나이는 4에서 11이어야 하면 14는 위반 |
| 정확성 | 현실의 값과 같은가 | 현실이나 기준 자료와 대어 맞는 비율 |
| 일관성 | 여러 곳의 같은 값이 같은가 | 저장소 간 값과 형식의 차이 |

정확성만은 데이터 안에서 확인할 수 없다. 현실의 대상이나 권위 있는 기준 자료와 대야 한다.<Ref n={1} /> 다른 차원은 데이터와 정의서만으로 잰다. 차원마다 중요도가 다르므로 어느 차원을 얼마나 엄격히 볼지는 쓰임에 맞춰 정한다.

ISO/IEC 25012는 특성을 15개 두며, 위와 겹치는 정확성, 완전성, 일관성에 신뢰성(credibility)과 현재성(currentness, 데이터의 나이가 쓰임에 맞는가)이 들어 있다.<Ref n={2} />

<Callout kind="warn">
여섯 차원을 모두 통과해도 못 쓰는 데이터가 있다. 읽는 사람이 이해하지 못하거나 쓰임에 맞지 않으면 쓸모가 없다.<Ref n={1} /> 정의를 이해할 수 있는지, 쓰임에 맞는지도 묻는다.
</Callout>

## 처음 받은 데이터를 점검할 때

규칙: 순서를 지켜라. 앞 단계가 틀리면 뒤 단계의 결과는 의미가 없다.

| 순서 | 무엇을 보나 | 어긋나면 의심 |
|---|---|---|
| 1 출처·기간·단위 | 누가 언제 어느 시스템에서 뽑았나. 한 행이 무엇인가. 단위, 통화, 시간대 | 다른 버전 파일, 걸러진 추출본 |
| 2 행 수와 기간 | 행 수가 원천 건수와 같나. 첫 날과 끝 날이 맞나. 중간에 빈 날이 있나 | 추출 중단, 잘린 파일 |
| 3 빠짐 | 항목별, 날짜별, 집단별 빈 비율 | 특정 기간의 수집 누락 |
| 4 중복 | 같은 키가 겹치나. 같은 대상이 다른 표기로 있나 | 재전송, 합치기 실수 |
| 5 값 범위 | 허용 범위 밖, 형식 위반, 이상값 후보 | 입력 오류, 단위 혼용 |
| 6 정의 일치 | 같은 이름의 항목이 다른 곳과 같은 뜻인가 | 시스템마다 다른 정의 |

표 모양도 먼저 본다. 변수는 열 하나, 관측은 행 하나, 관측 단위가 다른 정보는 별도 표가 분석하기 좋은 모양이다.<Ref n={3} /> 소득 구간처럼 값이 열 제목에 들어간 표는 모양부터 바꾼 뒤 점검한다. 점검은 한 번으로 끝나지 않는다. 분석 중에 새 문제가 보이면 되돌아와 다시 한다.<Ref n={3} />

## 값이 비어 있을 때

규칙: 지우거나 채우기 전에 빈 칸이 어디에 몰렸는지(기간, 집단, 값의 크기)부터 본다. 빈 이유가 결과를 좌우한다.

| 유형 | 뜻 | 예 |
|---|---|---|
| 완전 무작위(MCAR) | 모든 칸이 빠질 확률이 같다. 빠진 이유가 데이터와 무관하다 | 저울 배터리가 나가 측정이 빠짐 |
| 무작위(MAR) | 이미 아는 항목으로 나눈 집단 안에서는 빠질 확률이 같다 | 부드러운 바닥에서 빠짐이 늘고 바닥 종류를 알고 있음 |
| 비무작위(MNAR) | 둘 다 아니다. 모르는 이유로 빠질 확률이 달라진다 | 의견이 약한 사람이 덜 응답함 |

예시는 van Buuren 교재에서 가져왔다.<Ref n={4} /> MNAR는 다루기 가장 어렵다. 빠진 이유에 관한 자료를 더 모으거나, 가정을 바꿔 가며 결과가 얼마나 흔들리는지 본다.<Ref n={4} />

| 처리 | 결과에 미치는 영향 | 쓸 때 |
|---|---|---|
| 그대로 두기 | 분모가 달라진다. 모르는 값은 따로 표시하고 분모를 적는다 | 현황 요약, 빈 이유 자체가 정보일 때 |
| 제외(행 삭제) | 완전 무작위일 때만 평균, 회귀계수, 상관이 맞다. 아니면 틀어지고, 빠진 비율과 평균 차가 클수록 심하다 | 빠진 행이 적고 무작위라고 볼 근거가 있을 때 |
| 평균으로 대체 | 분산이 작아지고 변수 간 관계가 흐려진다. 공개 예시(대기 오존)에서 표준편차가 33에서 28.7로 줄었다 | 몇 칸을 임시로 메울 때만 |
| 모델로 대체 | 현대적 방법(다중 대체)은 MAR을 출발점으로 삼는다 | 이 글 범위 밖. 분석 담당자에게 맡긴다 |

<Figure caption="행 제외는 평균, 회귀계수, 상관 모두 완전 무작위 결측일 때만 맞다. 불가는 어떤 조건에서도 편향 없음이 보장되지 않는다는 뜻이다. 교재 표를 옮긴 것이다.">
  <MissingGrid />
</Figure>

<Callout kind="warn">
이 정도까지는 지워도 된다는 결측 비율의 안전선은 없다. 영향은 비율만이 아니라 빠진 쪽과 남은 쪽의 평균 차에도 달렸다.<Ref n={4} /> 행을 제외하면 분석마다 남는 표본이 달라지고, 날짜 행을 지우면 시간의 흐름이 끊긴다. 제외한 건수와 이유를 보고서에 적어라.
</Callout>

## 같은 행이 겹쳐 보일 때

규칙: 먼저 한 행이 무엇인지(주문 한 건, 고객 한 명) 정하고, 그 단위에서 같은 대상이 두 번 있는지 본다. 실제 대상 수보다 기록이 많으면 중복이 있다.<Ref n={1} /> 첫 행만 출처가 있는 사례이고 나머지는 흔한 경우를 정리한 것이다.

| 원인 | 증상 | 처방 |
|---|---|---|
| 같은 대상이 다른 표기로 두 번 등록 | 이름이 거의 같은 행이 쌍으로 있다(Fred Smith와 Freddy Smith 사례)<Ref n={1} /> | 식별자로 합치고 병합 규칙을 적는다 |
| 같은 기록이 두 번 들어옴 | 키와 시각이 같은 행 | 원천에 확인하고 키와 시각 기준으로 정리 |
| 겹치는 기간의 파일을 이어 붙임 | 겹친 날의 합계가 두 배 | 기간 경계를 맞춰 다시 합친다 |
| 단위가 다른 표를 합침 | 합친 뒤 행이 원본보다 많다 | 관측 단위별 표로 나눠 둔다<Ref n={3} /> |

같은 값이 정상 반복일 때도 있다(같은 상품 재구매). 주문번호나 시각 같은 키까지 같을 때만 중복으로 보고, 지우기 전에 원천에 묻는다.

## 값이 튀어 보일 때

규칙: 이상값은 지울 값이 아니라 원인을 물을 값이다. 삭제를 생각하기 전에 왜 나왔는지, 비슷한 값이 또 나올지 이해해라.<Ref n={5} />

NIST 핸드북은 이상값을 표본의 나머지에서 비정상적으로 떨어진 관측으로 정의한다. 무엇이 비정상인지는 분석자가 정하므로 먼저 정상 값의 모양을 본다.<Ref n={5} /> 후보를 찾는 기준은 상자그림의 울타리다. 사분위 범위(IQ)는 3사분위수 Q3에서 1사분위수 Q1을 뺀 값이다.

| 울타리 | 계산 | 밖에 있으면 |
|---|---|---|
| 안쪽 | Q1에서 1.5×IQ 아래, Q3에서 1.5×IQ 위 | 약한 이상값 |
| 바깥 | Q1에서 3×IQ 아래, Q3에서 3×IQ 위 | 극단 이상값 |

<Figure caption="NIST 예시 자료 90개로 계산했다. 1441 하나만 안쪽 울타리를 넘는 약한 이상값이다. 울타리는 후보를 찾는 기준이다.">
  <OutlierFences />
</Figure>

정규분포를 가정하는 검정(Grubbs)도 있다.<Ref n={5} /> 이 배수는 NIST가 쓰는 관례이며 맥락에 따라 다르다.

| 원인 | 알아보는 법 | 처리 |
|---|---|---|
| 입력, 단위 오류 | 자리수 실수, 다른 단위로 보면 정상 | 원천에서 고치고, 못 고치면 표시하고 이유를 적는다 |
| 수집, 시스템 오류 | 특정 날짜나 경로에 몰려 있다 | 이슈 로그에 남기고 해당 구간 제외를 결정한다 |
| 정당한 극단 | 실제 대형 거래, 특수 사용자 | 남기고 따로 본다 |
| 원인을 모름 | 확인할 수 없다 | 남기고, 넣은 결과와 뺀 결과를 둘 다 적는다 |

이상값은 데이터 문제일 수도, 정당한 특수 사용자일 수도 있다. 숙박 예약 사이트의 여행사처럼 평균 사용자보다 훨씬 많이 사는 정당한 사용자는 상한을 씌우지 말고 하위 집단별 지표를 따로 만들라고 한다.<Ref n={6} />

## 숫자가 안 맞을 때

규칙: 의심되는 항목을 나란히 놓고 정의, 시간대, 형식, 통화, 단위를 대 본다.

| 종류 | 증상 | 확인 질문 |
|---|---|---|
| 같은 이름 다른 의미 | 두 보고서의 매출이 다르다(가정 예) | 환불, 취소, 세금 포함 여부를 나란히 적었나. 일관성은 정의에 대 보는 것이다<Ref n={1} /> |
| 시간대 | 일별 합계가 시스템마다 다르다 | 시각에 UTC와의 시차가 붙어 있나. 시차 없는 현지 시각은 해석이 어긋난다<Ref n={7} /> |
| 날짜 형식 | 09/08이 9월 8일인지 8월 9일인지 모른다 | 형식을 명시했나. 미국식을 유럽식으로 읽어 나이를 잘못 계산한 사례가 있다<Ref n={1} /> |
| 통화 | 합계가 맞지 않는다 | 통화와 환율 기준 시점이 같은가 |
| 단위 | 값이 수십 배 차이 난다 | 단위가 같은가. 지상 소프트웨어는 야드파운드법, 탐사선 소프트웨어는 미터법을 써서 화성 기후 궤도선을 잃었다<Ref n={8} /> |

외부 점검으로 정확성을 확인한다.

| 대조 | 방법 | 어긋나면 |
|---|---|---|
| 원천 합계 | 같은 기간, 같은 정의로 결제나 회계 같은 원천의 합계와 맞춘다 | 차이의 크기와 방향을 적는다. 허용 차이는 미리 정해 둔다 |
| 전 기간 | 지난 기간의 같은 지표와 비교한다 | 날짜가 딱 갈리며 변하면 수집이나 정의 변경을 묻는다 |
| 로그 유실 | 기기에서 올리는 로그는 유실률 지표를 만들어 본다<Ref n={6} /> | 유실이 한쪽 집단에 쏠렸는지 본다 |

실험 데이터는 실제 집단별 인원 비율이 설계한 비율과 맞는지(SRM) 먼저 본다.<Ref n={6} /> 실험 점검의 자세한 방법은 d10 글에서 다룬다.

## 처리 결정을 기록할 때

규칙: 이슈 하나에 로그 한 건, 처리 하나에 결정 기록 한 건을 남긴다. 점검은 반복되므로<Ref n={1} /> 나중의 나나 다른 사람이 같은 결과를 다시 만들 수 있어야 한다.

| 기록 | 담을 것 | 언제 |
|---|---|---|
| 점검표 | 차원별 질문, 결과 수치, 합격 기준, 통과 여부 | 데이터를 받을 때마다 |
| 이슈 로그 | 무엇을, 어디서, 영향, 원인, 상태 | 문제를 본 즉시 |
| 결정 기록 | 결정, 이유, 확인 방법, 책임자와 날짜 | 지우거나 채우거나 제외할 때 |

## 증상으로 찾기

| 증상 | 원인 | 처방 |
|---|---|---|
| 합계가 원천보다 크다 | 중복, 겹친 기간, 합치며 행이 늘어남 | 행 키와 원천 건수를 대 본다 |
| 합계가 원천보다 작다 | 추출 중단, 걸러짐, 로그 유실 | 첫 날과 끝 날, 날짜별 행 수를 본다 |
| 특정 날부터 값이 변한다 | 수집이나 정의 변경 | 그날의 변경 이력을 묻는다 |
| 일별 수치가 다른 보고서와 조금씩 다르다 | 시간대 차이 | 시각의 시차 표기를 확인한다 |
| 평균이 이상하게 크다 | 이상값, 단위 혼용 | 최댓값 행의 원인부터 본다 |
| 분석에 쓸 행이 급격히 준다 | 결측 행 제외가 겹침 | 항목별 빈 비율과 처리 선택을 다시 본다 |

## 흔한 실수

| 하지 마라 | 이렇게 | 이유 |
|---|---|---|
| 평균으로 빈 칸을 채우고 끝낸다 | 빈 분포를 보고 처리를 고른다 | 분산이 줄고 관계가 흐려진다<Ref n={4} /> |
| 큰 값이라 지운다 | 원인을 확인하고 기록한다 | 정당한 극단일 수 있다<Ref n={5} /> |
| 첫 점검으로 끝낸다 | 데이터가 바뀔 때마다 반복한다 | 새 문제는 분석 중에 나온다 |
| 차원을 통과했으니 믿는다 | 정의와 쓰임에도 맞는지 본다 | 통과해도 쓸모없을 수 있다 |

## 점검 체크리스트

- 출처, 추출 시점, 기간, 한 행의 뜻, 단위, 시간대를 확인했는가
- 행 수와 첫 날, 끝 날이 설명서나 원천과 맞는가
- 항목별, 날짜별, 집단별 빈 비율을 보고 몰린 곳을 찾았는가
- 결측 처리를 고르고 제외한 건수와 이유를 적었는가
- 중복을 행 키로 확인했고 정상 반복과 구분했는가
- 허용 범위 밖의 값과 이상값 후보를 원인과 함께 적었는가
- 같은 이름의 항목이 다른 곳과 같은 정의인지 나란히 대 봤는가
- 합계를 원천과 맞췄고 전 기간과 비교했는가
- 점검표, 이슈 로그, 결정 기록이 남아 있는가
