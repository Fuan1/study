- 해라: 행을 줄이지 않고 행마다 계산하려면 윈도우 함수, 행을 합치려면 GROUP BY 를 쓴다.
- 해라: 그룹별 최신 1건과 상위 N건은 `ROW_NUMBER()` 로 번호를 붙이고 바깥에서 거른다. ORDER BY 끝에 동점이 안 생기는 열(PK)을 넣는다.
- 하지 마라: 누적합과 이동평균에서 프레임을 생략하지 마라. ORDER BY 만 쓰면 기본 프레임이 `RANGE` 라 같은 값의 행이 함께 묶인다. `ROWS` 를 써라.
- 하지 마라: WHERE 에 윈도우 함수를 쓰지 마라. 서브쿼리나 CTE 로 감싼다(BigQuery 는 `QUALIFY`).
- 기준값: 서브쿼리가 3단 넘게 겹치거나 같은 집합을 두 번 쓰면 CTE 로 나눈다(관행). CTE 하나는 한 가지 일만 한다.

## 행을 줄이지 않고 계산해야 할 때

규칙: 합계·순위·이전 값을 원래 행 옆에 붙이려면 윈도우 함수를 쓴다. GROUP BY 는 행을 합치고 윈도우 함수는 행을 그대로 둔다.<Ref n={1} />

예제 테이블(`sales`, `orders`, `monthly`, `emp`)은 모두 가상이다. 쿼리는 PostgreSQL 문법으로 쓰고 SQLite 3.43 으로 실행해 결과를 옮겼다.

<Figure caption="같은 6행에 GROUP BY 는 2행을 돌려주고, 윈도우 합계는 6행을 그대로 두고 열을 붙인다. 가상 매출이다.">
  <WindowVsGroup />
</Figure>

```sql
fn(col) OVER (
  PARTITION BY g1, g2
  ORDER BY o1 DESC
  ROWS BETWEEN 2 PRECEDING
    AND CURRENT ROW)
```

PARTITION BY 를 빼면 전체가 한 묶음이다. ORDER BY 는 순위와 LAG 에 필수다. 프레임을 빼면 기본 프레임이 적용된다(뒤의 함정 절).

- 윈도우 계산은 FROM, WHERE, GROUP BY, HAVING 다음에 한다. WHERE 로 지운 행은 윈도우 함수에 보이지 않는다.<Ref n={1} />
- 집계와 함께 쓰면 집계 결과 위에서 계산한다. 지역 합계의 비율은 `SUM(SUM(amount)) OVER ()` 로 쓴다.<Ref n={1} />

## 순위를 매길 때

규칙: 동점을 어떻게 다룰지로 함수를 고른다.<Ref n={2} />

| 함수 | 동점 처리 | 쓰는 곳 |
|---|---|---|
| ROW_NUMBER | 다른 번호. 동점 간 순서는 정해지지 않는다 | 그룹당 정확히 N행 |
| RANK | 같은 번호, 다음 번호를 건너뜀(1, 1, 3) | 공동 순위 표시 |
| DENSE_RANK | 같은 번호, 건너뛰지 않음(1, 1, 2) | 상위 N등급 |

```sql
SELECT rep, region, amount,
  ROW_NUMBER() OVER w AS rn,
  RANK() OVER w AS rk,
  DENSE_RANK() OVER w AS dr
FROM sales
WINDOW w AS (PARTITION BY region
             ORDER BY amount DESC)
ORDER BY region, rk, rep;
```

| rep | region | amount | rn | rk | dr |
|---|---|---|---|---|---|
| kim | east | 300 | 1 | 1 | 1 |
| lee | east | 300 | 2 | 1 | 1 |
| park | east | 200 | 3 | 3 | 2 |
| choi | west | 500 | 1 | 1 | 1 |
| han | west | 400 | 3 | 2 | 2 |
| jung | west | 400 | 2 | 2 | 2 |

동점인 kim 과 lee 중 누가 `rn` 1이 되는지는 DB 가 정한다. 표는 이 실행의 값이다. `WINDOW w AS (...)` 는 같은 정의에 이름을 붙인다.

## 그룹별 최신 1건·상위 N건을 뽑을 때

규칙: 번호를 붙이는 층과 번호로 거르는 층을 나눈다. 윈도우 안 ORDER BY 끝에는 PK 를 넣어 동점을 없앤다.

| order_id | user_id | order_date | amount |
|---|---|---|---|
| 1 | u1 | 2026-01-05 | 30 |
| 2 | u1 | 2026-01-20 | 50 |
| 3 | u2 | 2026-01-07 | 20 |
| 4 | u2 | 2026-01-07 | 40 |
| 5 | u3 | 2026-01-09 | 70 |
| 6 | u1 | 2026-02-02 | 10 |
| 7 | u3 | 2026-02-11 | 25 |

```sql
SELECT user_id, order_id,
       order_date, amount
FROM (
  SELECT *,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY order_date DESC,
               order_id DESC) AS rn
  FROM orders) t
WHERE rn = 1
ORDER BY user_id;
```

| user_id | order_id | order_date | amount |
|---|---|---|---|
| u1 | 6 | 2026-02-02 | 10 |
| u2 | 4 | 2026-01-07 | 40 |
| u3 | 7 | 2026-02-11 | 25 |

u2 의 3번과 4번은 같은 날짜다. `order_id DESC` 를 빼면 어느 쪽이 남을지 정해지지 않는다. 빼고 돌렸더니 SQLite 는 3번을 남겼다.

상위 N건은 윈도우 안을 `ORDER BY amount DESC, order_id` 로, 바깥을 `WHERE rn <= 2` 로 바꾼다. 결과는 u1 이 2번(50)과 1번(30), u2 가 4번(40)과 3번(20), u3 이 5번(70)과 7번(25)이다.

### 같은 층에서 거를 수 없을 때

`WHERE ROW_NUMBER() OVER (...) = 1` 은 오류다. 윈도우 함수는 SELECT 목록과 ORDER BY 에서만 쓸 수 있고, 계산은 WHERE 보다 뒤다.<Ref n={3} />

<Figure caption="윈도우 값은 WHERE 다음에 만들어진다. 번호 붙이기(안쪽)와 거르기(바깥)는 층을 나눈다.">
  <LatestFlow />
</Figure>

방언은 아래와 같다(MySQL 은 8.0 부터 윈도우 함수를 지원한다). PostgreSQL<Ref n={3} />, BigQuery<Ref n={4} /><Ref n={5} />, MySQL<Ref n={6} /> 문서로 확인했다.

| 항목 | PostgreSQL | BigQuery | MySQL |
|---|---|---|---|
| 윈도우 함수를 쓸 수 있는 곳 | SELECT 목록, ORDER BY | SELECT 목록, ORDER BY, QUALIFY | SELECT 목록, ORDER BY |
| 번호로 거르기 | 서브쿼리나 CTE 로 감싼다 | QUALIFY 로 같은 층에서 거른다 | 서브쿼리나 CTE 로 감싼다 |
| QUALIFY | 없음 | 있음 | 없음 |

BigQuery 는 `QUALIFY ROW_NUMBER() OVER (...) = 1` 처럼 같은 층에서 거른다.

## 이전·다음 값과 비교할 때

규칙: 전월 대비는 `LAG`, 다음 값은 `LEAD` 로 가져온다. 기본은 한 행 앞뒤이고, 없으면 NULL 이다.<Ref n={2} />

```sql
SELECT month, revenue,
  LAG(revenue) OVER w AS prev,
  revenue - LAG(revenue) OVER w AS diff,
  ROUND(100.0 * (revenue
    - LAG(revenue) OVER w)
    / LAG(revenue) OVER w, 1) AS pct,
  LEAD(revenue) OVER w AS next
FROM monthly
WINDOW w AS (ORDER BY month);
```

| month | revenue | prev | diff | pct | next |
|---|---|---|---|---|---|
| 2026-01 | 100 | NULL | NULL | NULL | 120 |
| 2026-02 | 120 | 100 | 20 | 20.0 | 90 |
| 2026-03 | 90 | 120 | -30 | -25.0 | 150 |
| 2026-04 | 150 | 90 | 60 | 66.7 | 150 |
| 2026-05 | 150 | 150 | 0 | 0.0 | 180 |
| 2026-06 | 180 | 150 | 30 | 20.0 | NULL |

- 첫 행의 `prev` 는 NULL 이 맞다. 세 번째 인자(`LAG(revenue, 1, 0)`)로 0 을 채우면 첫 달 증감이 매출 전체로 보인다.
- `LAG` 는 날짜가 아니라 행 위치로 간다. 빠진 달이 있으면 두 달 전과 비교하므로 빈 달을 LEFT JOIN 으로 먼저 채워라.
- `LAG`·`LEAD` 는 프레임을 무시한다.<Ref n={2} />

## 누적합과 이동평균을 낼 때

규칙: 누적은 `ROWS UNBOUNDED PRECEDING`, n개 이동평균은 `ROWS BETWEEN n-1 PRECEDING AND CURRENT ROW` 로 쓴다. 세 DB 모두 이 구문을 지원한다.<Ref n={3} /><Ref n={4} /><Ref n={7} />

```sql
SELECT month, revenue,
  SUM(revenue) OVER (
    ORDER BY month
    ROWS UNBOUNDED PRECEDING) AS cum,
  ROUND(AVG(revenue) OVER (
    ORDER BY month
    ROWS BETWEEN 2 PRECEDING
      AND CURRENT ROW), 1) AS ma3,
  COUNT(*) OVER (
    ORDER BY month
    ROWS BETWEEN 2 PRECEDING
      AND CURRENT ROW) AS n
FROM monthly;
```

| month | revenue | cum | ma3 | n |
|---|---|---|---|---|
| 2026-01 | 100 | 100 | 100.0 | 1 |
| 2026-02 | 120 | 220 | 110.0 | 2 |
| 2026-03 | 90 | 310 | 103.3 | 3 |
| 2026-04 | 150 | 460 | 120.0 | 3 |
| 2026-05 | 150 | 610 | 130.0 | 3 |
| 2026-06 | 180 | 790 | 160.0 | 3 |

<Figure caption="3개월 이동평균은 변동을 완만하게 한다. 처음 두 달(속 빈 점)은 평균 대상이 3개 미만이다.">
  <MovingAvg />
</Figure>

- 처음 n-1 행은 대상이 모자란 평균이다. 같은 프레임의 `COUNT(*)` 로 확인하고 보고서에서는 빼거나 표시한다.
- `ROWS` 는 행 수로 센다. 날짜가 빠졌으면 "최근 3일" 이 "최근 3행" 이 되므로 날짜 행을 먼저 채운다.

## 전체 대비 비율을 구할 때

규칙: 전체 합은 `SUM(col) OVER ()`, 묶음 합은 `SUM(col) OVER (PARTITION BY g)` 로 행 옆에 붙여 나눈다.

```sql
SELECT rep, region, amount,
  ROUND(100.0 * amount /
    SUM(amount) OVER (), 1) AS pct
FROM sales
ORDER BY region, rep;
```

| rep | region | amount | pct |
|---|---|---|---|
| kim | east | 300 | 14.3 |
| lee | east | 300 | 14.3 |
| park | east | 200 | 9.5 |
| choi | west | 500 | 23.8 |
| han | west | 400 | 19.0 |
| jung | west | 400 | 19.0 |

정수끼리 나누면 PostgreSQL 은 소수를 버린다(5 / 2 는 2).<Ref n={8} /> `amount / SUM(amount) OVER ()` 는 이 데이터에서 전부 0이므로 `100.0 *` 를 앞에 둔다.

## ORDER BY 를 넣었더니 값이 달라질 때

규칙: 윈도우에 ORDER BY 만 쓰고 프레임을 쓰지 않으면 기본 프레임은 `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` 다. 현재 행과 ORDER BY 값이 같은 행(동점)을 모두 포함한다.<Ref n={3} /> BigQuery 와 MySQL 도 같다.<Ref n={4} /><Ref n={7} />

- ORDER BY 가 없으면 묶음 전체가 프레임이다. `SUM(x) OVER ()` 에 ORDER BY 를 넣으면 전체 합이 누적으로 바뀐다(monthly 앞 3행: 790, 790, 790 → 100, 220, 310).
- `ROWS` 는 행 위치, `RANGE` 는 ORDER BY 값을 기준으로 한다.<Ref n={7} />

```sql
SELECT order_id, order_date, amount,
  SUM(amount) OVER (
    ORDER BY order_date) AS run_default,
  SUM(amount) OVER (
    ORDER BY order_date, order_id
    ROWS UNBOUNDED PRECEDING
  ) AS run_rows
FROM orders
ORDER BY order_date, order_id;
```

| order_id | order_date | amount | run_default | run_rows |
|---|---|---|---|---|
| 1 | 2026-01-05 | 30 | 30 | 30 |
| 3 | 2026-01-07 | 20 | 90 | 50 |
| 4 | 2026-01-07 | 40 | 90 | 90 |
| 5 | 2026-01-09 | 70 | 160 | 160 |
| 2 | 2026-01-20 | 50 | 210 | 210 |
| 6 | 2026-02-02 | 10 | 220 | 220 |
| 7 | 2026-02-11 | 25 | 245 | 245 |

<Figure caption="3번 행의 기본 프레임은 같은 날짜의 4번 행까지 먹어 90이 된다. ROWS 는 현재 행에서 멈춰 50이다.">
  <FrameTie />
</Figure>

- 증상: 같은 날짜의 행이 모두 같은 누적값을 갖는다. 하루 단위로 보면 정상이라 놓치기 쉽다.
- 처방: 누적에는 `ROWS` 를 쓰고 ORDER BY 끝에 PK 를 넣어 같은 날짜 안의 순서를 고정한다. 일 단위로 먼저 합쳐 날짜가 유일하면 `RANGE` 도 같은 값이다.
- `LAST_VALUE` 도 기본 프레임이 현재 행까지라 묶음의 마지막 값이 나오지 않는다. 마지막 값은 `ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWING` 으로 쓴다.<Ref n={2} />

## 쿼리가 길어져 단계로 나눌 때

규칙: 중첩 서브쿼리가 3단을 넘으면 CTE(`WITH 이름 AS (...)`)로 바꿔 위에서 아래로 읽히게 한다.

문제: 사용자별 최신 주문 금액이 최신 주문 금액의 평균보다 큰 사용자를 찾는다. 나쁜 쿼리는 "최신 1건" 블록을 두 번 복사하고 3단까지 들어간다.

```sql
SELECT user_id, amount
FROM (
  SELECT user_id, amount
  FROM (
    SELECT user_id, amount,
      ROW_NUMBER() OVER (
        PARTITION BY user_id
        ORDER BY order_date DESC,
                 order_id DESC) AS rn
    FROM orders) r
  WHERE rn = 1) l
WHERE amount > (
  SELECT AVG(amount)
  FROM (
    SELECT user_id, amount
    FROM (
      SELECT user_id, amount,
        ROW_NUMBER() OVER (
          PARTITION BY user_id
          ORDER BY order_date DESC,
                   order_id DESC) AS rn
      FROM orders) r2
    WHERE rn = 1) l2);
```

고친 쿼리는 `latest` 를 한 번 정의하고 두 번 읽는다. 결과는 같다.

```sql
WITH ranked AS (
  SELECT user_id, amount,
    ROW_NUMBER() OVER (
      PARTITION BY user_id
      ORDER BY order_date DESC,
               order_id DESC) AS rn
  FROM orders
),
latest AS (
  SELECT user_id, amount
  FROM ranked
  WHERE rn = 1
)
SELECT user_id, amount
FROM latest
WHERE amount > (SELECT AVG(amount)
                FROM latest);
```

| user_id | amount |
|---|---|
| u2 | 40 |

최신 금액은 10, 40, 25 이고 평균은 25 다. 40만 25를 넘는다.

선택 기준(관행): 한 줄짜리 조건(`IN (SELECT ...)`)은 서브쿼리로 둔다. 단계가 둘 이상이거나 같은 집합을 두 번 쓰면 CTE 로 쓴다. CTE 는 읽기 위한 도구이고 속도는 실행 계획으로 확인한다.

- 이름은 내용을 말하게 쓴다(`ranked`, `latest`). `t1`, `tmp` 는 쓰지 마라.
- CTE 하나에 거르기, 번호, 집계를 몰지 마라. 한 가지 일만 시킨다.

### 같은 CTE 를 여러 번 읽을 때

PostgreSQL 12 부터 부작용이 없고 재귀가 아닌 CTE 는 한 번만 참조하면 바깥 쿼리에 합쳐진다(인라인). 여러 번 참조하면 기본은 한 번 계산해 재사용한다. `AS MATERIALIZED` 는 따로 계산하게, `AS NOT MATERIALIZED` 는 합치게 강제한다.<Ref n={9} /><Ref n={10} /> 방언마다 다르다. BigQuery<Ref n={5} />, MySQL<Ref n={11} /><Ref n={12} /> 문서로 확인했다.

| 항목 | PostgreSQL | BigQuery | MySQL |
|---|---|---|---|
| 한 번 참조 | 바깥에 합침 | 구체화하지 않음 | 합치려고 시도 |
| 여러 번 참조 | 한 번 계산해 재사용 | 참조할 때마다 실행 | 확인 필요 |
| 방식 지정 | MATERIALIZED, NOT MATERIALIZED | 확인 필요 | MERGE, NO_MERGE 힌트 |

- "CTE 는 항상 따로 계산된다" 는 PostgreSQL 11 이하 이야기다. 12 부터 기본이 바뀌었다.

### 계층을 따라 내려갈 때

규칙: 상하 관계 탐색에만 재귀 CTE 를 쓴다. 시작 행, `UNION ALL`, 자기 자신을 읽는 부분의 세 조각이며 세 DB 모두 `WITH RECURSIVE` 로 쓴다. 자기 참조에서 새 행이 안 나오면 끝난다.<Ref n={9} />

`emp`(id, name, manager_id)는 가상의 조직도 6행이다.

```sql
WITH RECURSIVE tree AS (
  SELECT id, name, 0 AS depth
  FROM emp
  WHERE manager_id IS NULL
  UNION ALL
  SELECT e.id, e.name, t.depth + 1
  FROM emp e
  JOIN tree t ON e.manager_id = t.id
)
SELECT id, name, depth
FROM tree
ORDER BY depth, id;
```

| id | name | depth |
|---|---|---|
| 1 | ceo | 0 |
| 2 | a | 1 |
| 3 | b | 1 |
| 4 | c | 2 |
| 5 | d | 2 |
| 6 | e | 3 |

- 순환 데이터(A 의 상사가 B, B 의 상사가 A)는 끝나지 않는다. 깊이 상한(`WHERE depth < 10`)을 걸어라.
- BigQuery 는 500회 반복을 넘으면 실패하고, MySQL 은 `cte_max_recursion_depth` 가 기본 1000이다.<Ref n={5} /><Ref n={11} /> PostgreSQL 은 `CYCLE` 절로 순환을 잡는다(14 이상).<Ref n={13} />

## 증상으로 찾기

| 증상 | 원인 | 처방 |
|---|---|---|
| 윈도우 함수를 WHERE 에 썼더니 오류 | 윈도우는 WHERE 뒤에 계산된다 | 서브쿼리나 CTE 로 감싸거나 QUALIFY(BigQuery) |
| 최신 1건이 실행마다 바뀐다 | 정렬 기준에 동점이 있고 ROW_NUMBER 는 동점 순서가 불명 | ORDER BY 끝에 PK 추가 |
| 같은 날짜 행의 누적값이 같다 | 기본 프레임 RANGE 가 동점을 묶는다 | `ROWS UNBOUNDED PRECEDING` 과 PK 추가 |
| 전월 대비가 엉뚱한 달과 비교된다 | LAG 는 행 위치로 간다. 빠진 달이 있다 | 빈 달을 먼저 채운다 |
| 비율이 전부 0 이다 | 정수 나눗셈 | `100.0 *` 를 앞에 둔다 |
| 이동평균 앞쪽 값이 이상하다 | 프레임의 행이 n개 미만 | `COUNT(*)` 로 확인하고 빼거나 표시 |
| 조인 뒤 순위나 합계가 부풀었다 | 윈도우 전에 행이 늘었다 | 조인 결과의 행 수와 키 중복을 먼저 본다 |

## 점검 체크리스트

- 윈도우 함수를 WHERE, GROUP BY, HAVING 에 쓰지 않았는가.
- ROW_NUMBER 의 ORDER BY 끝에 동점이 안 생기는 열이 있는가.
- 누적합과 이동평균에 `ROWS` 프레임을 명시했는가.
- LAG 가 비교하는 행이 의도한 달인가(빠진 달 없음).
- 윈도우 계산 전에 조인으로 행이 늘지 않았는가.
- 서브쿼리가 3단 이하이고, 같은 블록을 복사하지 않았는가.
- CTE 이름이 내용을 말하고 CTE 마다 한 가지 일만 하는가.
