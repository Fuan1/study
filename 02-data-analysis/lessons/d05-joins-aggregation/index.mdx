- 해라: 조인 전에 양쪽 키가 유일한지 `GROUP BY` + `HAVING COUNT(*) > 1` 로 센다. 중복이면 키 단위로 집계한 뒤 조인한다.
- 해라: 조인 후 행 수와 합계를 조인 전과 대조한다. 기준 테이블을 `LEFT JOIN` 으로 보존했다면 같아야 한다.
- 하지 마라: `LEFT JOIN` 의 오른쪽 테이블 조건을 `WHERE` 에 두지 마라. 짝을 제한하는 조건은 `ON` 에 둔다.
- 하지 마라: 없는 것 찾기에 `NOT IN` 을 쓰지 마라. 서브쿼리에 NULL 이 있으면 결과가 비어 버린다. `NOT EXISTS` 를 써라.
- 기준값: 조인 전후 합계 차이 0. 1:N 조인은 N 쪽 행 수만큼, N:M 은 키별 곱만큼 행이 는다. 합계가 어긋나면 `DISTINCT` 로 덮지 말고 grain 을 맞춘다.

## 조인 종류를 고를 때

규칙: 종류는 "어느 쪽 행을 반드시 남기나"로 고른다.<Ref n={1} />

| 종류 | 남는 행 | 쓰는 때 | 주의 |
|---|---|---|---|
| INNER | 양쪽 일치만 | 짝 있는 것만 볼 때 | 짝 없는 행이 말없이 빠진다 |
| LEFT | 왼쪽 전부 + 일치한 오른쪽 | 기준 테이블을 다 남길 때 | 오른쪽 조건을 WHERE 에 두면 INNER 가 된다 |
| FULL | 양쪽 전부 | 두 목록을 대조할 때 | MySQL 은 문법이 없다 |
| CROSS | 모든 짝(n × m) | 조합 틀을 만들 때 | 행 수가 곱이 된다 |

<Figure caption="같은 두 테이블도 종류에 따라 6, 7, 8, 28행이 된다. 칸의 숫자는 order_id 이고 주문 3은 세 번 나온다.">
  <JoinRows />
</Figure>

- `RIGHT JOIN` 대신 테이블 순서를 바꿔 `LEFT JOIN` 으로 쓴다. MySQL 문서도 이식성을 위해 LEFT 를 권한다.<Ref n={2} />
- FULL 이 필요한 MySQL 에서는 LEFT 결과에 오른쪽만 있는 행을 `UNION ALL` 로 붙인다(관행). BigQuery 는 `FULL JOIN` 을 지원한다.<Ref n={3} />

## 조인하기 전에 확인할 것

규칙: 키가 양쪽에서 유일한지 먼저 센다. 조인 뒤 행 수는 이 결과로 정해진다.

```sql
SELECT order_id, COUNT(*) AS n
FROM order_items
GROUP BY order_id
HAVING COUNT(*) > 1;
```

| order_id | n |
|---|---|
| 1 | 2 |
| 3 | 3 |

같은 쿼리를 `orders` 에 돌리면 0행이다. 왼쪽 키는 유일하고 오른쪽 키는 중복이다.

| 왼쪽 키 | 오른쪽 키 | 관계 | 조인 뒤 행 수 |
|---|---|---|---|
| 유일 | 유일 | 1:1 | 왼쪽 이하(LEFT 면 같다) |
| 유일 | 중복 | 1:N | 왼쪽 값이 짝 수만큼 반복된다 |
| 중복 | 중복 | N:M | 키별 곱으로 폭증한다 |

- 키 칼럼에 NULL 이 있으면 `=` 로는 짝이 되지 않는다. 키의 NULL 개수도 같이 센다.
- 유일해야 할 키가 중복이면 조인을 멈추고 원인(중복 적재, 키 정의 오류)부터 찾는다.

## 합계가 부풀 때: 1:N 조인

증상: 조인만 했는데 합계가 원래보다 크다. 원인은 fan-out 이다. 1:N 조인에서 1 쪽 값이 N 쪽 행 수만큼 복제된다.

나쁜 쿼리: 상품을 붙인 채로 주문 금액을 합한다.

```sql
SELECT COUNT(*) AS n_rows,
       SUM(o.amount) AS total
FROM orders o
LEFT JOIN order_items i
  ON i.order_id = o.order_id;
```

| n_rows | total |
|---|---|
| 7 | 1500 |

조인 전 `orders` 는 4행에 합계 800이다. 주문 1(100)은 두 번, 주문 3(300)은 세 번 더해졌다.

<Figure caption="조인 뒤 4행이 7행이 되면서 합계가 800에서 1500으로 늘었다.">
  <FanOut />
</Figure>

고치는 원칙: 조인 직전에 오른쪽을 왼쪽 키 단위로 만든다.

### 집계한 뒤 조인한다

상품 쪽 값이 필요하면 키 단위로 집계해서 붙인다.

```sql
SELECT COUNT(*) AS n_rows,
       SUM(o.amount) AS total
FROM orders o
LEFT JOIN (
  SELECT order_id, SUM(qty) AS qty
  FROM order_items
  GROUP BY order_id
) i ON i.order_id = o.order_id;
```

| n_rows | total |
|---|---|
| 4 | 800 |

### 키만 중복 제거해서 조인한다

"A 상품이 있는 주문"처럼 오른쪽 값이 필요 없으면 키만 `DISTINCT` 로 뽑아 붙인다. 존재만 필요하면 뒤의 `EXISTS` 가 더 간단하다.

```sql
SELECT COUNT(*) AS n_rows,
       SUM(o.amount) AS total
FROM orders o
JOIN (
  SELECT DISTINCT order_id
  FROM order_items
  WHERE sku = 'A'
) i ON i.order_id = o.order_id;
```

| n_rows | total |
|---|---|
| 3 | 600 |

여러 행 중 최신 1건만 남기는 중복 제거는 d06 의 윈도우 함수로 한다.

### COUNT(DISTINCT) 로 덮지 않는다

`COUNT(DISTINCT 키)` 는 건수에는 통하지만 합계에는 틀린다. 값이 같은 서로 다른 행이 하나로 합쳐지기 때문이다.

```sql
SELECT COUNT(DISTINCT o.order_id) AS n,
       SUM(DISTINCT o.amount) AS s
FROM orders o
LEFT JOIN order_items i
  ON i.order_id = o.order_id;
```

| n | s |
|---|---|
| 4 | 600 |

`n` 은 맞다. `s` 는 틀렸다(정답 800). 주문 2와 4의 금액이 둘 다 200이라 하나로 합쳐졌다. 금액이 안 겹치면 맞아 보여서 더 위험하다.

## LEFT JOIN 인데 행이 줄 때

증상: `LEFT JOIN` 인데 일부 행이 사라진다. 원인: 오른쪽 칼럼 조건을 `WHERE` 에 뒀다. `ON` 은 조인 전에, `WHERE` 는 조인 뒤에 걸린다.<Ref n={1} /> 짝 없는 행은 오른쪽 칼럼이 NULL 이라 조건이 참이 못 되어 걸러지고, 결과가 INNER JOIN 과 같아진다.

나쁜 쿼리와 결과(B 상품이 있는 주문만 남았다):

```sql
SELECT o.order_id, i.sku
FROM orders o
LEFT JOIN order_items i
  ON i.order_id = o.order_id
WHERE i.sku = 'B';
```

| order_id | sku |
|---|---|
| 1 | B |
| 3 | B |

고친 쿼리와 결과(주문은 4개 다 남고 B 짝만 붙는다):

```sql
SELECT o.order_id, i.sku
FROM orders o
LEFT JOIN order_items i
  ON i.order_id = o.order_id
 AND i.sku = 'B';
```

| order_id | sku |
|---|---|
| 1 | B |
| 2 | NULL |
| 3 | B |
| 4 | NULL |

<Figure caption="같은 조건을 WHERE 에 두면 주문 2와 4가 사라지고, ON 에 두면 4행이 남는다.">
  <OnVsWhere />
</Figure>

| 조건의 대상 | 두는 곳 |
|---|---|
| 왼쪽(기준) 테이블 칼럼으로 행을 줄이기 | `WHERE` (예: `WHERE o.amount >= 200`) |
| 오른쪽 테이블에서 붙일 짝을 제한하기 | `ON` |
| 오른쪽에 짝이 없는 행 찾기 | `WHERE 오른쪽 키 IS NULL` |

- `WHERE i.sku = 'B' OR i.sku IS NULL` 로 땜질하지 마라. 주문 4는 살아나지만 A 상품만 있는 주문 2는 여전히 빠진다(결과 1, 3, 4).

## 없는 것을 찾을 때: anti-join

규칙: "주문이 없는 고객"처럼 없는 것은 `NOT EXISTS` 로 찾는다. `LEFT JOIN … IS NULL` 도 같은 결과다.

```sql
SELECT c.customer_id
FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.customer_id
);
```

```sql
SELECT c.customer_id
FROM customers c
LEFT JOIN orders o
  ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;
```

위 두 쿼리의 결과는 같다.

| customer_id |
|---|
| c3 |
| c4 |

`NOT IN` 은 결과가 비어 버린다. 주문 4의 `customer_id` 가 NULL 이기 때문이다.

```sql
SELECT c.customer_id
FROM customers c
WHERE c.customer_id NOT IN (
  SELECT customer_id FROM orders
);
```

결과: 0행.

목록에 NULL 이 섞이면 "일치하지 않는다"가 참이 못 되고 NULL 로 평가되어 모든 행이 걸러진다. 세 방언 모두 같은 규칙이다.<Ref n={4} /><Ref n={5} /><Ref n={6} />

| 방법 | 서브쿼리에 NULL 이 있을 때 | 쓰는 기준 |
|---|---|---|
| NOT EXISTS | 정상 | 기본으로 쓴다 |
| LEFT JOIN … IS NULL | 정상 | 오른쪽 키나 NOT NULL 칼럼으로 검사한다 |
| NOT IN | 0행(전부 사라짐) | 서브쿼리에 `IS NOT NULL` 을 붙일 때만 |


## 있는지만 확인할 때: semi-join

규칙: "주문한 적 있는 고객"처럼 존재만 필요하면 `JOIN` 말고 `EXISTS` 를 쓴다. 오른쪽이 N 개여도 왼쪽 행이 복제되지 않는다.

```sql
SELECT c.customer_id
FROM customers c
JOIN orders o
  ON o.customer_id = c.customer_id;
```

| customer_id |
|---|
| c1 |
| c1 |
| c2 |

c1 이 주문 수만큼 두 번 나온다. 존재만 필요하면 이렇게 쓴다.

```sql
SELECT c.customer_id
FROM customers c
WHERE EXISTS (
  SELECT 1 FROM orders o
  WHERE o.customer_id = c.customer_id
);
```

| customer_id |
|---|
| c1 |
| c2 |


## 다대다로 행이 폭발할 때

증상: 건수가 몇 배로 늘었다. 원인: 양쪽 키가 모두 중복이다. 방문과 주문은 서로 관계가 없는데 `customer_id` 만으로 이었다.

```sql
SELECT v.customer_id,
       COUNT(*) AS visits
FROM visits v
JOIN orders o
  ON o.customer_id = v.customer_id
GROUP BY v.customer_id;
```

| customer_id | visits |
|---|---|
| c1 | 6 |
| c2 | 2 |

실제 방문은 c1 이 3회, c2 가 2회다. c1 은 방문 3 × 주문 2 = 6행이 되었다. c2 는 주문이 1건이라 우연히 맞았다.

<Figure caption="한 키에 방문 3행과 주문 2행이면 6행이다. 키당 1000행씩이면 100만 행이다.">
  <ManyToMany />
</Figure>

예방: 양쪽 키가 모두 중복이면 조인하지 말고 각각 키 단위로 집계한 뒤 붙인다.

```sql
SELECT v.customer_id, v.visits, o.orders
FROM (
  SELECT customer_id, COUNT(*) AS visits
  FROM visits
  GROUP BY customer_id
) v
JOIN (
  SELECT customer_id, COUNT(*) AS orders
  FROM orders
  GROUP BY customer_id
) o ON o.customer_id = v.customer_id;
```

| customer_id | visits | orders |
|---|---|---|
| c1 | 3 | 2 |
| c2 | 2 | 1 |

## 매칭이 안 될 때

증상: `LEFT JOIN` 뒤 오른쪽 칼럼이 많이 NULL 이거나 `INNER JOIN` 뒤 행이 확 줄었다. 먼저 짝을 못 찾는 건수를 센다. 키에 공백과 대소문자가 섞인 가상 테이블 `orders_raw` 를 썼다.

```sql
SELECT COUNT(*) AS n,
       COUNT(c.customer_id) AS matched
FROM orders_raw r
LEFT JOIN customers c
  ON c.customer_id = r.customer_id;
```

| n | matched |
|---|---|
| 4 | 2 |

짝 못 찾은 키를 꺼낸다. 대괄호와 길이를 같이 찍으면 보이지 않는 공백이 드러난다.

```sql
SELECT r.order_id,
       '[' || r.customer_id || ']'
         AS cid,
       LENGTH(r.customer_id) AS len
FROM orders_raw r
LEFT JOIN customers c
  ON c.customer_id = r.customer_id
WHERE c.customer_id IS NULL;
```

| order_id | cid | len |
|---|---|---|
| 1 | [c1 ] | 3 |
| 2 | [C2] | 2 |

고침: 정제 단계에서 키를 정규화하는 것이 원칙이다. 급하면 `ON c.customer_id = LOWER(TRIM(r.customer_id))` 로 맞춘다(`matched` 가 4). 키에 함수를 씌우면 인덱스를 못 쓸 수 있다(d07).

| 원인 | 확인 방법 | 처방 |
|---|---|---|
| 앞뒤 공백 | `LENGTH(키)` 와 `LENGTH(TRIM(키))` 비교 | `TRIM`. 기본으로 공백 문자만 지운다<Ref n={7} /> |
| 대소문자 | 짝 못 찾은 키를 `LOWER` 로 다시 비교 | `LOWER` 로 통일 |
| 타입 불일치 | 아래 방언 표 | 한쪽을 `CAST` |
| NULL 키 | `COUNT(*)` 와 `COUNT(키)` 비교 | 제외하거나 NULL 안전 비교 |

| 항목 | PostgreSQL | BigQuery | MySQL |
|---|---|---|---|
| 정수 = 문자열 | 오류(암묵 변환 없음)<Ref n={8} /> | 확인 필요(변환 표에서 INT64 는 STRING 으로 자동 변환되지 않음)<Ref n={9} /> | 자동 변환해 비교(실수 비교)<Ref n={6} /> |
| NULL 안전 비교 | `IS NOT DISTINCT FROM`<Ref n={10} /> | `IS NOT DISTINCT FROM`<Ref n={5} /> | `<=>`<Ref n={6} /> |

MySQL 의 자동 변환은 오류 없이 조용히 어긋나므로 키 타입을 직접 확인한다. NULL 키끼리 짝을 지으려면 `ON a.k IS NOT DISTINCT FROM b.k` 를 쓴다. 키가 `x` 와 NULL 인 두 테이블에서 `=` 는 1행, 이 방식은 2행을 냈다.

## 집계 단위를 맞출 때

규칙: `GROUP BY` 에 쓴 칼럼 조합이 결과 한 행의 정체(grain)다. 조인 전에 양쪽을 같은 grain 으로 맞춘다.

| 테이블 | 한 행 | 키 | 붙일 때 |
|---|---|---|---|
| orders | 주문 1건 | order_id | 그대로 |
| order_items | 주문 안의 상품 1줄 | item_id | order_id 로 집계한 뒤 |
| visits | 방문 1회 | 없음(고객+일자 확인 필요) | customer_id 로 집계한 뒤 |

`LEFT JOIN` 뒤 건수는 `COUNT(*)` 가 아니라 오른쪽 키의 `COUNT` 로 센다. 짝 없는 행도 1행으로 세기 때문이다.

```sql
SELECT o.order_id,
       COUNT(*) AS cnt_star,
       COUNT(i.item_id) AS cnt_item
FROM orders o
LEFT JOIN order_items i
  ON i.order_id = o.order_id
GROUP BY o.order_id;
```

| order_id | cnt_star | cnt_item |
|---|---|---|
| 1 | 2 | 2 |
| 2 | 1 | 1 |
| 3 | 3 | 3 |
| 4 | 1 | 0 |

주문 4는 상품이 0개인데 `COUNT(*)` 는 1이다.

## 조인한 뒤 검증할 때

규칙: 조인 결과를 쓰기 전에 행 수와 합계를 원본과 나란히 놓는다.

```sql
WITH j AS (
  SELECT o.order_id, o.amount
  FROM orders o
  LEFT JOIN order_items i
    ON i.order_id = o.order_id
)
SELECT
  (SELECT COUNT(*) FROM orders) o_rows,
  COUNT(*) AS j_rows,
  COUNT(DISTINCT order_id) AS j_orders,
  (SELECT SUM(amount) FROM orders)
    AS o_sum,
  SUM(amount) AS j_sum
FROM j;
```

| 구분 | o_rows | j_rows | j_orders | o_sum | j_sum |
|---|---|---|---|---|---|
| 상품을 그대로 조인 | 4 | 7 | 4 | 800 | 1500 |
| 상품을 집계해 조인 | 4 | 4 | 4 | 800 | 800 |

- `j_rows` 가 `o_rows` 보다 크면 fan-out 이다.
- `INNER JOIN` 이면 줄어든 행이 의도한 것인지 본다. 짝 없는 행 수는 반대쪽에서 센다.

```sql
SELECT COUNT(*) - COUNT(o.order_id)
         AS no_match
FROM order_items i
LEFT JOIN orders o
  ON o.order_id = i.order_id;
```

| no_match |
|---|
| 1 |

상품 7(order_id 9)은 짝이 없다. `INNER JOIN` 이면 오류 없이 사라진다.

| 나쁜 예 | 고친 예 | 이유 |
|---|---|---|
| 1:N 조인 뒤 `SUM(o.amount)` | 오른쪽을 키 단위로 집계한 뒤 조인 | 1 쪽 값이 복제된다 |
| 합계가 안 맞아 `SUM(DISTINCT 금액)` | grain 을 맞춤 | 같은 금액의 다른 행이 합쳐진다 |
| `LEFT JOIN` + `WHERE i.sku = 'B'` | 조건을 `ON` 으로 이동 | WHERE 가 INNER 로 바꾼다 |
| 없는 것 찾기에 `NOT IN` | `NOT EXISTS` | NULL 이 있으면 0행이 된다 |
| 양쪽이 중복인 키로 조인 | 양쪽을 집계한 뒤 조인 | 키별 곱이 된다 |

## 증상으로 찾기

| 증상 | 원인 | 처방 |
|---|---|---|
| 조인 후 합계가 원본보다 크다 | 1:N 조인의 fan-out | 오른쪽을 집계하거나 키만 중복 제거 |
| 건수가 몇 배로 늘었다 | 양쪽 키 중복(N:M) | 양쪽을 키 단위로 집계한 뒤 조인 |
| LEFT JOIN 인데 행이 줄었다 | 오른쪽 조건을 WHERE 에 둠 | 조건을 ON 으로 옮김 |
| 없는 것 찾기가 0행이다 | NOT IN 목록에 NULL | NOT EXISTS 로 교체 |
| 조인 후 오른쪽 칼럼이 다 NULL | 키 공백, 대소문자, 타입 불일치 | 짝 못 찾은 키를 꺼내 정규화 |
| INNER 뒤 행이 줄었다 | 짝 없는 키가 조용히 빠짐 | 반대쪽에서 짝 없는 행 수를 센다 |
| 0건이어야 하는 행이 1건이다 | LEFT JOIN 뒤 COUNT(*) | 오른쪽 키로 COUNT |

## 점검 체크리스트

- 조인 키가 양쪽에서 유일한지 센 결과를 확인했는가.
- 키의 NULL 개수, 공백, 대소문자, 타입을 확인했는가.
- 조인 직전에 오른쪽이 왼쪽 키 단위(1행 1키)인가.
- `LEFT JOIN` 의 오른쪽 조건이 모두 `ON` 에 있는가.
- 없는 것 찾기는 `NOT EXISTS`, 존재 확인은 `EXISTS` 로 썼는가.
- `COUNT(DISTINCT)` 나 `SUM(DISTINCT)` 로 복제를 덮지 않았는가.
- 조인 전후 행 수와 합계 차이가 0인가.
- `GROUP BY` 단위가 지표 정의의 단위와 같은가.
