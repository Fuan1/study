## 제출 전에 숫자를 검증할 때

예제는 모두 가정한 데이터다. 주문 `orders`(10행: 주문번호, 사용자, 채널, 상태, 주문 시각 UTC, 금액)와 주문 상품 `order_items`(13행)가 있고, 정산 시스템은 결제(paid) 주문 8건, 380,000원이라고 알려 줬다고 가정한다. 쿼리는 PostgreSQL 문법이고 SQLite로 돌려 결과를 옮겼다(시간대 변환만 SQLite 식으로 대체).

### 1단계: 요구와 정의를 다시 확인할 때

요청한 질문과 내 지표가 같은지 정의서(분자, 분모, 제외 조건)와 대조하고, 기간, 시간대, 환불·취소 포함 여부를 적는다. 정의서가 없으면 한 줄로 써서 요청자에게 확인받는다. 예제의 지표는 "결제(paid) 주문의 금액 합"이다.

### 2단계: 행 수와 합계를 원천과 대조할 때

규칙: 원천(정산, 원장, 운영 화면)의 건수와 합계를 먼저 받아 두고 내 결과와 나란히 놓는다.

```sql
SELECT COUNT(*) AS n_rows,
  COUNT(DISTINCT order_id) AS n_ord,
  SUM(amount) AS total
FROM orders
WHERE status = 'paid';
```

| n_rows | n_ord | total |
|---|---|---|
| 9 | 8 | 440000 |

건수는 8로 맞지만 합계가 60,000 많고 `n_rows`와 `n_ord`가 다르다. 중복 적재를 의심하고 키를 찾는다.

```sql
SELECT order_id, COUNT(*) AS n
FROM orders
GROUP BY order_id
HAVING COUNT(*) > 1;
```

| order_id | n |
|---|---|
| 1005 | 2 |

적재를 고치는 것이 원칙이고, 임시로는 모든 열이 같은 행만 `SELECT DISTINCT *`로 제거한다. 이후는 이 중복 제거본 `orders_ok`(9행)로 돌린다. 조인 앞뒤에서도 합계를 다시 찍는다.

```sql
-- 나쁜 쿼리: 상품 행만큼 금액이 반복됨
SELECT SUM(o.amount) AS total
FROM orders_ok o
JOIN order_items i
  ON i.order_id = o.order_id
WHERE o.status = 'paid';
```

| total |
|---|
| 492000 |

주문 하나에 상품이 여러 줄이면 주문 금액이 줄 수만큼 더해진다(조인 폭증). 상품 쪽을 주문 단위로 먼저 집계한다.

```sql
-- 고친 쿼리: 주문 단위로 맞춘 뒤 조인
SELECT SUM(o.amount) AS total
FROM orders_ok o
JOIN (SELECT order_id,
        COUNT(*) AS n_items
      FROM order_items
      GROUP BY order_id) i
  ON i.order_id = o.order_id
WHERE o.status = 'paid';
```

| total |
|---|
| 380000 |

`SUM(DISTINCT amount)`로 막지 마라. 금액이 같은 다른 주문도 사라진다.

### 3단계: 지표를 다른 방법으로 재계산할 때

규칙: 같은 값을 다른 테이블이나 다른 경로로 한 번 더 구한다. 주문 금액 합을 상품 줄의 `수량 x 단가` 합으로 대조한다.

```sql
SELECT SUM(i.qty * i.unit_price)
    AS item_total
FROM order_items i
JOIN orders_ok o
  ON o.order_id = i.order_id
WHERE o.status = 'paid';
```

| item_total |
|---|
| 380000 |

주문 합계 380,000과 같다. 다르면 주문별 차이를 내려 어긋나는 주문을 찾는다.

### 4단계: 세그먼트 합을 전체와 맞출 때

규칙: 채널, 지역 같은 조각의 합은 전체와 같아야 한다. 조각에는 NULL(값 없음) 그룹도 있다. 값 없음을 이름 붙여 남긴다.

```sql
SELECT COALESCE(channel, '(없음)')
    AS ch,
  SUM(amount) AS rev
FROM orders_ok
WHERE status = 'paid'
GROUP BY 1
ORDER BY 2 DESC;
```

| ch | rev |
|---|---|
| web | 262000 |
| app | 103000 |
| (없음) | 15000 |

조각의 합과 전체를 한 번에 찍어 비교한다.

```sql
WITH seg AS (
  SELECT channel, SUM(amount) AS rev
  FROM orders_ok
  WHERE status = 'paid'
  GROUP BY channel)
SELECT SUM(rev) AS seg_sum,
  (SELECT SUM(amount) FROM orders_ok
   WHERE status = 'paid') AS total
FROM seg;
```

| seg_sum | total |
|---|---|
| 380000 | 380000 |

나쁜 쿼리는 `AND channel IN ('web', 'app')` 한 줄 때문에 같은 대조에서 365000 대 380000이 나온다(15,000이 어느 조각에도 없다).

<Figure caption="조각을 WHERE로 거르면 합이 전체보다 작다. 값 없음 조각을 남기면 같다. 가정한 결제 8건이다.">
  <SegmentCheck />
</Figure>

한 건이 두 조각에 걸치는 분류(태그)는 합이 전체보다 커도 정상이며, 이때는 "중복 포함 합"이라고 쓴다.

### 5단계: 극단값과 샘플 행을 눈으로 볼 때

규칙: 합계가 맞아도 상위, 하위, 무작위 몇 건은 원본 행으로 직접 본다. 몇 건을 봐야 한다는 정해진 기준은 없고 각 5건 정도가 실무 관행이다.

```sql
SELECT order_id, channel, amount
FROM orders_ok
WHERE status = 'paid'
ORDER BY amount DESC
LIMIT 3;
```

| order_id | channel | amount |
|---|---|---|
| 1007 | web | 120000 |
| 1005 | web | 60000 |
| 1009 | web | 52000 |

1007은 합계의 31.6퍼센트이고 중앙값(41,500)의 약 2.9배다. 3단계에서 상품 줄(10개 x 12,000)과 맞았으므로 오류가 아닌 대량 주문이다. 보고에는 "1건 제외 시 260,000"을 함께 쓴다. 단위가 100배 틀린 값, 0과 음수, 테스트 계정도 여기서 잡힌다.

### 6단계: 결과 방향이 상식과 맞는지 볼 때

규칙: 상식과 반대이거나(가격 인상 뒤 주문 증가), 모든 세그먼트가 같이 움직이거나, 비율이 100퍼센트를 넘으면 기간 불일치, 집계 기준 변경, 중복, 모집단 불일치부터 지운다. 다 지워도 남으면 새 발견으로 쓴다.

## 숫자가 이상할 때

규칙: 증상으로 원인을 좁히고, 확인 쿼리를 한 번씩 돌린다.

| 증상 | 흔한 원인 | 확인과 처방 |
|---|---|---|
| 합계가 원천보다 크다 | 중복 적재 | 키별 `COUNT(*) > 1` 확인. 적재를 고치거나 제거본 사용 |
| 조인 뒤 합계가 커졌다 | 조인 폭증(한쪽이 여러 행) | 조인 전후 `COUNT(*)` 비교. 먼저 같은 단위로 집계 |
| 합계가 원천보다 작다 | 필터 누락, 내부 조인으로 NULL 행 탈락 | 필터와 조인 조건 점검. 조각 합 대조 |
| 날짜별 값이 원천과 하루씩 어긋난다 | 시간대(UTC 대 KST) | 같은 주문을 두 시간대로 묶어 비교 |
| 비율이 0이나 1로 나온다 | 정수 나눗셈 | `1.0 *`를 곱하거나 형변환. 분모 0은 NULL 처리 |
| 어제 값이 오늘 다시 뽑으니 다르다 | 늦게 들어오는 데이터, 재적재 | 기준 시각과 스냅샷을 고정해 다시 비교 |

날짜가 어긋나면 시간대를 먼저 본다. 같은 결제 매출(UTC 저장)을 UTC 날짜와 KST 날짜로 묶으면 다음처럼 다르다.

```sql
SELECT (ordered_at AT TIME ZONE
          'Asia/Seoul')::date AS d_kst,
  SUM(amount) AS rev
FROM orders_ok
WHERE status = 'paid'
GROUP BY 1;
```

| 날짜 | UTC 기준 | KST 기준 |
|---|---|---|
| 9월 1일 | 170000 | 75000 |
| 9월 2일 | 210000 | 253000 |
| 9월 3일 | 없음 | 52000 |

기간 전체의 합은 두 쪽 다 380,000이고 날짜별 값만 다르다. 일 단위 보고는 기준 시간대를 쓴다. 시간대와 나눗셈은 방언마다 다르다.

| 작업 | PostgreSQL | BigQuery | MySQL |
|---|---|---|---|
| UTC 저장 시각을 KST 날짜로 | `(ts AT TIME ZONE 'Asia/Seoul')::date` (ts 가 timestamptz)<Ref n={1} /> | `DATE(ts, 'Asia/Seoul')`<Ref n={2} /> | `DATE(CONVERT_TZ(ts, '+00:00', '+09:00'))`. 이름 시간대는 시간대 테이블이 필요하다<Ref n={3} /> |
| 정수 나누기 정수 | 소수점 아래를 버린다(5 / 2 는 2)<Ref n={4} /> | FLOAT64로 나온다<Ref n={5} /> | 소수(decimal)로 나온다<Ref n={6} /> |
| 분모가 0 | `NULLIF(b, 0)`로 감싼다 | `SAFE_DIVIDE(a, b)`는 NULL<Ref n={7} /> | NULL이 나온다<Ref n={6} /> |

PostgreSQL에서 ts가 시간대 없는 `timestamp`이면 `AT TIME ZONE 'Asia/Seoul'`은 값을 서울 시각으로 간주하는 반대 방향 변환이다. UTC로 저장했다면 `(ts AT TIME ZONE 'UTC') AT TIME ZONE 'Asia/Seoul'`로 두 번 쓴다.<Ref n={1} />

## 의사결정 메모를 쓸 때

규칙: 결정할 것을 예 또는 아니오로 답할 수 있게 첫 줄에 쓴다.

| 항목 | 쓸 내용 | 쓰지 말 것 |
|---|---|---|
| 결정할 것 | 질문 한 문장과 기한 | 분석 배경 설명 |
| 권고 | 하나. 보류도 권고다 | 선택지만 나열 |
| 근거 수치 | 2-3개. 단위, 기간, 모수, 비교 기준 포함 | 표 10개 첨부 |
| 위험 | 틀렸을 때 비용, 되돌릴 수 있는지 | 막연한 우려 |
| 확인 안 된 것 | 항목별로 확인 방법과 시점 | 본문 곳곳에 흩어 쓰기 |

## 숫자를 표기할 때

| 항목 | 규칙 | 나쁜 예 → 고친 예 |
|---|---|---|
| 단위 | 단위를 붙이고 한 보고서에서 통일 | 380000 → 380,000원 |
| 기간 | 시작과 끝, 시간대 | 9월 → 9월 1일부터 9월 30일(KST) |
| 모수 | 비율 옆에 분자/분모 | 12% → 12.0%(48/400) |
| 비교 기준 | 무엇 대비인지 | 증가 → 8월 대비 증가 |
| 소수점 | 구간 폭이 허용하는 자리까지. 보고서 안에서 통일(관행) | 12.0432% → 12.0% |
| %p와 % | 비율의 차이는 %p, 상대 변화는 %. 하나만 쓰면 어느 쪽인지 밝힌다 | 12.0에서 13.5로 올랐다 → +1.5%p(상대 +12.5%) |

작은 모수의 변화율은 쓰지 마라. 2건에서 3건은 +50%지만 건수를 그대로 쓰는 편이 낫다.

## 불확실성을 쓸 때

규칙: 표본에서 나온 비율은 점 하나가 아니라 범위로 쓴다. 표본이 클수록 범위가 좁아진다.

<Figure caption="같은 12.0%라도 n=100이면 구간이 7.0에서 19.8%로 넓다. n이 4배가 되면 폭이 약 절반이 된다. 가정한 값의 계산이다.">
  <IntervalWidth />
</Figure>

비율의 구간은 Wilson 식으로 계산했다. 단순 정규근사는 하한이 음수가 될 수 있다.<Ref n={8} /> 계산법은 d09에서 다룬다. 가정 예: 9월 48/400은 12.0%(95% 구간 9.2에서 15.6%), 8월 42/400은 10.5%(7.9에서 13.9%)다. 차이 +1.5%p의 95% 구간은 정규근사로 -2.9에서 +5.9%p이며 0을 포함한다.

| 상황 | 쓰는 법 | 쓰지 말 것 |
|---|---|---|
| 표본 기반 비율 | 점추정, 구간, n을 함께 | 점추정만 |
| 두 값의 차이 | 차이의 구간. 0을 포함하면 방향을 단정하지 않는다 | 구간이 0을 지나는데 "개선" |
| 전수 합계 | 구간 없이 쓰고 누락, 정의의 한계를 쓴다 | 전수 합에 오차 범위 |
| 약 | 반올림할 때만. 약 38만원 | 모르는 값을 얼버무릴 때 |
| 추정 | 모형이나 가정으로 구한 값에만. 가정을 옆에 | 직접 센 값에 |
| 확인 안 된 것 | 본문과 떼어 목록으로. 확인 방법 포함 | 문장 곳곳에 흩어 쓰기 |

한계와 오차 가능성을 밝히는 것은 통계 실무 윤리 지침도 요구한다.<Ref n={9} />

| 비분석 팀 | 자기 업무에 영향 주는 숫자와 뜻, 쓰면 안 되는 해석 | 통계 용어, 구간 계산 |

## 다시 돌릴 수 있게 남길 때

규칙: 같은 쿼리와 조건으로 같은 숫자가 나와야 한다. 통계 실무 윤리 지침도 방법과 문서를 공유해 재현을 돕도록 권한다.<Ref n={9} />

| 남길 것 | 방법 |
|---|---|
| 쿼리와 파라미터 | 전문을 버전 관리에 두고 기간, 제외 조건은 맨 위에 모은다 |
| 기준 시각 | 뽑은 시각과 데이터 기준 시점 둘 다. 늦게 들어오는 데이터는 재실행 값을 바꾼다 |
| 데이터 스냅샷 | 테이블, 적재 일자, 행 수. 원천이 덮어써지면 결과 표도 저장 |
| 변경 이력 | 날짜, 바뀐 숫자, 이유. 이미 공유한 숫자가 바뀌면 그 사실부터 알린다 |

```sql
-- report: d13 sample v3
-- params: 2026-09-01 ~ 2026-09-03 KST
-- snapshot: orders, 2026-10-02 09:00
-- status: paid only
```

## 리뷰를 요청할 때

규칙: "한번 봐주세요"가 아니라 무엇을 검토해 달라는지 쓴다.

- 검토 대상: 지표 정의와 필터, 조인 조건, 시간대를 줄 번호로 짚는다.
- 이미 확인한 것과 안 한 것을 나눠 쓴다. 가장 걱정되는 곳(예: 상품 조인 뒤 금액)도 쓴다.
- 쿼리, 결과 표, 대조한 원천 값, 기한을 함께 준다.

## 흔한 보고 실수

| 실수 | 왜 문제인가 | 처방 |
|---|---|---|
| 결론이 맨 끝에 있다 | 읽는 사람이 결정을 못 한다 | 첫 문장에 결론과 숫자 |
| 숫자에 단위, 기간, 모수가 없다 | 다른 숫자와 비교가 안 된다 | 표기 규칙 표대로 쓴다 |
| 구간 없이 "개선됐다" | 차이가 우연일 수 있다 | 차이의 구간을 쓰고 0을 포함하면 단정하지 않는다 |
| 이전 보고서 숫자를 복사하거나 바뀐 숫자를 말하지 않는다 | 정의, 기간이 달라졌을 수 있고 신뢰를 잃는다 | 다시 돌려 대조하고 변경 이력을 먼저 알린다 |
| 극단값 1건을 말하지 않는다 | 합계와 평균이 한 건에 달렸다 | 한 건 제외 값을 함께 쓴다 |

## 점검 체크리스트

- 질문, 지표 정의, 기간, 시간대, 제외 조건을 한 줄로 적었는가.
- 행 수와 합계가 원천과 같은가(정수 합계 차이 0). 중복 키와 조인 전후를 확인했는가.
- 다른 경로로 재계산한 값이 같은가.
- 세그먼트의 합이 전체와 같은가(값 없음 조각 포함).
- 상위, 하위, 무작위 행을 원본으로 봤는가. 극단값 1건 제외 값을 썼는가.
- 결과 방향을 이전 값, 외부 수치와 비교했는가.
- 첫 문장에 결론과 숫자가 있고 단위, 기간, 모수가 붙었는가. %p와 %를 구분했는가.
- 확인 안 된 것이 따로 모여 있고, 쿼리와 기준 시각, 스냅샷을 남겼는가.
