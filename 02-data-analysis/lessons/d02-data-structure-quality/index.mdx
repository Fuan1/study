## 처음 보는 테이블을 받았을 때

규칙: 먼저 "이 테이블의 한 행은 ___ 한 건이다"를 적어라. 이것을 grain(한 행의 단위)이라 부른다.<Ref n={1} /> 적지 못하면 합계와 건수를 믿지 마라.

| 확인 | 방법 | 판단 |
|---|---|---|
| 한 행의 뜻 | 컬럼명, 샘플 10행, 정의서 | "주문 한 건", "사용자 하루" 처럼 한 문장 |
| 기본키 후보 | 행 수와 키 distinct 수 비교 | 같으면 후보. 다르면 중복이거나 복합키 |
| 복합키 | 키 둘로 group by 후 having count(*) > 1 | 0행이면 둘이 합쳐 키 |
| 외래키 | 다른 테이블의 키와 같은 값을 담은 컬럼 | 상대 테이블에서 유일한지, 짝 없는 값이 있는지 |
| 키의 NULL | 키 컬럼 NULL 개수 | 하나라도 있으면 조인에서 빠진다 |

정의서에 "유일"이라고 적혀 있어도 직접 센다. 적재가 두 번 돌면 키가 중복된다.

## 테이블 종류별 집계 주의점

규칙: 한 행의 뜻으로 종류를 가르고, 종류마다 정해진 집계만 한다.

| 종류 | 한 행 | 집계 주의 |
|---|---|---|
| 이벤트 로그 | 사건 한 번(주문, 클릭) | 건수와 고유 사용자 수를 구분한다. 재전송으로 중복될 수 있다 |
| 스냅샷 | 어느 시점의 상태 하나(일별 잔액, 재고) | 날짜를 가로질러 더하지 않는다. 하루를 고르거나 평균을 낸다 |
| 마스터(차원) | 개체 하나의 현재 값(사용자, 상품) | 키가 유일해야 한다. 덮어쓴 값이라 과거 사건에 현재 속성이 붙는다 |
| 매핑 | 두 키의 짝 하나(상품과 카테고리) | N:M 이 흔하다. 조인하면 행이 늘어난다. 유효 기간 컬럼이 있는지 본다 |

잔액은 계좌끼리는 더해도 되지만 날짜끼리는 더할 수 없다.<Ref n={1} /> 가상의 일별 잔액 `acct_daily`(계좌 3개, 3일, 9행)로 본다.

```sql
select sum(balance) as total
from acct_daily;
```

| total |
|---|
| 560000 |

```sql
select sum(balance) as total
from acct_daily
where snap_date = '2026-09-30';
```

| total |
|---|
| 190000 |

## 조인하기 전에 관계를 확인할 때

규칙: 조인 키가 양쪽에서 유일한지 먼저 센다. 유일하지 않은 쪽의 행 수만큼 반대쪽 행이 복제된다.

| 관계 | 뜻 | 조인 후 행 수 | 주의 |
|---|---|---|---|
| 1:1 | 양쪽 키가 유일 | 그대로 | 유일하다고 믿지 말고 센다 |
| 1:N | 한쪽만 유일 | N 쪽 행 수 | 1 쪽 금액을 더하면 부푼다 |
| N:M | 양쪽 모두 중복 | 곱으로 늘어난다 | 한쪽을 먼저 집계하거나 매핑 테이블을 거친다 |

가상의 주문 `orders_mini`(3건, 금액 10000, 20000, 30000)와 품목 `order_items`(6행)로 본다. 먼저 키가 어느 쪽에서 중복되는지 센다.

```sql
select count(*) as n_rows,
       count(distinct order_id) as n_ids
from order_items;
```

| n_rows | n_ids |
|---|---|
| 6 | 3 |

품목이 N 쪽이다. 나쁜 쿼리는 이 상태에서 주문 금액을 더한다.

```sql
select sum(o.amount) as total
from orders_mini o
join order_items i
  on i.order_id = o.order_id;
```

| total |
|---|
| 130000 |

주문 합계는 60000이다. 고친 쿼리는 N 쪽을 주문 단위로 먼저 집계한 뒤 조인한다.

```sql
select sum(o.amount) as total,
       sum(i.n_items) as n_items
from orders_mini o
join (select order_id,
             count(*) as n_items
      from order_items
      group by order_id) i
  on i.order_id = o.order_id;
```

| total | n_items |
|---|---|
| 60000 | 6 |

<Figure caption="1:N 조인 뒤 1 쪽 금액을 더하면 N 쪽 행 수만큼 복제되어 합계가 부푼다. 가상 데이터다.">
  <JoinInflate />
</Figure>

- 조인 후 `count(*)` 와 합계가 조인 전과 같은지 본다.
- 내부 조인은 짝 없는 행을 지운다. 지워도 되는지 정하고 쓴다.
- LEFT JOIN 조건 위치 같은 나머지 함정은 관련 글을 따른다.

## 시간 컬럼을 다룰 때

규칙: 시간 컬럼마다 세 가지를 확인한다. 저장 시간대, 이벤트 시각인지 적재 시각인지, 값의 범위.

- PostgreSQL 의 `timestamptz` 는 내부에 UTC 로 저장하고 `timestamp` 는 시간대 정보가 없다.<Ref n={2} /> 시간대 표시가 없는 문자열은 정의서나 알려진 사건으로 시간대를 확인한다.
- 이벤트 시각은 일이 일어난 때, 적재 시각은 데이터가 들어온 때다. 분석 기간은 이벤트 시각으로, 신선도는 적재 시각으로 본다. 이벤트가 적재보다 늦으면 이상하다.
- 날짜별 집계는 보고 기준 시간대(예: KST)로 바꾼 뒤 묶는다.

| 할 일 | PostgreSQL | BigQuery | MySQL |
|---|---|---|---|
| UTC 시각을 KST 날짜로 | timestamptz 면 `(ts at time zone 'Asia/Seoul')::date`. timestamp 면 `at time zone 'UTC'` 를 먼저 붙인다<Ref n={2} /> | TIMESTAMP 면 `DATE(ts, 'Asia/Seoul')`<Ref n={3} /> | `DATE(CONVERT_TZ(ts,'+00:00','+09:00'))`. 이름(`'Asia/Seoul'`)은 시간대 테이블이 있어야 한다<Ref n={4} /> |

`ordered_at` 이 UTC `timestamptz` 인 가상 `orders`(14행, 다음 절)로 본다. 나쁜 쿼리는 변환 없이 날짜로 묶는다.

```sql
select ordered_at::date as d_utc,
       count(*) as n
from orders
group by 1
order by 1;
```

고친 쿼리는 KST 로 바꾼 뒤 묶는다.

```sql
select (ordered_at at time zone
        'Asia/Seoul')::date as d_kst,
       count(*) as n
from orders
group by 1
order by 1;
```

| 날짜 | 앞 쿼리(UTC 날짜) | 고친 쿼리(KST 날짜) |
|---|---|---|
| 09-28 | 2 | 2 |
| 09-29 | 3 | 2 |
| 09-30 | 5 | 4 |
| 10-01 | 3 | 5 |
| 10-05 | 1 | 1 |

`timestamptz::date` 는 세션 시간대를 따른다. 표는 UTC 세션을 가정해 sqlite 로 같은 논리를 돌린 값이다.

<Figure caption="같은 이벤트가 UTC 날짜로는 09-29, KST 날짜로는 09-30 이다. 경계가 다르면 일별 건수가 하루씩 어긋난다.">

## NULL 을 만났을 때

규칙: NULL 을 보면 먼저 의미를 정한다. 의미에 따라 처리가 다르다.

| 의미 | 예 | 처리 |
|---|---|---|
| 모름 | 금액 누락, 가입 때 입력 안 한 값 | 0 으로 채우지 말고 비율로 보고한다. 평균에서는 빠진다 |
| 해당 없음 | 쿠폰을 안 쓴 주문의 쿠폰 | 정상 값이다. "쿠폰 없음" 범주로 센다 |
| 아직 없음 | 진행 중인 건의 종료 시각 | 기간 계산 때 현재 시각으로 둘지 제외할지 정한다 |
| 빈 문자열 | 입력했다 지웠거나 적재가 NULL 대신 넣은 값 | NULL 과 같은 뜻인지 확인해 하나로 통일한다 |
| 0 | 실제 0원 | 측정된 값이다. NULL 과 다르다 |

NULL 과의 비교는 참도 거짓도 아닌 NULL 이 되어 where 에서 걸러진다. 가상 `orders` 에서 실제로 돌린 결과다.

| 쓴 것 | 결과 | 고침 |
|---|---|---|
| `coupon <> 'WELCOME'` | 1행. NULL 9행이 빠진다 | `coalesce(coupon,'') <> 'WELCOME'` 는 10행. 또는 `is distinct from` |
| `user_id = NULL` | 항상 0행 | `user_id is null` |
| `avg(amount)` | 13행으로 평균을 낸다. NULL 1행은 분모에서 빠진다 | NULL 을 0 으로 볼지 정하고 쿼리에 적는다 |

NULL 을 0 으로 채우면 모름이 측정값으로 둔갑한다. 채우는 기준은 정제 글에서 다룬다.

| 할 일 | PostgreSQL | BigQuery | MySQL |
|---|---|---|---|
| NULL 안전 비교 | `a is not distinct from b`<Ref n={5} /> | 확인 필요 | `a <=> b`<Ref n={6} /> |
| 조건부 개수 | `count(*) filter (where c is null)`<Ref n={7} /> | `countif(c is null)`<Ref n={8} /> | `sum(c is null)`. 조건식은 1 또는 0 을 돌려준다<Ref n={6} /> |

## 처음 보는 테이블 점검 쿼리

규칙: 처음 보는 테이블에는 아래 순서로 돌린다. 가상 `orders`(14행, UTC)에서 실행한 결과다. 컬럼은 order_id, user_id, status, amount, coupon, ordered_at(이벤트 시각), loaded_at(적재 시각)이다.

### 행 수와 키 유일성

```sql
select count(*) as n_rows,
       count(distinct order_id) as n_ids
from orders;
```

| n_rows | n_ids |
|---|---|
| 14 | 13 |

행 수와 distinct 수가 다르면 중복 키를 찾는다.

```sql
select order_id, count(*) as n
from orders
group by order_id
having count(*) > 1;
```

| order_id | n |
|---|---|
| 1009 | 2 |

1009 의 두 행은 loaded_at 만 다르다. 같은 주문이 두 번 적재된 것이다.

### 컬럼별 NULL 과 빈 문자열

```sql
select count(*) as n,
  count(*) - count(user_id) as n_user,
  count(*) - count(amount) as n_amt,
  count(*) - count(coupon) as n_cpn,
  count(*) filter (where coupon = '')
    as n_cpn_empty
from orders;
```

| n | n_user | n_amt | n_cpn | n_cpn_empty |
|---|---|---|---|---|
| 14 | 1 | 1 | 9 | 1 |

NULL 비율은 `(count(*) - count(컬럼)) / count(*)` 이다. user_id 와 amount 는 각 1건(7.1퍼센트)이다. coupon 은 9건(64.3퍼센트)이 해당 없음이라 정상이고, 빈 문자열 1건은 NULL 과 통일할지 정한다.

### 날짜 범위와 적재 시각

```sql
select min(ordered_at) as first_at,
       max(ordered_at) as last_at,
       max(loaded_at) as last_load
from orders;
```

| first_at | last_at | last_load |
|---|---|---|
| 2026-09-28 01:15:00 | 2026-10-05 09:00:00 | 2026-10-02 03:00:00 |

last_at 이 last_load 보다 늦다. 이벤트가 적재보다 늦은 행을 센다.

```sql
select count(*) as n_future
from orders
where ordered_at > loaded_at;
```

| n_future |
|---|
| 1 |

### 범주 분포

```sql
select status, count(*) as n,
  round(100.0 * count(*)
    / sum(count(*)) over (), 1) as pct
from orders
group by status
order by n desc, status;
```

| status | n | pct |
|---|---|---|
| paid | 10 | 71.4 |
| refunded | 2 | 14.3 |
| PAID | 1 | 7.1 |
| canceled | 1 | 7.1 |

`paid` 와 `PAID` 가 따로 센다. `lower(status)` 로 묶으면 paid 11건이 된다.

## 데이터 품질을 점검할 때

규칙: 쿼리를 돌리기 전에 합격 기준을 정한다. 허용 NULL 비율, 허용 지연 같은 값은 정해진 표준이 아니라 지표마다 합의해서 정한다.

| 차원 | 무엇을 검사하나 | 어떻게 | 예제 결과 |
|---|---|---|---|
| 완전성 | 필수 값이 채워졌나 | 컬럼별 NULL 과 빈 문자열 비율 | user_id NULL 1건 |
| 유일성 | 같은 대상이 한 번만 있나 | 키로 group by 후 having count(*) > 1 | 1009 가 2행 |
| 유효성 | 형식, 범위, 허용값 안인가 | `count(*) filter (where amount <= 0)`, 허용 목록 밖 값 | amount 0 이하 2건 |
| 적시성 | 기대한 시점까지 최신인가 | max(loaded_at) 과 현재 시각의 차, 날짜별 행 수 공백 | 마지막 적재 10-02 03:00 UTC |
| 일관성 | 같은 것이 같게 적혔나 | 대소문자와 표기 변형, 테이블 간 합계 대조 | paid 와 PAID |

<Callout kind="note">
다섯 차원은 흔히 쓰는 분류다. DAMA UK 백서는 정확성(실제 세계와 일치하는가)을 더해 여섯 차원으로 나눈다.<Ref n={9} /> 정확성은 외부 기준과 대조해야 해서 테이블 안의 쿼리만으로는 못 본다.
</Callout>

## 숫자가 이상할 때

| 증상 | 원인 | 확인 쿼리 |
|---|---|---|
| 행 수가 갑자기 늘거나 줄었다 | 중복 적재, 적재 누락, 필터 변경 | 적재일별 `count(*)` 와 `count(distinct 키)` |
| 합계가 다른 표와 안 맞는다 | 1:N 조인 복제, 중복 행, 시간대 경계, 필터 차이 | 조인 전후 합계 대조, 키 중복 쿼리 |
| 중복 ID | 재적재, 재전송, 키가 사실 복합키 | `group by 키 having count(*) > 1` 후 두 행을 나란히 본다 |
| 미래 날짜 | 시간대 오표기, 시계 오류, 테스트 데이터 | `where 이벤트시각 > 적재시각` |
| 최근 날짜만 행이 적다 | 적재가 아직 끝나지 않았다 | `max(loaded_at)`, 마지막 날을 빼고 비교 |
| 같은 값이 둘로 갈린다 | 대소문자와 공백 불일치 | `group by lower(trim(col))` 와 비교 |
| 일별 건수가 보고서와 하루 어긋난다 | 시간대 경계 | UTC 와 KST 로 각각 묶어 비교 |

## 나쁜 예와 고친 예

| 나쁜 예 | 고친 예 | 이유 |
|---|---|---|
| 이름만 보고 `sum(amount)` | 한 행의 뜻을 적고 샘플 10행을 본 뒤 집계 | 한 행이 품목이면 주문 금액이 복제된다 |
| `count(*)` 를 사용자 수로 보고 | `count(distinct user_id)` | 한 사람이 여러 행이다 |
| 최근 7일을 `loaded_at` 으로 자름 | `ordered_at` 으로 자르고 loaded_at 은 신선도에만 사용 | 늦게 적재된 사건이 엉뚱한 날에 들어간다 |
| 중복 ID 를 보고 바로 삭제 | 두 행의 차이를 보고 남길 행의 기준을 기록한 뒤 처리 | 값이 다르면 어느 쪽이 맞는지 정해야 한다 |

## 점검 체크리스트

- 한 행의 뜻을 한 문장으로 적었는가.
- 기본키 후보의 `count(*)` 와 `count(distinct 키)` 가 같은가.
- 키 컬럼에 NULL 이 없는가.
- 테이블 종류(이벤트, 스냅샷, 마스터, 매핑)에 맞는 집계만 하는가.
- 조인 전에 양쪽 키의 유일성을 세고, 조인 후 행 수와 합계를 대조했는가.
- 시간 컬럼의 저장 시간대와 이벤트 시각인지 적재 시각인지 확인했는가.
- 날짜별 집계 전에 보고 기준 시간대로 변환했는가.
- NULL, 빈 문자열, 0 을 구분해서 세었는가.
- 날짜 범위가 기대와 같고 미래 날짜가 없는가, 마지막 적재 시각이 기대 시점 안인가.
- 범주 컬럼에 표기 변형이 없는가.
- 합격 기준을 먼저 정하고 결과를 기록했는가.
