## 정제를 시작할 때

규칙: 원본은 읽기 전용이고, 정제는 다시 만들 수 있는 형태로 한다.

- 원본(raw)에 UPDATE 나 DELETE 를 하지 마라. 결과는 뷰나 파생 테이블로 만든다.
- 순서는 정규화, 중복, 결측, 이상치다. 표기가 갈린 키는 중복으로 안 잡히고, 중복이 남으면 평균이 틀어진다.
- 단계마다 전후 행 수를 센다. 줄어든 행은 이유가 있어야 하고, 늘어난 행은 조인 문제다(d05).

## 결측이 있을 때

### 결측 비율을 셀 때

규칙: NULL 만 세지 말고 빈 문자열과 자리표시자(`N/A`, `-`, `0`, `-1`, `9999`)도 센다. `COUNT(컬럼)` 은 NULL 을 세지 않는다.

```sql
WITH cnt AS (
  SELECT COUNT(*) AS n,
    COUNT(amount) AS a,
    COUNT(country) AS c,
    COUNT(NULLIF(TRIM(country), ''))
      AS r
  FROM orders_raw
)
SELECT n,
  ROUND(100.0 * (n - a) / n, 1)
    AS amount_pct,
  ROUND(100.0 * (n - c) / n, 1)
    AS country_pct,
  ROUND(100.0 * (n - r) / n, 1)
    AS country_real_pct
FROM cnt;
```

| n | amount_pct | country_pct | country_real_pct |
|---|---|---|---|
| 22 | 13.6 | 9.1 | 18.2 |

`country` 는 NULL 만 세면 9.1퍼센트, 빈 문자열까지 세면 18.2퍼센트다.

### 결측 원인을 따질 때

규칙: 처리는 비율보다 원인으로 고른다. 원인은 셋으로 나눈다.<Ref n={1} />

| 유형 | 모양 | 삭제하면 |
|---|---|---|
| 무작위 누락(MCAR) | 값·그룹과 무관(전송 오류) | 평균은 안 틀어지고 행만 줄어든다 |
| 관측 열에 따라 누락(MAR) | 채널·국가·기간별로 결측률이 다르다 | 결측이 많은 집단이 덜 반영되어 틀어질 수 있다 |
| 값 때문에 누락(MNAR) | 고액일수록 입력을 피한다 | 평균이 틀어진다 |

MAR 은 결측 여부를 0과 1로 만들어 `AVG(amount_missing)` 을 그룹별로 비교해 본다. MNAR 은 데이터만으로 확정할 수 없으니 수집 담당자에게 확인한다.

### 처리 방법을 고를 때

규칙: 비율과 원인으로 고른다. 5퍼센트와 30퍼센트는 이 글의 작업 기준이지 표준이 아니다.

| 상황 | 처리 | 주의 |
|---|---|---|
| 5퍼센트 미만, 무작위로 보임 | 그 분석에서만 해당 행을 제외한다 | 제외한 행 수를 기록한다 |
| 특정 집단·기간·채널에 몰림 | 표시 열을 만들고 집단별로 본다 | 전체 평균 대체는 집단 차이를 지운다 |
| 값 때문에 빈 것으로 의심(MNAR) | 대체하지 않는다. 최소·최대로 가정한 결과 범위를 보고한다 | 이유가 데이터에 없다 |
| 30퍼센트 이상 | 그 열을 쓰는 분석을 보류하고 원인부터 확인한다 | 결과가 대체 방식에 좌우된다 |
| 그래도 채워야 한다 | 중앙값(집단이 있으면 집단 중앙값) + 표시 열 | 대체가 든 통계에는 표시한다 |
| 빈 것이 의미(쿠폰 NULL 은 쿠폰 없음) | 값(`none`)으로 바꾸고 기록한다 | 업무 정의를 확인한다 |

표시 열(`amount_missing`)은 대체한 행을 추적하는 용도다. 회귀에 넣으면 추정이 틀어질 수 있다.<Ref n={1} />

### 평균으로 채우고 싶을 때

규칙: 평균 대체는 평균만 지킨다. 표준편차와 상관은 줄어든다.<Ref n={1} /> 아래는 가상 10,000건(금액과 방문 수, 상관 0.63)을 파이썬으로 만들어 계산한 값이다. 무작위는 29퍼센트를 임의로, 값 때문에는 중앙값 이상 값의 60퍼센트를 뺐다.

## 중복이 있을 때

규칙: 중복은 세 종류로 나누고 종류마다 처리를 다르게 한다.

| 종류 | 모양 | 처리 |
|---|---|---|
| 완전 중복 | 모든 열이 같다(적재 두 번) | 1건만 남긴다 |
| 키 중복 | 키가 같고 다른 열이 다르다(갱신 이력) | 남길 행의 규칙(최신 등)을 정해 1건만 남긴다 |
| 의미 중복 | 키는 다르나 같은 사실(더블 클릭 주문) | 같은 사용자·금액·날짜로 후보만 뽑고, 삭제는 업무 확인 뒤 한다 |

행 수에서 DISTINCT 행 수를 뺀 것이 완전 중복, DISTINCT 행 수에서 키 수를 뺀 것이 키 중복이다.

```sql
WITH d AS (
  SELECT DISTINCT * FROM orders_raw
)
SELECT
  (SELECT COUNT(*) FROM orders_raw)
    AS n_rows,
  (SELECT COUNT(*) FROM d)
    AS n_distinct,
  (SELECT COUNT(DISTINCT order_id)
     FROM orders_raw) AS n_keys;
```

| n_rows | n_distinct | n_keys |
|---|---|---|
| 22 | 21 | 20 |

완전 중복 1건(주문 3), 키 중복 1건(주문 7)이다. ROW_NUMBER 로 키별 순번을 매기고 순번 1만 남긴다.

```sql
WITH latest AS (
  SELECT *,
    ROW_NUMBER() OVER (
      PARTITION BY order_id
      ORDER BY updated_at DESC
    ) AS rn
  FROM orders_raw
)
SELECT order_id, amount, updated_at, rn
FROM latest
WHERE order_id = 7
ORDER BY rn;
```

| order_id | amount | updated_at | rn |
|---|---|---|---|
| 7 | 60 | 2026-03-05 | 1 |
| 7 | 55 | 2026-03-03 | 2 |

- 같은 시각의 행이 있으면 남을 행이 정해지지 않는다. `ORDER BY` 에 적재 번호 같은 tie-breaker 를 더해라.
- 최신이 항상 정답은 아니다. 남길 기준은 업무에 물어 정한다.
- 주문 19와 20은 의미 중복 후보라 지우지 않고 기록한다.

## 이상치가 있을 때

### 이상치를 찾을 때

규칙: 업무상 불가능한 값(도메인 규칙)을 먼저 걸러내고, 통계 기준은 후보를 표시하는 데 쓴다.<Ref n={2} />

| 방법 | 계산 | 한계 |
|---|---|---|
| 도메인 규칙 | 금액 0 이하, 미래 날짜, 나이 120 초과 | 규칙을 아는 사람이 필요하다 |
| IQR 1.5 규칙 | Q1 - 1.5 IQR 미만, Q3 + 1.5 IQR 초과 | 극단값에 덜 흔들린다. 긴 꼬리 쪽 정상값도 걸린다. 1.5는 관행 |
| z-score | 절댓값 3 초과(관행) | 평균과 표준편차가 이상치에 끌려간다. 작은 표본은 3을 못 넘는다 |

IQR 은 Q3 - Q1 이다. 가상 주문 중 금액이 있는 17건은 Q1 25, 중앙값 29, Q3 38, IQR 13이라 하한 5.5, 상한 57.5다. 상한을 넘는 값은 60과 520이고, 극단 기준(Q3 + 3 IQR = 77)을 넘는 것은 520뿐이다.

<Figure caption="IQR 1.5 규칙은 60과 520을 모두 잡지만 60은 정상 주문이다. 후보를 잡는 것과 지우는 것은 다른 결정이다.">
  <IqrFence />
</Figure>

```sql
WITH q AS (
  SELECT
    PERCENTILE_CONT(0.25) WITHIN GROUP
      (ORDER BY amount) AS q1,
    PERCENTILE_CONT(0.75) WITHIN GROUP
      (ORDER BY amount) AS q3
  FROM orders_clean
),
f AS (
  SELECT q1 - 1.5 * (q3 - q1) AS lo,
         q3 + 1.5 * (q3 - q1) AS hi
  FROM q
)
SELECT o.order_id, o.amount
FROM orders_clean o, f
WHERE o.amount < f.lo
   OR o.amount > f.hi;
```

| order_id | amount |
|---|---|
| 7 | 60 |
| 18 | 520 |

sqlite 에는 분위수 함수가 없어 파이썬과 순번 쿼리로 같은 값을 확인했다. 방언별 문법은 5절 표에 있다.

z-score 는 표본 표준편차를 쓰면 한 값의 z 가 `(n-1)/sqrt(n)` 을 넘을 수 없다. 10건이면 2.85라서 3 기준은 아무것도 못 잡는다.

<Figure caption="10건 이하에서는 어떤 값도 z 3을 넘지 못한다. 막대는 표본 크기별 z 최댓값이다.">
  <ZLimit />
</Figure>

이상치가 둘이면 서로 가린다. 위 금액에 480을 더한 18건에서 520의 z 는 2.87, 480은 2.61이지만 IQR 상한(62.4)은 둘 다 잡는다.

### 이상치를 처리할 때

규칙: 오류로 확인된 것만 고치거나 뺀다. 실제 값이면 행을 지키고 요약 방법을 바꾼다. 아래는 위 17건의 결과다.

| 처리 | 쓰는 때 | 평균 | 중앙값 |
|---|---|---|---|
| 그대로 두고 중앙값 요약 | 실제 값이고 평균이 목적이 아니다 | 60.1 | 29 |
| 제거 | 입력 오류가 확인됐다(16건) | 31.4 | 28.5 |
| 윈저라이징(경계값으로 바꾸기) | 값은 맞지만 영향이 과하다. 상한 57.5로 | 32.8 | 29 |
| 로그 변환 | 오른쪽으로 길고 곱셈 단위로 퍼진다 | 35.3(기하평균) | 29 |

로그 변환은 모델링·시각화용이고 보고 숫자는 원래 단위로 되돌린다. 판단 순서는 이렇다.

1. 도메인 규칙을 어기나. 그렇다면 오류다. 고치거나 제외하고 기록한다.
2. 가능한 값인가. 그렇다면 지우지 않고 윈저라이징이나 중앙값을 쓴다.
3. 모르겠다면 표시만 하고, 포함·제외 결과를 함께 보고한다.

### 이상치를 지우면 안 될 때

- 이상치가 분석 대상일 때(사기, 장애, 대량 구매).
- 원인을 확인하지 못했을 때, 표본이 작아 한 건의 비중이 클 때, 원래 오른쪽으로 긴 분포(금액)일 때.
- 지우면 결론이 바뀔 때. 두 결과를 함께 보고한다.

## 형 변환과 문자열을 맞출 때

규칙: 변환 전에 실패할 행 수를 세고, 원본 열은 남기고 새 열을 만든다.

| 항목 | 확인 | 처리 |
|---|---|---|
| 공백 | 앞뒤 공백, 탭, 줄바꿈, NBSP | `TRIM` 이 못 지우는 문자는 따로 센다 |
| 대소문자 | `app`, `APP`, `App` 이 다른 그룹이 된다 | 코드·채널은 `LOWER`. 이름은 의미를 확인한다 |
| 전각/반각 | 전각 영문·숫자, 반각 기호 | NFKC 정규화. 키에 쓰기 전에 바뀌는 범위를 확인한다 |
| 숫자·날짜 문자열 | `1,200`, `12%`, 섞인 날짜 형식 | 기호를 지우고 변환. 실패 행 수를 먼저 센다 |
| 단위·통화 | 천 원과 원, KRW 와 USD | 환산 열을 추가하고 환율 기준일을 기록한다 |
| 시간대 | 저장은 UTC, 집계는 업무 시간대 | 일별 집계 전에 변환한다 |

UTC 2026-03-01 15:30은 서울에서 2026-03-02 00:30이라 변환하지 않으면 일별 집계가 하루 어긋난다. NFKC 는 전각 `ＡＢＣ１２３` 을 `ABC123` 으로 바꾸지만 `①` 도 `1` 로 바꾸므로 식별자에는 확인 후 쓴다.

| 작업 | PostgreSQL | BigQuery | MySQL |
|---|---|---|---|
| 분위수(IQR 계산) | `percentile_cont(0.25) WITHIN GROUP (ORDER BY x)`. NULL 은 무시한다 | `PERCENTILE_CONT(x, 0.25) OVER ()`. 윈도우 형태로만 쓴다 | 내장 함수 없음(8.4 기준) |
| 안전한 형 변환 | `CAST` 는 실패하면 오류. 검사는 `pg_input_is_valid`(도입 버전 확인 필요) | `SAFE_CAST(x AS INT64)`. 실패하면 NULL | `TRY_CAST` 없음. `CAST` 는 오류나 경고 |
| NFKC 정규화 | `normalize(x, NFKC)`. 서버 인코딩 UTF8 필요 | `NORMALIZE(x, NFKC)` | 내장 함수 없음 |
| 시간대 변환 | `ts AT TIME ZONE 'Asia/Seoul'` | `DATETIME(ts, 'Asia/Seoul')` | `CONVERT_TZ(dt, 'UTC', 'Asia/Seoul')`. 이름 시간대는 시간대 테이블 필요 |

방언 칸은 각 공식 문서로 확인했다.<Ref n={3} /><Ref n={4} /><Ref n={5} />

## 정제 쿼리를 단계로 나눌 때

규칙: CTE 한 단계에 변환 하나만 두고 이름을 붙인다.

```sql
CREATE VIEW orders_clean AS
WITH norm AS (
  SELECT order_id, user_id,
    LOWER(TRIM(channel)) AS channel,
    amount,
    COALESCE(NULLIF(TRIM(country), ''),
             'unknown') AS country,
    updated_at
  FROM orders_raw
),
latest AS (
  SELECT *,
    ROW_NUMBER() OVER (
      PARTITION BY order_id
      ORDER BY updated_at DESC
    ) AS rn
  FROM norm
)
SELECT order_id, user_id, channel,
  amount, country, updated_at,
  CASE WHEN amount IS NULL
    THEN 1 ELSE 0 END AS amount_missing,
  CASE WHEN amount > 300
    THEN 1 ELSE 0 END AS amount_check
FROM latest
WHERE rn = 1;
```

`amount > 300` 은 가정한 업무 상한이다. `orders_raw` 22행과 `orders_clean` 20행을 세어 대조했다. `' app'`, `APP`, `App` 은 모두 `app` 이 되었고, 결측(3건)과 이상(1건)은 지우지 않고 표시 열로 남겼다.

## 정제 기록을 남길 때

규칙: 남이 봐도 규칙, 이유, 영향을 알 수 있게 한 줄에 모두 쓴다.

| 단계 | 규칙 | 이유 | 행 수 | 담당·일자 |
|---|---|---|---|---|
| 정규화 | channel LOWER+TRIM, country 빈 값은 unknown | 표기 차이로 그룹이 갈라짐 | 22에서 22 | A · 03-09 |
| 중복 | order_id 별 updated_at 최신 1건 | 완전 중복 1, 키 중복 1 | 22에서 20 | A · 03-09 |
| 결측 | amount 대체 안 함, amount_missing 표시 | 3건(15퍼센트), 원인 확인 중 | 20에서 20 | A · 03-09 |
| 이상치 | 300 초과는 amount_check 표시만 | 주문 18(520)은 대량 구매인지 확인 중 | 20에서 20 | A · 03-09 |

가상 예시다. 규칙이 바뀌면 이전 줄을 고치지 말고 새 줄을 더한다.

## 나쁜 예와 고친 예

```sql
-- 나쁜 쿼리: 중복을 DISTINCT 로 지움
SELECT DISTINCT * FROM orders_raw;
```

결과는 21행이고 주문 7 의 55와 60이 둘 다 남는다. 고친 쿼리는 ROW_NUMBER 뷰이고 20행이다.

| 나쁜 예 | 고친 예 | 이유 |
|---|---|---|
| 원본에 DELETE 로 이상치 제거 | 뷰에서 표시 열만 추가 | 되돌릴 수 없다 |
| `AVG(COALESCE(amount, 0))` | `AVG(amount)` 와 결측 건수(3) | 같은 뷰에서 평균이 60.1에서 51.1로 내려간다 |

## 증상으로 찾기

| 증상 | 원인 | 처방 |
|---|---|---|
| 같은 채널이 여러 그룹으로 나뉜다 | 공백, 대소문자 차이 | `LOWER(TRIM())` 로 정규화한 뒤 집계한다 |
| 결측률이 0인데 값이 비어 보인다 | 빈 문자열, `N/A` 는 NULL 이 아니다 | `NULLIF(TRIM(x), '')` 로 센다 |
| DISTINCT 후에도 같은 키가 둘이다 | 키 중복(다른 열이 다르다) | 키 기준 ROW_NUMBER 로 1건 남긴다 |
| 평균이 한 건 때문에 튄다 | 이상치 한두 건 | 중앙값을 함께 보고 윈저라이징을 검토한다 |
| 일별 집계가 하루 어긋난다 | UTC 와 업무 시간대 차이 | 변환한 뒤 날짜를 자른다 |

## 점검 체크리스트

- 원본을 수정하지 않았고 정제 결과를 다시 만들 수 있는가.
- 단계마다 전후 행 수를 세고 줄어든 행의 이유를 적었는가.
- 결측률을 열별로 세었고(빈 문자열 포함) 원인을 확인하고 처리를 골랐는가.
- 평균 대체를 썼다면 표시했는가.
- 완전, 키, 의미 중복을 나눠 처리했고 남길 행의 규칙이 있는가.
- 이상치에 도메인 규칙을 먼저 적용했고 지운 결과와 안 지운 결과를 비교했는가.
- 형 변환 실패 행 수, 시간대, 단위, 통화를 확인했는가.
- 정제 기록에 규칙, 이유, 행 수, 담당자, 일자가 있는가.
