### 결정 없는 분석을 걸러낼 때

규칙: 아래 질문에 답하지 못하면 분석을 시작하지 말고 요청자에게 되묻는다.

| 질문 | 이 답이면 멈춘다 |
|---|---|
| 숫자가 높으면 무엇을 하고 낮으면 무엇을 하나 | 두 답이 같다 |
| 결정하는 사람과 기한은 | 기한 뒤에 나온다 |
| 이미 결론이 정해졌나 | 근거 장식만 필요하다 |

| 그 질문에 답할 데이터가 있나 | 측정한 적이 없다 |

## 지표를 정의서로 고정할 때

규칙: 지표마다 정의서 한 장을 만든다. 빈 칸이 있으면 사람마다 다른 숫자를 만든다.

| 항목 | 적는 것 | 비우면 |
|---|---|---|
| 이름 | 한 가지 뜻만 갖는 이름 | 같은 이름에 다른 숫자 |
| 분자 | 무엇을 세는가, 고유 사용자인가 건수인가 | 중복 집계 |
| 분모 | 누구 중에서 비율을 내는가 | 비율의 의미가 바뀐다 |
| 기간 | 시작과 끝, 시간대, 기준 날짜 열 | 경계 근처 숫자가 어긋난다 |
| grain | 결과 한 행이 무엇인가(일 × 플랫폼) | 합계가 안 맞는다 |
| 필터·제외 | 테스트 계정, 취소, 내부 직원 | 조용히 부풀거나 줄어든다 |
| 출처 테이블 | 테이블과 열 이름 | 재현할 수 없다 |
| 갱신 주기 | 언제 몇 시에 다시 계산하나 | 낡은 숫자를 쓴다 |
| 담당 | 정의를 바꿀 수 있는 사람 | 정의가 몰래 바뀐다 |

가정한 예 두 개다.

| 항목 | 주간 활성 사용자 | 일간 구매 전환율 |
|---|---|---|
| 분자 | 7일 안에 핵심 행동(검색, 주문, 저장)을 1번 이상 한 고유 `user_id` 수 | 같은 날 결제 완료 주문이 있는 고유 사용자 수 |
| 분모 | 없음(개수 지표) | 그날 방문한 고유 사용자 수 |
| 기간 | 달력 주, 월요일 00시부터, KST | 하루, KST, 방문일 기준 |
| grain | 주 | 일 × 플랫폼 |
| 필터·제외 | 테스트·내부 계정 제외. 앱 실행만 한 것은 활성이 아니다 | 테스트 계정 제외, 취소 주문 제외 |
| 출처 | `events` | `visits`, `orders` |
| 갱신·담당 | 매주 월요일 06시, 그로스 분석 | 매일 07시, 커머스 분석 |

정의가 바뀌면 이름은 그대로 두지 말고 버전을 올리고 바뀐 날짜를 적는다. 바뀌기 전과 후의 숫자를 한 그래프에 이어 붙이지 마라.

## 선행 지표, 후행 지표, 가드레일을 고를 때

규칙: 결과를 재는 후행 지표 1개를 정하고, 그것을 미리 알려 주는 선행 지표와 해치면 안 되는 가드레일을 함께 정한다. 이 구분은 온라인 실험 교재의 분류(목표, 동인, 가드레일)와 같다.<Ref n={1} />

| 종류 | 고르는 규칙 | 가정한 예 |
|---|---|---|
| 후행(목표) | 최종 성과를 직접 잰다. 늦게 움직인다. 1개 | 4주 재구매율 |
| 선행 | 후행과의 관계를 과거 데이터로 확인한 것만. 빨리 움직인다 | 첫 주 주문 횟수 |
| 가드레일 | 핵심을 올리려다 망가뜨릴 것. 허용 하락폭을 숫자로 미리 적는다 | 취소율 0.5%p 이상 상승 금지 |

- 하지 마라: 선행 지표만 올리기. 클릭이 늘어도 구매가 줄 수 있다.
- 하지 마라: 결과를 본 뒤에 지표와 가드레일을 고르기. 정의서는 분석 전에 확정한다.
- 가드레일 개수는 2개에서 3개가 관행이다. 많으면 매번 어느 하나가 걸린다.

## 정의서를 SQL로 옮길 때

규칙: 정의서 한 줄은 쿼리의 한 곳에 대응한다. 대응이 안 되는 줄은 쿼리에 아직 안 옮긴 것이다. 아래는 일간 구매 전환율이다. 테이블과 값은 가상이며 PostgreSQL 문법이다.

```sql
SELECT
  v.visit_date,
  v.platform,
  COUNT(DISTINCT v.user_id) AS visitors,
  COUNT(DISTINCT o.user_id) AS buyers,
  ROUND(
    1.0 * COUNT(DISTINCT o.user_id)
    / COUNT(DISTINCT v.user_id), 3
  ) AS cvr
FROM visits v
LEFT JOIN orders o
  ON o.user_id = v.user_id
 AND o.order_date = v.visit_date
 AND o.status <> 'canceled'
WHERE v.is_test = 0
  AND v.visit_date BETWEEN '2026-09-01'
                       AND '2026-09-02'
GROUP BY v.visit_date, v.platform
ORDER BY v.visit_date, v.platform;
```

| visit_date | platform | visitors | buyers | cvr |
|---|---|---|---|---|
| 2026-09-01 | app | 3 | 1 | 0.333 |
| 2026-09-01 | web | 4 | 1 | 0.250 |
| 2026-09-02 | app | 2 | 1 | 0.500 |
| 2026-09-02 | web | 3 | 1 | 0.333 |

| 정의서 항목 | 쿼리의 위치 |
|---|---|
| 분자, 분모 | `COUNT(DISTINCT ...)` 두 개. 건수가 아니라 고유 사용자 |
| grain | `GROUP BY`와 `SELECT`의 같은 열 |
| 기간 | `WHERE`의 날짜 조건 |
| 제외(방문자 쪽) | `WHERE v.is_test = 0` |
| 제외(구매 쪽) | `LEFT JOIN`의 `ON`. `WHERE`에 두면 안 된다 |
| 출처 | `FROM`, `JOIN` |
| 갱신, 담당 | 쿼리 밖. 맨 위 주석에 정의서 이름과 버전을 적는다 |

구매 쪽 조건을 `WHERE o.status <> 'canceled'`로 옮기면 구매 없는 방문자 행이 사라져 분모가 구매자 수와 같아지고 네 행의 `cvr`가 모두 1.0이 된다. 같은 데이터에서 `DISTINCT` 없이 행 수로 세고 취소와 테스트 제외를 빼면 09-01 web이 0.250이 아니라 0.500으로 나온다. 조인 조건 위치와 행 증식은 JOIN 글에서 다룬다.

## 지표 숫자가 이상할 때

| 증상 | 원인 | 확인과 처방 |
|---|---|---|
| 월 평균 비율이 합산 비율과 다르다 | 일별 비율을 평균냈다(평균의 평균) | 두 방식으로 계산해 비교. 합산 분자를 합산 분모로 나눈다 |
| 전환율이 100%에 붙는다 | 분모를 `WHERE`로 걸러 구매자만 남았다 | 분모 행 수를 필터 전후로 센다. 조건을 `ON`으로 옮긴다 |
| 비율이 전부 0이다 | 정수끼리 나눴다 | 한쪽에 `1.0 *`을 곱한다 |
| 분모가 0인 날 쿼리가 멈춘다 | 0으로 나눴다 | `NULLIF(분모, 0)`로 NULL을 만든다 |
| 대시보드와 보고서의 활성 사용자가 다르다 | 활성 정의 불일치(로그인 대 핵심 행동, 7일 롤링 대 달력 주) | 정의서의 분자·기간 줄을 나란히 비교한다. 정의별로 같은 기간을 세어 차이를 확인한다 |
| 월말, 자정 근처 숫자가 어긋난다 | 기간 기준 불일치(UTC 대 KST, 주문일 대 결제일, 마감 뒤 취소) | 기준 열과 시간대를 정의서에 쓴다. 경계 시각 행 몇 건을 직접 본다 |
| 플랫폼별 사용자 합이 전체보다 크다 | 고유 사용자를 합산했다. 한 사람이 두 플랫폼을 쓴다 | 합계는 같은 grain으로 다시 `COUNT(DISTINCT)` 한다 |
| 구간별로는 좋은데 전체는 나쁘다 | 구성비 차이 | 아래 집계 수준 규칙 |

### 비율의 평균을 낼 때

규칙: 기간 전체의 비율은 분자의 합을 분모의 합으로 나눈다. 일별 비율의 평균은 방문이 100명인 날과 1,000명인 날을 같은 무게로 센다. 가상의 `daily_summary`(09-01은 방문 1,000명에 구매 50명으로 5%, 09-02는 100명에 20명으로 20%, 09-03은 900명에 45명으로 5%)로 비교한다.

```sql
-- 나쁜 쿼리: 비율의 평균
SELECT ROUND(AVG(
  1.0 * buyers / visitors), 4) AS cvr
FROM daily_summary;
```

| cvr |
|---|
| 0.1000 |

```sql
-- 고친 쿼리: 합의 비율, 0 방어
SELECT ROUND(
  1.0 * SUM(buyers)
  / NULLIF(SUM(visitors), 0), 4
) AS cvr
FROM daily_summary;
```

| cvr |
|---|
| 0.0575 |

방문 2,000명에 구매 115명이므로 5.75%가 맞다. 평균의 평균은 방문이 적은 날의 20%를 3분의 1로 반영해 10%가 나왔다.

### 나눗셈과 0을 다룰 때

방언마다 정수 나눗셈과 0 나누기가 다르다.

| 방언 | 정수 / 정수 | 0으로 나눌 때 |
|---|---|---|
| PostgreSQL | 소수점 아래를 버린다(5 / 2는 2)<Ref n={2} /> | 오류(`division_by_zero`)<Ref n={2} /> |
| MySQL | `/`는 소수 결과, 정수 나눗셈은 `DIV`<Ref n={3} /> | NULL<Ref n={3} /> |
| BigQuery | `/`는 FLOAT64(소수) 결과<Ref n={4} /> | 오류. `SAFE_DIVIDE(a, b)`는 NULL<Ref n={4} /> |

방언과 상관없이 `1.0 *`와 `NULLIF(분모, 0)`를 함께 쓰면 같은 모양으로 읽힌다.<Ref n={2} /> NULL이 된 날은 0%가 아니라 계산 불가라는 뜻이므로 그래프에서 빈 칸으로 둔다.

## 구간별로는 좋은데 전체는 나쁠 때

규칙: 비율을 비교할 때는 전체와 한 단계 아래 구간, 두 수준을 모두 계산한다. 두 수준의 방향이 다르면 구간의 구성비가 다른 것이다.

가정한 A/B 비교다. 방문은 각각 1,000명이다.

| 구간 | A 방문 | A 구매 | A 전환율 | B 방문 | B 구매 | B 전환율 |
|---|---|---|---|---|---|---|
| 모바일 | 800 | 24 | 3.0% | 200 | 5 | 2.5% |
| 데스크톱 | 200 | 24 | 12.0% | 800 | 88 | 11.0% |
| 전체 | 1,000 | 48 | 4.8% | 1,000 | 93 | 9.3% |

<Figure caption="구간별로는 A가 모두 높은데 전체는 B가 높다. B에 전환율이 높은 데스크톱 방문이 80% 몰렸기 때문이다. 수치는 가정이다.">
  <SimpsonBars />
</Figure>

어느 수준을 믿을지는 통계로 정해지지 않고 원인 구조로 정해진다. 구간 기준이 결과에 영향을 주면서 두 안의 구성비를 다르게 만든 교란이면 구간별 값을 쓴다. 안의 효과가 거쳐 가는 중간 단계이면 구간으로 쪼개면 효과가 가려진다.<Ref n={5} /> 판단이 서지 않으면 두 수준을 모두 싣고 구성비를 함께 적는다. 무작위 배정인데 구성비가 이렇게 다르면 배정 오류부터 의심한다.

가정한 가입 코호트 1,000명의 1주차 주문은 1,200건(평균 1.2건)이고, 4주차에는 300명이 남아 900건을 주문했다. 남은 사용자 기준은 3.0건, 코호트 기준은 0.9건이며 유지율은 30%다. 남은 사용자 지표에는 유지율을 함께 싣는다.

## 나쁜 예와 고친 예

| 나쁜 예 | 고친 예 | 이유 |
|---|---|---|
| 활성 사용자가 늘었다 | 주간 활성(핵심 행동 1회 이상, 달력 주, KST)이 늘었다 | 정의가 이름에 따라붙는다 |
| 전환율 3%라고만 보고 | 방문 50,000명 중 구매 1,500명, 3.0% | 분자와 분모가 있어야 검산한다 |
| 일별 전환율의 평균을 월 전환율로 보고 | 월 구매자 합을 월 방문자 합으로 나눔 | 방문이 적은 날이 과대 반영된다 |
| 구매 전환율 하나를 목표로 삼음 | 핵심 1개와 가드레일(취소율 등) | 올리려다 망가지는 것을 잡는다 |
| 4주차에 남은 사용자만 평균 | 가입 코호트 1,000명으로 고정 | 이탈자가 사라지면 지표가 올라간다 |
| 정의를 쿼리 안에만 둠 | 정의서 한 장과 쿼리 주석에 같은 버전 | 쿼리를 읽어야 정의를 안다 |

## 점검 체크리스트

- 요청이 질문, 결정, 지표, 데이터 순서로 적혀 있는가.
- 숫자가 높을 때와 낮을 때의 행동이 다른가.
- 정의서의 아홉 항목이 모두 채워졌는가.
- 이름이 한 가지 뜻만 갖고, 정의 변경에 버전이 있는가.
- 상위 지표가 가지의 곱이나 합으로 맞아떨어지는가.
- 핵심 지표 1개와 가드레일 2개에서 3개, 허용 하락폭이 분석 전에 정해졌는가.
- 분자와 분모가 같은 집합(사용자, 기간, 제외 조건)에서 나오는가.
- 기간 비율이 합의 비율인가. 평균의 평균이 아닌가.
- 비율을 전체와 구간 두 수준에서 비교했고 구성비를 적었는가.
- 시간에 따라 빠지는 사용자는 시작 시점 코호트를 분모로 쓰는가.
